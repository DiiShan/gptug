## 1. 执行摘要：从“有两个模型”升级为“可验收的工程工作流”

### 1.1 核心结论

对这个岗位，合理目标不是让 AI 直接接管芯片设计，而是让它接管一部分**资料整理、跨文件定位、重复实现、实验组织和证据归档**，由工程师保留设计意图、验证充分性、PPA 权衡和签核责任。

建议建设的最小闭环是：

```text
获准的需求与设计资料
  → 有版本和权限的项目上下文
  → 有明确边界的任务合同
  → 模型提出分析/补丁/实验
  → 受控 EDA、仿真、形式验证或数据处理
  → 独立检查 + 人工评审
  → 可追溯的工程交付物
  → 缺陷与经验回流
```

应把成果单位从“生成多少文字/代码”改为“通过既定质量门禁的任务”。模型回答正确、补丁通过仿真、模块通过验证、芯片可以签核，是不同层次，不能相互替代。

### 1.2 首批投入顺序

| 优先级 | 工作流 | 为什么先做 | 首个交付物 |
|---|---|---|---|
| P0 | 综合/时序/回归报告结构化与差异分析 | 输入输出明确，易对照原始数据，修改设计的风险低 | 带原始位置的差异报告与责任候选 |
| P0 | 回归失败归类、日志取证、debug 假设整理 | 减少重复阅读和信息搬运，覆盖设计、验证与硅后 | 失败指纹、证据、反证实验、未决事项 |
| P0 | 规格审查和需求—检查项追踪 | 前移发现歧义，避免后续实现偏离 | 歧义清单、接口契约、检查项映射 |
| P1 | 小范围 RTL 修改与定向测试/SVA 草稿 | 价值高，但必须接入独立验证和代码评审 | 小补丁、测试证据、风险说明 |
| P1 | 综合/后端约束审查与候选优化实验 | 帮设计工程师更快理解物理反馈 | 假设、对照实验、同条件 PPA 比较 |
| P1 | 硅后日志/寄存器分析与实验方案 | 提高定位效率，但不能让模型默认控制实物 | 根因假设矩阵、只读分析、实验审批包 |
| P2 | 大范围架构搜索、多代理长任务、自动 PPA 搜索 | 集成和验证成本高，先证明较小工作流有收益 | 有预算和停止条件的受控探索 |

不建议第一步就微调模型、建立十个自治代理、自动修复全部 lint、自动关闭 coverage hole，或让 AI 直接修改 SDC 以实现时序“变好”。

### 1.3 可用于立项的收益表达

没有内部评测数据，因此当前不能声称 Qwen3.8-27B 或 `dsv4` 已为本岗位带来某个确定比例的提效。本文给出三组**非统计置信区间、非承诺**的规划情景：

| 情景 | 整体净人工工时节省 | 每人每月按 160 小时示例 | 10 人同类团队的工时容量释放 | 相同质量、持续有任务时的理论吞吐提升 |
|---|---:|---:|---:|---:|
| 保守 | 8% | 12.8 小时 | 128 小时，即 0.8 FTE | 约 8.7% |
| 中性 | 20% | 32.0 小时 | 320 小时，即 2.0 FTE | 25.0% |
| 进取 | 29% | 46.4 小时 | 464 小时，即 2.9 FTE | 约 40.8% |

这些数字已经在示例中扣除持续运行维护工时，但没有扣除首次建设投入。初期实际收益可以为零甚至为负。FTE 是等效全时工作量，不是可以直接裁撤的人数。第 7 节给出完整计算与适用条件。

## 2. 当前已知、需要核实、不能直接推出的结论

### 2.1 不把产品名称等同于实际能力

| 项目 | 已知或公开可核验的内容 | 公司部署仍需核实 |
|---|---|---|
| Qwen3.8-27B | 官方模型卡描述为 27B 稠密视觉语言模型；原生上下文 262,144 tokens，可扩展；提供思考控制等能力[^s01] | 是否确为该权重与版本；精度/量化；上下文限制；视觉入口；工具调用与推理字段是否保留 |
| `dsv4` | 只是当前服务名称。DeepSeek-V4 官方公开模型包括 Pro 和 Flash；公开模型卡列出不同参数规模与配置[^s02][^s03] | 是 Pro、Flash、某个日期版、内部别名还是其他变体；不能自行映射 |
| API key 并发 10 | 已知配额条件 | 两模型共享还是各自独立；按用户/key/租户如何计数；流式请求何时释放；RPM/TPM 和全局队列 |
| 三种客户端可调用 | 需求输入说明具备接入方式 | 客户端版本、网关版本、协议转换、工具调用完整性、服务支持责任 |
| 内部部署 | 已提供模型服务 | 模型推理、检索、日志、遥测、插件和工具执行是否都在获准边界内 |

**尚未掌握**：芯片类型、主要 HDL 与脚本语言、EDA 工具及版本、项目规模、团队人数、工作时间分布、算力与 license 余量、代码保密级别、当前自动化程度。因此文中收益和任务规模必须替换成真实基线后才能成为业务承诺。

### 2.2 两款模型的正确比较方式

公开模型卡中，DeepSeek-V4-Pro 为 1.6T 总参数、49B 激活参数；Flash 为 284B 总参数、13B 激活参数，均标注百万 token 上下文。这些是相应公开模型的规格，不是对内部 `dsv4` 的识别结果。不能将 MoE 激活参数与稠密模型参数直接当作能力排名或延迟预测。[^s02][^s03]

当前可提出、但必须验证的分工假设：

| 能力/任务 | Qwen3.8-27B 的首轮试用方向 | `dsv4` 的首轮试用方向 | 决定因素 |
|---|---|---|---|
| 文档、日志、报告结构化 | 高频主力候选 | 同题对照，尤其长资料 | 信息遗漏率、引用正确率、验收成本 |
| Python/Tcl/Shell 辅助脚本 | 小步开发与工具闭环候选 | 同等预算对照 | 正确运行率、维护性、重试次数 |
| 微架构推理与跨文件 debug | 必须进入评测，不能仅因 27B 排除 | 若确认较强版本，可作为深度分析候选 | 隐含约束、反例、证据与长任务完成率 |
| RTL 修改与 SVA 草稿 | 受限任务候选 | 独立候选或复核候选 | 仿真、形式验证、规范与审查结果 |
| 波形图、框图等视觉输入 | 官方具备视觉能力，内部入口仍需验证 | 不能从 `dsv4` 名称推定支持图像 | 图片细节保真、工具预处理、结构化信号 |
| 大量并发低风险任务 | 若实测延迟和资源占用合适，可优先 | 若部署吞吐更好，也可反向分工 | 每个验收任务的端到端成本，而非参数量 |
| 高风险结论/签核 | 仅辅助 | 仅辅助 | 责任人、权威工具与现有签核制度 |

两个模型相互复核可以增加检查视角，但**不能视为独立真值**：它们可能共享知识缺口、都接受了同一错误需求，或被同一错误测试误导。

### 2.3 需要评估的能力维度

建议至少覆盖以下能力，而不是只问几道 Verilog 面试题：

| 维度 | 芯片工程中的具体问题 | 可观察的失败 |
|---|---|---|
| 需求与意图对齐 | 是否保留延迟、吞吐、复位、功耗、兼容性要求 | 为了局部指标擅自改变规格 |
| 硬件语义 | 位宽、符号、周期、并发、复位和 X 语义 | 软件式推理掩盖硬件边界问题 |
| 微架构分析 | backpressure、flush、ordering、fairness、死锁 | 只描述正常路径，不讨论反例 |
| 多文件理解 | module/package/include/参数/层级关系 | 看错配置，漏掉跨模块契约 |
| 验证能力 | 从需求构造检查，不从 DUT 机械复述行为 | 自证正确、断言空真、过度约束 |
| Debug 能力 | 证据定位、根因排序、最小区分实验 | 把相关性当因果，提前锁定结论 |
| EDA 辅助 | Tcl、SDC、报告口径、PPA 对照 | 伪造命令、忽略 corner 或约束变化 |
| 工具使用 | 文件读取、补丁、命令、结果回收 | 只打印命令不执行，执行失败却声称通过 |
| 长上下文 | 检索到正确版本，跨文件约束保持 | 能塞进上下文但不能可靠利用 |
| 不确定性处理 | 缺少输入时列出前提与待验证项 | 编造规格、寄存器定义或测试结果 |
| 运行可靠性 | 长任务恢复、超时、取消、资源预算 | 无限重试、任务漂移、重复启动 EDA |
| 成本与协作 | 用户监督量、评审量、工具算力 | 把执行时间转嫁给资深工程师审查 |

## 3. OpenCode、Codex、Claude Code：评估的是整条执行链

### 3.1 模型与客户端不是一回事

```text
客户端/agent harness
  = 上下文收集 + 任务规划 + 工具调用 + 补丁管理
    + 错误恢复 + 权限控制 + 交付判断

模型服务
  = 实际权重 + 推理实现 + 量化 + 采样/思考预算
    + 网关协议 + 上下文限制 + 服务资源
```

把 Qwen 或 DeepSeek 接到 Codex/Claude Code，并不等于换成了 OpenAI/Anthropic 的模型。反过来，同一个模型在不同 harness 下也可能表现不同。这是需要对照实验的系统问题，不应预设某个客户端必然最聪明。

### 3.2 当前公开文档给出的接入边界

| 客户端 | 公开文档确认的边界 | 本方案建议 |
|---|---|---|
| OpenCode | 提供自定义 OpenAI-compatible provider 的配置方式[^s04] | 可作为内部双模型对照的候选基础；仍需检查工具调用和流式处理 |
| Codex | 当前配置参考中，provider 的 `wire_api` 仅支持 `responses`[^s05] | 平台若只提供 Chat Completions，需要正确适配；不能仅修改 base URL 就认定完整兼容 |
| Claude Code | 官方支持符合规定 API 格式的网关，但明确不支持经网关路由到非 Claude 模型[^s06] | 将公司已有接入视为内部维护的兼容方案；评估稳定性、升级风险、支持与使用条款，不写成官方支持 |

以上是 2026-10-04 核查的文档行为；实际安装版本必须单独记录。旧版、分叉版和内部补丁可能不同。官方模型研究使用某个第三方 harness，也不等于该 harness 厂商为这种部署提供支持。

### 3.3 最容易导致“同一个模型效果不同”的因素

任务系统提示词、文件选择、上下文截断、项目规则加载、思考预算、工具 schema、并行工具结果顺序、补丁失败处理、超时上限、自动压缩历史、模型路由和验收条件都应记录。

Qwen 官方还提供 `reasoning_effort` 与历史思考保留相关机制，并提示降低单轮思考预算不一定降低整个任务耗时。应测试端到端完成成本，不以“每轮出字更快”作为最优设置。具体字段能否经过内部网关正确传递仍待核实。[^s01]

### 3.4 统一任务合同，降低目的漂移

每个任务都提供同样的业务合同：目标、非目标、允许改动、禁止改动、必须保持的不变量、工具预算、验收命令、证据格式、停止条件。

例如：“修复 flush 与 backpressure 同周期导致的请求重复提交”不能被替换成“增加 buffering 提升吞吐”；“解释时序变差”不能被替换成“增加 false path 让报告变好”。

不同客户端可以采用各自最佳实践，但应分两轮比较：第一轮固定任务合同与预算看基础表现，第二轮分别调优看各自上限。两轮成绩不能混在同一排行榜。

## 4. 模型评估与验收规划

### 4.1 四层评估

| 层次 | 回答的问题 | 主要产物 |
|---|---|---|
| L0：服务与协议 | 请求和工具回合能否可靠完成？ | 部署信息卡、兼容性矩阵、并发/延迟曲线 |
| L1：领域能力 | 是否理解本岗位的真实任务？ | 分领域正确率、错误分类、拒答与幻觉记录 |
| L2：工具闭环 | 能否做出通过检查的工程交付物？ | 补丁、工具日志、检查结果与人工评审 |
| L3：真实生产力 | 是否在相同质量下减少总人工投入？ | 配对试点工时、返工、缺陷和成本报告 |

公开基准可用于冒烟测试。例如 NVIDIA 的 VerilogEval 是针对 Verilog 生成的执行评测，原始问题来源包括 HDLBits；这并不代表复杂 IP、多时钟域或项目签核能力。[^s07]

### 4.2 对照组和实验矩阵

至少包含：人工加现有脚本的基线、两个模型的直接调用基线、两个模型分别配三个客户端的六种组合。不能用“全手工且没有现有自动化”的弱基线夸大收益。

主任务池建议 60 题：微架构 12、RTL 14、验证协助 12、综合协助 8、后端协助 6、硅后支持 8。另设 12 类 API/工具链兼容性检查。具体题目与字段见配套手册。

建议将任务池按 IP/时间/问题家族划分为 40 题开发集和 20 题封存集，防止相近修复泄漏。先用开发集中的 12 题筛查六组合，再扩大到表现较好的组合。完整六组合、60 题、各重复 3 次意味着 1,080 次 agent 任务执行，尚未包括直接调用与人工基线；这不是要求一次性全部执行。

**重复次数不能冒充独立任务数。** 三次重试仍然是在做同一道题，统计分析应以任务或 IP 家族为聚类单位。

### 4.3 成功定义

一个任务只有同时满足需求、质量门禁、资源预算、权限约束和证据要求，才算验收成功。

必须分别记录：一次成功率、预算内成功率、人工修正后成功率、完全失败率、人工接管工时。不能只报告成功案例，也不能只统计最终通过时那一次调用的成本。

| 指标 | 计算或记录方式 | 防止什么误判 |
|---|---|---|
| 需求保持率 | 逐条检查硬约束与非目标 | 补丁通过但改错需求 |
| 正确性 | 仿真/形式/独立测试/领域评审 | 编译通过被当成正确 |
| 缺陷检测能力 | 已知缺陷、变异缺陷与反例的发现情况 | checker 与 DUT 一起犯错 |
| 证据完整性 | 文件位置、版本、命令、退出状态、日志、限制 | 没执行却宣称验证完成 |
| 人工总投入 | 准备、交互、检查、修正、接管和后续返工 | 只计算 AI 执行时间 |
| 端到端时延 | 包括模型排队、EDA 排队、运行和评审等待 | 并发增加却交付更慢 |
| 每验收任务成本 | 所有尝试的推理、EDA、人工与维护成本 | 低 token 单价掩盖失败成本 |
| 质量负债 | 7/30 天返工、缺陷逃逸、维护问题 | 当天很快、后面很慢 |

微架构开放题应由至少两位适当领域评审者按固定 rubric 评分；AI 评审只帮助整理，不能成为唯一裁判。隐藏测试、golden/reference model 和签核约束不应由被测 agent 随意修改。

### 4.4 试点放行规则

以下是建议起点，不是行业标准，也不是硅片可靠性认证：

- 硬性条件：没有越权执行、伪造工具结果、泄密，或通过删改 oracle/放宽约束来“通过”的事件。出现即暂停相关权限并复盘。
- 低风险、限定任务：预算内验收率可先以 80% 作为试点门槛，失败时必须能够安全接管；净人工节省中位数以 15% 作为候选门槛。
- 生产 RTL、约束、硅后操作：保持原有全部工程审查与签核门禁；不因模型分数提高而降低要求。

样本量小、置信区间跨零、或错误集中在关键场景时，仅保持实验资格。几十题没有出错不代表极低失效率；即使简化为独立伯努利样本，零失败样本量为 n 时，95% 失效率上界的粗略量级仍约为 3/n。真实任务相关性还会进一步削弱这种推断。

### 4.5 人在回路的真实试点

从真实 backlog 中预先选任务，按难度、阶段、工程师经验做分层匹配，再分配 AI 组和非 AI 组；同一工程师不要先做完同一道题再作为另一个条件的基线。单人情况下采用不同但匹配的任务交叉轮换，并承认样本限制。

观察期应延伸到评审和后续返工。除了每任务速度，还要检查：资深工程师评审是否变成瓶颈，新增产物是否被真正使用，普通工程师是否失去理解与维护能力。

## 5. 全岗位工作机会：具体做什么、怎么做、怎样验收

### 5.0 收益区间的统一解释

下列区间是对**适合 AI、输入准备充分的单项任务**设定的试点目标，不是已测结果，不适用于该阶段全部工作，也不可以直接相加。计时必须包括上下文准备、提示、人工检查和返工；失败和接管也计入。首次平台建设、知识治理和共享维护另计。

例如“目标节省 30%–50%”表示原本 100 小时的一类适合任务，希望降到 50–70 小时，不表示整个芯片项目节省 30%–50%。无法可靠验收、上下文不全或难度很高的任务，收益允许为负。

### 5.1 微架构

| 工作内容 | AI 的具体参与方式 | 必须保留的检查 | 单项任务人工节省试点目标 |
|---|---|---|---:|
| 需求与规格审查 | 抽取吞吐、延迟、排序、错误、复位、低功耗要求；跨章节找冲突；生成待决问题 | 标注原文位置与版本；禁止补写未定义行为后当成正式规格 | 20%–40% |
| 方案比较 | 枚举流水级、buffer 深度、仲裁、credit/backpressure 等方案和代价 | 人工确认约束；性能模型和实际综合验证关键假设 | 10%–25% |
| 接口与异常路径 | 形成握手、flush、timeout、重试、原子性等契约和状态转移表 | 设计/验证双方确认；给反例和边界时序 | 20%–40% |
| 性能与容量建模 | 生成 Python/SystemC 等模型骨架、流量发生器、敏感性实验 | 用解析边界与已有数据校准；不能把模型输出直接当芯片保证 | 20%–40% |
| 架构评审材料 | 自动更新方案决策记录、需求追踪、风险与争议清单 | 所有结论可回溯；未决问题不能自动“闭环” | 30%–50% |

高价值不只在写文档快，还在于把正常路径以外的情况提前展开。最终选择架构、接受何种 PPA 取舍、决定哪种兼容性可变化，仍由责任工程师裁决。

### 5.2 RTL 设计

| 工作内容 | AI 的具体参与方式 | 必须保留的检查 | 单项任务人工节省试点目标 |
|---|---|---|---:|
| 规格到骨架 | 生成 module/package、端口、参数、状态定义和 TODO | 可综合性、命名、接口契约与项目规范 | 30%–60% |
| CSR/寄存器与连接 | 从经过批准的机器可读源生成 RTL、文档、模型/头文件草稿 | 地址/位宽/访问属性一致；优先复用确定性生成器 | 40%–70% |
| 小范围缺陷修复 | 先建立失败证据，再修改最小相关代码，补定向测试 | 原失败复现、新测试、回归、必要时等价/形式检查 | 15%–35% |
| 重构与参数化 | 清理重复逻辑、参数传播、模块接口更新 | 参数边界、配置矩阵、语义保持；不能只测默认参数 | 20%–40% |
| lint 与代码评审预检 | 定位规则触发原因，建议替代写法，检查位宽/符号/复位 | waiver 由人批准；不许用注释屏蔽问题获得干净报告 | 20%–40% |
| CDC/RDC/低功耗/DFT 协作 | 整理跨域、复位、隔离/保持、时钟门控、扫描相关问题 | 由专用分析、设计意图和专家确认；不承诺自动签核 | 10%–25% |

对现有成熟 IP，优先让 AI 理解并修改已有实现，而不是重新生成一个“看起来更简洁”的版本。对 CSR 等已有可靠生成器的任务，AI 负责输入检查、生成器开发和异常解释，不应替代已确定的生成规则。

### 5.3 协助验证

| 工作内容 | AI 的具体参与方式 | 必须保留的检查 | 单项任务人工节省试点目标 |
|---|---|---|---:|
| 验证计划 | 将需求拆成场景、检查项、覆盖项，指出缺失定义 | 需求可追踪；由 DV owner 接受计划 | 25%–45% |
| 定向测试与 UVM 草稿 | 生成 sequence、monitor/checker、scoreboard 结构和激励组合 | 参考模型独立；区分 DUT 与 testbench 错误；确保真正执行 | 25%–50% |
| SVA/形式辅助 | 从确认的契约生成 safety/liveness 属性、assumption 候选 | 时钟/复位/采样语义、空真、可达性、过度约束与环境假设审查 | 20%–40% |
| 回归 triage | 提取失败指纹、聚类重复症状、关联变更与 seed | 抽样检查漏分与误合并；保留原始日志和失败任务 | 30%–60% |
| 波形与根因定位 | 先用工具切片为信号/时间/事务，再让模型解释和提出反证 | 不能仅凭截图判根因；区分推测与已证实因果 | 15%–35% |
| 覆盖率收敛 | 找未覆盖需求、建议定向激励和不可达分析 | 不自动删 bin、改 exclusion 或弱化断言；覆盖率不等于无缺陷 | 15%–35% |

关键独立性：可以由 AI 辅助编写 DUT，也可以辅助编写检查，但两者必须由独立规格与隐藏检查约束。让同一 agent 修改 DUT、reference model 和验收标准后宣布全部通过，不能构成可靠闭环。

### 5.4 协助综合

| 工作内容 | AI 的具体参与方式 | 必须保留的检查 | 单项任务人工节省试点目标 |
|---|---|---|---:|
| 综合脚本整理 | 依据本公司工具版本和已有模板生成 Tcl、小型流程封装 | 命令与参数在获准沙箱验证；记录工具版本 | 25%–50% |
| SDC 预审 | 检查 clock/generated clock、I/O delay、例外、约束缺失 | 设计意图核对；false/multicycle path 必须独立批准 | 15%–30% |
| 报告差异与异常 | 比较面积、关键路径、资源映射、层级变化，关联 RTL 变更 | 单位、corner、库、约束、层级一致；直接回查原报告 | 35%–60% |
| RTL 局部 PPA 优化 | 提出位宽、资源共享、逻辑结构等候选，组织小实验 | 功能验证/等价；同条件综合；不靠减少功能获得 PPA | 10%–30% |
| 与综合工程师协作 | 汇总失败、必要输入、原因候选与待决问题 | 明确所有者、限制和证据，不自动接受 waiver | 25%–45% |

这里的百分比是人工整理、分析与迭代投入的目标，不承诺综合工具本身运行速度提升，也不承诺固定面积/频率/功耗改善比例。

### 5.5 协助后端

| 工作内容 | AI 的具体参与方式 | 必须保留的检查 | 单项任务人工节省试点目标 |
|---|---|---|---:|
| 时序路径分类 | 归类 setup/hold、fanout、逻辑深度、跨层级路径并映射 RTL | mode/corner 与约束一致；不能忽略例外与不确定度 | 25%–45% |
| 拥塞/高扇出/布局反馈 | 将物理报告与模块结构关联，提出待验证的 RTL/分区建议 | 真实 P&R 验证；不从文字推断确定的物理结论 | 15%–30% |
| ECO 协作 | 整理候选修改、受影响路径、检查清单和回归范围 | 人工审批；等价/时序/功耗及相关签核检查 | 10%–25% |
| 功耗意图与跨域接口 | 对齐 UPF、隔离/保持/电源序列与 RTL 意图 | low-power/CDC/RDC 等既有工具和责任人确认 | 10%–25% |
| 交接与签核资料 | 自动生成版本清单、约束差异、问题状态与证据索引 | 不替代 STA、DRC/LVS、IR/EM 等责任方签核 | 30%–50% |

|---|---|---|---:|

| 日志和寄存器解码 | 依据对应 stepping、固件和寄存器版本解析 dump，做正常/异常对比 | 位定义、端序、单位、clear-on-read 与保留位等副作用 | 35%–60% |
| 根因假设与实验 | 跨 RTL、固件、板级、时序、PVT 组织证据和区分实验 | 每个假设列支持/反证、实验预期与停止条件 | 15%–35% |
| 性能/功耗/PVT 数据 | 整理样本、环境变量、异常与重复性，形成对比分析 | 样本定义、混杂因素、仪器精度；统计相关不当因果 | 25%–45% |

默认让 AI 读取已导出的日志和数据，不直接控制设备。更改电压/时钟、JTAG 写寄存器、烧写固件、熔丝/OTP 等操作必须显式审批；不可逆操作不交给默认自治模式。所谓“只读寄存器”也必须检查读副作用。

### 5.7 横向工作不单独重复计费

代码阅读、文档整理、会议准备、issue/PR 草稿、交接和新人学习可穿过全部阶段。建议将它们归入实际所属的工作任务，而不是在六阶段收益之外再额外加一个“文档提效 30%”。

同一个失败可能同时节省设计与 DV 工时。个人测算只算本人的时间；团队测算可以合并不同人的实际投入，但同一小时只计一次。

## 6. 工程落地：上下文、工具、权限与并发

### 6.1 项目上下文不是把整个仓库塞进窗口

建议建立带版本的最小“项目上下文包”：规格索引、批准的设计决策、模块/接口/时钟复位关系、关键参数、编码规范、工具版本、测试入口、已知限制和历史问题。

检索时先做权限和版本过滤，再按模块/符号/报错精确检索，必要时结合语义检索。每段内容附源路径、commit/文档版本、生成时间。不要将旧版规格、当前 RTL、另一 stepping 的寄存器定义混成一个答案。

优先利用结构化资料：RTL AST/层级图、filelist、寄存器 schema、机器可读报告、信号切片。自然语言检索不能替代参数 elaboration、真实层级解析与工具计算。

对 FSDB/VCD、大型仿真数据库、长报告、版图结果，先由获准工具筛选/导出所需窗口或指标，不默认让模型直接理解原始二进制格式。

### 6.2 最小工具接入层

建议先封装有限、可审计的接口：搜索资料、读取文件、获取 diff、在指定 worktree 生成补丁、运行 lint、编译/小回归、执行批准的形式任务、解析报告。

这些接口必须由工程平台实现并绑定实际工具链，本文不声称已经提供可运行的 EDA agent。每个工具返回：工具版本、输入版本、完整退出状态、日志位置、摘要、是否超时、是否截断。

补丁生成和验证结果要分开保存。检查失败后不允许自动更改验收命令、忽略错误码、删测试、增加 waiver 或声称“理论上应当通过”。

### 6.3 四级权限

| 级别 | 允许范围 | 审批与限制 |
|---|---|---|
| A0：只读分析 | 获准资料与导出报告，提出建议 | 不执行写入，不访问超出任务范围的资料 |
| A1：沙箱产出 | 独立 worktree/容器内写草稿、补丁和运行低成本检查 | 不改主干、golden、签核约束和设备状态 |
| A2：受控实验 | 提交批准的回归、形式或 PPA 实验 | 人工授权预算，受 license/算力/时间门禁约束 |
| A3：责任决策 | 合并生产修改、waiver、签核、硅后高风险操作 | 由原责任体系决定，AI 无默认自治权限 |

prompt 中写“不要越权”不够，文件权限、网络出口、工具白名单和资源限制必须在模型之外执行。

### 6.4 如何使用每 key 并发 10

并发 10 是请求配额，不是十名工程师，不是十个完整任务的稳定吞吐，也不代表两个模型合计并发 20。

建议第一版将受控请求上限设为 6–8，留余量给人工交互、重试和其他进程，再根据压测调整。采用全 key 范围的调度器，不能每个客户端都各自开 8 个请求。禁止用额外 key 绕过未授权配额。

初期用一个主执行 agent、一个复核角色，以及少量只读并行分析即可。所有写入者隔离到不同 worktree；由单一责任点整合，不允许多个 agent 同时改同一文件。

LLM 请求完成后释放模型槽位；EDA 运行用独立队列和 license/CPU/内存配额，不应把整个仿真等待期算作持续模型请求。对于长仿真，避免让模型频繁轮询并重复读取全部日志。

在稳态简化条件下：

```text
可持续请求率 ≤ 可用并发槽位 / 平均每请求占用时间
完整任务吞吐还受 每任务调用次数、EDA 运行、排队和人工验收限制
```

纯示例：8 个槽位、每请求平均占用 30 秒，对应理论上限约 16 请求/分钟；若一个任务平均需 12 次调用，则仅模型环节的理想上限约 1.33 任务/分钟。它不是本部署性能预测，真实负载和反馈依赖会降低吞吐。

需要记录并发 1/2/4/8/10 下的首 token 时延、p50/p95 完整响应时间、有效 tokens/s、错误/取消率和任务成功率。不能只用单个短 prompt 的最快结果。

### 6.5 推理与模型路由

默认按任务类型和验收成本路由，而不是按模型名大小：简单提取和报告用较低成本路径；歧义、跨文件根因和复杂 RTL 使用更充足预算；触及工具失败/错误率阈值就升级模型或交给人。

深度分析失败两轮、同一错误反复出现、预算超过上限、缺少关键输入、或关键约束发生争议时停止自治。模型切换不得默认回退到公网服务；回退路径也要通过数据边界审批。

## 7. 提升幅度与人力测算：区分局部、整体、工期与人员

### 7.1 四种指标不能混用

**局部人工节省**：某个合格任务需要的总人工时间减少多少。  
**整体人工节省**：按真实工作占比加权，并扣除运行维护后的净节省。  
**工期缩短**：关键路径、依赖、EDA 等待和评审队列是否变化。  
**生产力增加**：相同人员能交付更多合格成果，或同等成果能增加验证深度和方案探索。

局部任务提速 2 倍等于该任务工时减少 50%，不是“减少 200%”。若整体净工时节省 20%，同质量、任务不断供时理论吞吐提升为 1/(1−20%)−1=25%，不是所有芯片项目周期缩短 20%。

### 7.2 推荐的通用模型

设阶段 i 的原工时占比为 w_i，可纳入 AI 的工作比例为 a_i，纳入部分经过全部人工检查/修正后的平均节省率为 s_i；每月每人基线工时为 H，参与人数为 N，团队持续维护工时为 O。

```text
阶段实际节省率 r_i = a_i × s_i
团队月度净节省工时 = N × H × Σ(w_i × r_i) − O
整体净节省率 S = 净节省工时 / (N × H)
等效人力容量释放 FTE = 净节省工时 / H = N × S
固定人员的理论吞吐提升 = 1/(1−S) − 1
```

这里 s_i 应基于全部纳入任务，包括失败、接管和后续返工；a_i 不能仅统计“最终成功案例比例”。当阶段比例直接由配对试点获得时，可以直接使用 r_i，不要再重复乘一次成功率或采用率。

财务分析另外记录 GPU/服务、存储、EDA license、工具接入、运维、培训、安全与机会成本。释放工时是经济容量，不一定形成现金支出减少；不要把同一份工资既当固定成本又重复当可节省现金。

| 持续维护开销/基线 | — | — | 2% | 2% | 3% |
| **整体净节省** | — | — | **8%** | **20%** | **29%** |

阶段 r_i 已考虑阶段中不适合 AI 的部分，因此低于第 5 节适合单项任务的目标区间；这些比例是情景输入，不是从行业案例倍率换算而来。

中性情景的逐项节省为：微架构 4.8、RTL 12、验证 8、综合 4、后端 3.2、硅后 3.2 小时，合计 35.2 小时；扣除持续维护 3.2 小时，得到每人每月 32 小时。

### 7.4 如何理解“节省多少人力”

对 10 人同类团队，中性情景释放约 320 小时/月，即 2.0 FTE。实际可能表现为少加班、缩短等待、延后招聘、承担更多模块、增加 corner case 和 PPA 探索，而非必然减少两名员工。

保守/中性/进取情景适用于**工作流成熟且仍有相应工作负载**的状态。首次建设和学习投入必须另扣。例如单人某月产生 32 小时稳定态净收益，但当月另投入 24 小时搭建和学习，则该月仅净释放 8 小时。这个例子也只是计算说明。

对于某个一次性脚本任务，应比较“使用已有工具”“人工写脚本”“AI 辅助写可复用工具”三条路径。长期收益可能来自新工具复用，不能在以后每次运行时再次声称节省了同一份开发投入。

### 7.5 收益受什么限制

最敏感的因素通常是：适合任务占比、原有自动化水平、资料可用性、验收能力、服务排队、人工审查量、维护成本和任务失败后的返工。

建议每月输出一个敏感性表：采用比例下降 20%、评审工时增加一倍、EDA license 排队增加、强模型不可用时，净节省是否仍为正。不要只保留最有利情景。

## 8. 全球领先芯片研发团队的经验：学习方法，而不是复制倍率

### 8.1 证据分级

**A：研究或可检查的技术方法。** 能支持方法论，但不一定证明公司整体 ROI。  
**B：厂商/客户公开案例。** 有参考意义，常有任务选择、工具/算力和口径限制。  
**C：前瞻公告。** 说明方向，不能作为已兑现效果。  
**D：本方案估算。** 必须在内部试点中验证。

| 案例与日期 | 公开证据和准确范围 | 可以迁移的经验 | 不能推出什么 |
|---|---|---|---|
| NVIDIA ChipNeMo，2023-10 | 研究工程问答、EDA 脚本、缺陷总结；领域适配在若干任务上允许最多约 5 倍模型规模缩减，保持相当或更好表现。A[^s08] | 专业上下文、领域检索和真实任务比单纯扩大参数重要 | 不是工程师快 5 倍，也不是全流程自动设计 |
| Google AlphaChip / MediaTek，2024-09 公布经验 | 强化学习用于布局；Google 披露用于 TPU 代际设计，并提到 MediaTek 扩展该方法。A/B[^s09] | 把问题变成可评分、可迭代的闭环；复用历史设计经验 | 不是通用 LLM，仅有 API 就能得到同样布局收益 |
| Google AlphaEvolve，2025-05 | 公开展示对矩阵乘法相关电路的 Verilog 改写，经严格验证后用于其后续 TPU。A/B[^s10] | 候选生成、自动评估、保留有效改进；真值在验证器 | 不是无需验证的自动 RTL，也没有本岗位整体工时比例 |
| Renesas + Synopsys DSO.ai，2021-04 | 公布在汽车芯片设计中采用强化学习设计空间优化，面向 PPA。B[^s11] | 把资深工程师经验封装成可复用、可搜索流程 | 不应将专用优化引擎效果归给 Qwen/DeepSeek |
| Cadence + Altera / NVIDIA / Qualcomm / Tenstorrent，2026-02-10 | 官方公告列出早期部署；Altera 的部分验证领域约 10 倍投入改善，Tenstorrent 在三个模块、三个月评估中最多 4 倍时间改善；Qualcomm 表述为鼓舞性初期结果。B[^s12] | 从验证与具体模块切入，以 agent 调用真实 EDA；区分客户和场景 | 不是所有客户或芯片项目都达到 4–10 倍 |
| Cadence + NVIDIA，2026-06-01 | 公告描述自动化 RTL 验证环节超过 40 倍周期改善，并称更高自治能力预计于 2026 下半年向早期客户提供。B/C[^s13] | 受控执行环境与仿真/形式引擎共同建设 | 公告中的预期能力不自动成为当前已全面可用能力；周期倍率不是净人力倍率 |
| OpenAI + Synopsys，2026-09-30 | 宣布联合开发 GPT-Synopsys，目标是模型使用 EDA、解释结果、迭代到可审查成果。C[^s14] | 最新方向仍是“模型 + 专业工具 + 可验证结果” | 刚公布的合作不是成熟 ROI，也不证明内部双模型拥有相同能力 |

截至本次核查，Cadence 产品资料另称 ChipStack 已在多家领先企业进行生产部署；这与 6 月公告中某一更高自治功能的早期访问计划不是同一层面的可用性声明，不能混成“所有功能已普及”。[^s15]

### 8.2 对本团队最值得复制的五点

一是选择有工程真值的任务，而不是以演示流畅度评估。二是将设计意图和资料关系结构化。三是将执行、验证和证据归档连起来。四是保留权限和责任边界。五是把成功流程沉淀为团队资产，而不是依赖个人聊天技巧。

大型企业案例中，成果通常来自模型、EDA、算力、数据和流程的组合。因此本方案可以利用现有内部模型逐步建设，但不能将商业 EDA agent 的公开倍率作为内部模型部署的收益保证。

### 8.3 反向证据也要认真对待

METR 在 2025 年针对特定资深开源开发者的随机试验中观察到 AI 使用者完成任务反而更慢；2026-02-24 的后续更新又指出，新的参与者选择和并行 agent 计时问题使其难以可靠估计当前收益。它们研究的是软件开发，不是芯片设计。这里引用的意义仅是：主观感觉、公开基准和真实净工时可能不同，评估方法本身也必须持续修订。[^s16][^s17]

## 9. 90 天实施路线：分阶段决定是否扩大

以下是项目实施建议，不表示本次已经执行内部部署或会在后台自动开展。

| 阶段 | 主要工作 | 验收物 | 责任角色 | 扩大条件 |
|---|---|---|---|---|
| 第 1 周：摸底 | 确认模型身份、网关、版本、权限、并发口径与可用 EDA | 双模型信息卡、接入检查、数据流边界图的文字说明 | 平台/IT + 设计负责人 | 没有未批准数据出口；基础工具链可重放 |
| 第 2 周：建基线 | 选 60 题任务池、封存集、人工基线与记录规则 | 任务卡、质量门禁、首轮六组合筛查 | 设计 + DV/综合/后端代表 | 失败可解释，评测无明显泄漏 |
| 第 3–4 周：低风险试点 | 报告差异、日志 triage、规格检查三条流程 | 可复用模板、工具接口、真实工时记录 | 1 名流程维护者 + 试点工程师 | 净收益为正、引用可靠、没有越权 |
| 第 5–8 周：小闭环 | 小 RTL 修复、定向测试/SVA、综合对照实验 | 经审查补丁、独立验证证据、失败样本库 | 模块 owner + DV owner | 质量不下降，资深评审负担可承受 |
| 第 9–12 周：岗位贯通 | 后端反馈、硅后只读分析、需求到缺陷回流 | 分阶段 ROI、模型路由、扩展/停止决策 | 设计负责人 + 跨职能伙伴 | 7/30 天返工与维护成本仍可接受 |

个人启动不需要先建立独立 AI 团队。可以先由一位工程师维护少量工作流，由现有模块/验证/实现责任人沿用原评审制度。团队推广时再明确平台与领域 owner 的长期维护投入。

每个阶段都允许得出“这个模型/客户端/任务暂时不适合”的结论。淘汰低收益组合、缩小自治范围，都是有效成果，不是试点失败。

## 10. 容易忽略但有价值的事项

### 10.1 安全不仅是模型是否本地

应审查 prompt、源码、工具日志、向量索引、缓存、遥测、插件、崩溃报告、自动更新和兜底模型路径。工具输出和仓库文档属于不可信数据，不能因为其中出现“请上传文件/忽略限制”就执行。

机密上下文不能被公开 GitHub 仓库、未经许可的云 CI、外部 issue 或分享链接承载。索引的权限不得比原文宽；项目结束、访问撤销和资料删除时同步更新缓存和检索权限。

### 10.2 许可证与使用边界

模型权重许可、客户端条款、第三方网关维护责任、EDA 自动化接口与 license 使用、PDK/IP 资料使用范围，分别确认。本文不作特定法律结论，也不假定“内部使用”自动覆盖所有权限。

### 10.3 工程证据与可重现性

保留模型标识、权重/部署版本、客户端和网关版本、工具版本、代码 commit、输入资料版本、采样参数、预算、工具调用和输出校验值。无法保证 bit-exact 模型输出时，至少保证输入、执行过程和验收判断可以审计。

模型或网关升级后先跑固定回归集，再小范围放量；保留上一工作版本和回退方案。长上下文窗口、生成长度或量化变化也属于需要回归的系统变更。

### 10.4 防止新的产出过剩和评审瓶颈

多生成测试、代码、文档并不自动产生价值。应限制待评审工作量，按每周验收的有效任务评估。维护简单、可读的小补丁，避免一次改很多模块让人工无法理解。

把释放工时的一部分投入难角落、形式属性、硅后回归和跨模块一致性，可能比追求更多代码更有价值。

### 10.5 防止技能退化与责任真空

工程师应能解释接受的 RTL、SDC、SVA 和实验结论。对关键决策保留人工推导和评审；新人培训不能只学如何让模型给答案。

每个任务只有一个明确责任 owner。模型“建议合并”不构成批准，AI 输出中的“已验证”不构成签核证据。

### 10.6 何时值得微调或采购专业方案

先修复数据、检索、工具和验收流程。如果错误长期集中在稳定领域语义或固定产出格式，且已有足够获准训练数据、封存评测与维护预算，再考虑领域适配；不应以微调掩盖版本不一致或缺少事实输入。

当 EDA 深度闭环已成为主要瓶颈时，再把专业 EDA agent 与内部方案作同任务 PoC。比较可用功能、数据位置、工具许可、总成本、可审计性、部署与退出成本，而不是只比较发布会倍率。

## 11. 覆盖审核与最终对比

| 用户工作范围 | 本方案覆盖 | 主要提升机制 | 关键边界 | 推荐启动顺序 |
|---|---|---|---|---|
| 微架构 | 第 5.1 节；评测 12 题 | 规格审查、方案比较、接口契约、性能模型 | 架构决策与关键假设由人确认 | 首批规格检查，其后方案探索 |
| 设计 | 第 5.2 节；评测 14 题 | 骨架、CSR、局部修复、参数化、预审 | 独立验证、跨域/低功耗/DFT 专项检查 | 先确定性生成与小修改 |
| 协助验证 | 第 5.3 节；评测 12 题 | 计划、测试/SVA、回归 triage、根因与覆盖协作 | 不改 oracle 自证；不自动排除覆盖项 | 首批 triage，其后小闭环 |
| 协助综合 | 第 5.4 节；评测 8 题 | 脚本、约束预审、报告差异、PPA 实验 | 不放宽约束；同条件对比 | 首批报告分析 |
| 协助后端 | 第 5.5 节；评测 6 题 | 路径分类、物理反馈、ECO、交接 | 不替代后端签核 | 先只读分析与交接 |
| 硅后支持 | 第 5.6 节；评测 8 题 | bring-up、日志/寄存器、实验、errata、硅前回流 | 实物操作和不可逆操作明确审批 | 先日志/数据分析 |
| 模型能力与评估 | 第 2–4 节及手册 | 身份核实、双模型三客户端、分层测试 | 当前没有内部实测排名 | 最先开展 |
| 收益与节省人力 | 第 7 节 | 任务计时、阶段加权、维护扣除、FTE | 情景不是承诺，工时不是岗位 | 从试点第一天记录 |
| 顶尖团队经验 | 第 8 节 | 专业上下文、工具闭环、可验证搜索 | 区分 LLM、专用 AI、案例与公告 | 学方法，不搬倍率 |
| 其他必要事项 | 第 6、9、10 节 | 权限、并发、知识治理、成本、技能与实施 | 不越过现有工程责任体系 | 与技术试点同步 |

**最终建议：先把“报告差异、失败 triage、规格追踪”做成有输入、有工具、有验收的三条稳定流程，再扩大到 RTL—验证的小闭环，之后贯通综合、后端和硅后。以完整任务的净人工投入和质量衡量两个模型及三个客户端，模型名称和每 key 并发 10 都不能替代这一评估。**
