# 多 IP、多轮综合/时序报告：结构化与差异分析实施及操作手册

> v1.0｜2026-10-05｜面向同一工艺下多个 IP 的持续综合与时序分析。  
> 状态：**可用于分工和执行的实施设计，不是已经接通公司 EDA/API 的软件产品，也不是内部实测报告。**  
> 未提供工具厂商/版本、实际报告、IP 数量和现有脚本；本文采用工具无关的数据契约，将具体 EDA 导出和解析作为必须完成的适配工作，不编造可直接运行的商业工具命令。  
> [全岗位选题与优先级见 04](04-全岗位首批试点选择与优先级修订.md)。为本专题制定详细方案，不意味着它是全岗位默认第一优先级。  
> [表单、样例、提示词和验收用例见 06](06-综合时序报告模板与验收用例.md)。公开仓库仅存方法和空白模板；真实报告、网表、库、约束、IP 名称及内部结果存获准内部系统。

## 1. 目标、边界与验收对象

### 1.1 每轮最终要回答的八个问题

1. 哪些 IP/配置/场景完成了本轮，哪些失败、缺失、仍在运行或数据不可信？
2. 本轮与哪个基线比较，比较条件是否一致，不一致在哪里？
3. 面积、单元构成、setup/hold、违例端点、约束覆盖与资源消耗有什么变化？
4. 哪些变化是真正的同条件变化，哪些只是更换库、SDC、频率、阶段或报告口径？
5. 哪些问题是新增、持续、恶化、改善，哪些只是没有出现在本轮 Top-N 中？
6. 变化可能与哪些 RTL/配置/约束改动有关，证据和反证是什么？
7. 谁负责下一步，应该补哪份报告或做哪个最小对照实验？
8. 本轮实际节省多少人工，是否把工作转移给了综合/时序专家？

核心交付物不是一篇 AI 总结，而是 **运行台账、质量检查结果、可比性判定、确定性差异表、带证据的解释、待办和评审结论**。

### 1.2 首版范围

先收集已有完成轮次，不默认启动新的综合。建议用 2 个有差异的 IP、各 3 轮历史记录做适配：一个规则简单、一个多时钟或含宏；选择实际必需的分析场景，额外加入失败/缺失样本。另留一个不同 IP 或未参与调试的后续轮次作盲测。

这只是控制首次投入的样本设计，不代表用户只有两个 IP，也不是强制所有项目只有一种 mode/corner。若某 IP 的有效性需要多个场景，不能为了试点容易而遗漏必需场景并宣称该 IP 通过。

首版包含：运行与输入版本、综合面积与单元统计、setup/hold 汇总、关键路径有限明细、约束完整性、运行状态、日志严重问题。功耗、细粒度物理拥塞、IR/EM 等作为可选扩展；没有相应数据时必须标记未测，不填写 0。

### 1.3 明确不做

不自动修改 RTL、SDC、库、dont_use、时序例外或签核阈值；不自动重跑无限制实验；不把综合时序当作后端签核；不凭模型结论宣告功能等价、故障关闭或 PPA 优化成功。

模型不负责权威数值、单位换算、差异计算和 pass/fail 真值。即使模型不可用，结构化数据、比较和质量门禁仍必须可运行。

## 2. 总体流程和职责分工

```text
现有综合/STA 作业与报告（只读）
  → 封存原始产物 + run manifest + 完成状态
  → 厂商/版本适配器：优先原生结构化导出，其次受测文本解析
  → 统一数据模型 + 单位转换 + 字段级来源
  → 数据质量检查 → 无效数据隔离，不进入“正常”汇总
  → 选择基线 + 比较条件审查
  → 确定性差异/趋势/告警
  → LLM 接收有限证据包，撰写解释和下一步假设
  → 工程师复核 → 内部发布 → 待办/实验 → 下一轮闭环
```

| 角色 | 首次建设负责什么 | 每轮负责什么 | 不应外包给模型的责任 |
|---|---|---|---|
| 设计工程师/专题负责人 | 选择 IP、消费者、问题和基线 | 看差异、关联 RTL、确认待办 | 设计意图、收益口径、最终解释 |
| 综合/STA 负责人 | 定义 stage、scene、metric 语义与有效性 | 审查约束/库变化、异常与候选实验 | 分析有效性、SDC 与签核规则 |
| CAD/脚本维护者 | 适配器、schema、校验、归档和回归测试 | 处理格式变更、失败和版本迁移 | 工具执行真实性与解析正确性 |
| 平台/安全负责人 | 数据边界、权限、模型接入、配额 | 服务异常和审计 | 允许的数据、工具与网络范围 |
| 使用方/评审者 | 确认产物够用而不过度建设 | 接收结果、接受或退回行动项 | 验收与关闭问题 |

小团队可以一人兼多角，但必须区分产出与复核；高风险时序判断由具有相应职责的人确认。

## 3. 多 IP、多轮数据如何组织

### 3.1 不能只用 IP 名和“第几轮”做主键

定义四层对象：

| 对象 | 建议标识 | 含义 |
|---|---|---|
| IP 配置 | `ip_id + config_id` | 参数/宏/接口/容量等配置明确的设计对象 |
| 实验/迭代 | `experiment_id + round_label` | 人类描述的一次改动或迭代；标签不保证跨 IP 可比 |
| 执行实例 | 全局唯一 `run_id`，另有 `attempt` | 一次实际工具执行；失败、重试都保留，不覆写旧记录 |
| 分析观察 | `run_id + stage + scene_id + check_type + path_group + scope` | 某阶段、场景、检查类型、路径组/层级下的指标 |

`scene_id` 必须映射到真实的 mode、PVT、RC/寄生条件、分析设置，不只是一个随意的“ss”字符串。同一网表可能产生多个观察，不应因此在台账中算作多次综合或重复累加面积。

必须保存 `parent_run_id`、`baseline_run_id`、`baseline_kind`、`source_run_id`。分别区分设计迭代来源、比较基线和被 STA/报告导出复用的实际网表来源。重解析报告也必须保留解析版本，不改变原始 run 的身份。

### 3.2 目录建议（内部使用，不在公开仓库填真实数据）

```text
internal-report-project/
  config/              # IP 注册表、分析场景、指标规则、人工批准的基线
  adapters/            # 每个工具家族/报告版本的导出与解析适配
  tests/               # 获准样本、golden 标注、异常与回归用例
  runs/<ip_id>/<run_id>/
    manifest.json
    raw/               # 原始报告、日志、工具导出；完成后只读封存
    normalized/<parser_version>/
    quality/<rules_version>/
  comparisons/<comparison_id>/
    manifest.json      # 明确 base/head、比较类型、规则与例外审批
    deterministic/     # 差异 CSV/JSON、告警、条件变化
    ai/                # 输入证据索引、输出、模型/客户端版本
    review/            # 接受/退回理由、未决事项、行动责任人
  published/           # 只包含已评审且注明状态的内部交付
```

首版可以是 JSON/CSV+文件目录，不要求上数据库或仪表盘。规模增大后可建立可查询索引，但原始数据和历史比较应可追溯。文件路径只作定位，内容散列用于确认未被替换；元数据不能只靠目录名猜测。

### 3.3 运行 manifest 必填信息

| 字段组 | 必须记录的内容 | 用途 |
|---|---|---|
| 身份/生命周期 | schema_version、run_id、IP/config/top、experiment/round/attempt、创建/结束时间及时区、执行状态、退出码、作业 ID | 区分执行、重试、失败、未完成 |
| 设计 | RTL commit、dirty patch 散列、实际输入文件内容散列、filelist 顺序、include、宏、参数、生成器版本、网表散列 | commit 相同不保证输入相同；配置变化不能被隐藏 |
| 工艺与模型 | process/PDK release、标准单元库与版本/散列、允许的 VT/单元集合、memory/macro 模型、dont_use 规则 | 同工艺不代表同库、同宏模型或同实现条件 |
| 工具与流程 | 综合工具/STA 工具的名称、版本/build、脚本版本、命令与有效选项、优化策略、seed（适用时）、增量/全量、CPU 配置 | 标记工具/配方变化、复现条件与性能口径 |
| 约束 | SDC 主文件及递归依赖散列、实际时钟/生成时钟、I/O delay/load、uncertainty、latency、case analysis、例外、约束覆盖摘要 | 不只检查一个顶层 SDC 文件是否变更 |
| 分析条件 | stage、mode、PVT、RC/寄生源、ideal/propagated clock、OCV/AOCV/POCV 与 derate、CRPR、SI、GBA/PBA 等适用设置 | 区分分析上下文；不适用应显式说明 |
| 报告条件 | 报告命令/选项、units、精度、路径选择/Top-N、endpoint 去重口径、范围、完整性、原始位置 | 避免报告格式/截断被当成设计变化 |
| 基线/审批 | parent、固定基线、前一个可比基线、实验基线、变更类别、责任人、批准记录 | 固定基线不得自动随“最好结果”漂移 |
| 功耗（可选） | activity 来源/散列、时间窗、工作负载、频率、覆盖率、默认 toggle 假设 | 没有一致活动假设不比较动态功耗优劣 |

OpenSTA 的公开说明列出了 netlist、Liberty、SDC、SPEF 等输入，以及时钟和路径例外；ORFS 的配置文档说明平台、设计、工具变量及其相互影响。这些公开资料支持“需要保存有效分析条件”的原则，不代表可替代公司工具手册。[S1][S2]

### 3.4 完成状态：执行成功不等于结果有效

建议分开保存三个状态：`execution_status`、`data_quality_status`、`review_status`。工具退出码为 0 仍须检查报告完整、预期场景齐备、无关键未约束/黑盒等问题。

报告文件存在但仍在写入不能被导入。由作业封装在关闭文件后写原子完成标记；旧流程没有标记时，必须用作业状态、日志结束信息和稳定性检查联合确认，再由负责人接受。不要只根据文件 mtime 或尾部一行“成功”判断。

相同 `run_id` 与相同内容重复导入应幂等；同一 ID 不同内容必须报冲突。失败的最后一轮不能被“上一轮成功”悄悄替代，应同时展示最新执行状态和最后可比有效结果。

## 4. 指标字典：先约定含义，再写解析器

### 4.1 最小指标集

| 指标组 | 建议字段 | 统一规则与陷阱 |
|---|---|---|
| 面积 | stdcell_area、macro_area、total_cell_area、层级 exclusive/inclusive 标志 | 验证面积单位及来源；不能把 core/die area 混入 cell area；不能将父层级面积再与子层级相加 |
| 单元 | sequential/combinational、buffer/inverter、latch、VT 分类、unmapped/blackbox | 保存互斥/包含关系；分类相互重叠时禁止简单求和 |
| Setup | worst_slack、WNS、TNS、violating_endpoints、checked_endpoints | 按 scene/path group，保存命令、范围和统计口径 |
| Hold | 同上，但 check_type 独立 | 不用 setup 改善抵消 hold 恶化；综合阶段估计不代表布线后 hold 通过 |
| 其他时序检查 | recovery/removal、clock gating、min pulse width 等适用项 | 不塞进 setup/hold 同一数字；按工具定义独立保存 |
| 时序完整性 | unconstrained/no_clock 等计数、预期场景和时钟覆盖 | 保留已批准例外及依据；新增问题或状态未知不能显示为绿色 |
| 电气设计规则 | max transition、max capacitance、max fanout 等 | 标明这是电气/时序 DRC，不是版图 DRC |
| 资源 | 工具运行 wall time、CPU time、peak RSS、license/queue wait | 排队、主机、核数、增量状态不同，不直接归因 RTL |
| 功耗（可选） | leakage、internal、switching、total 与 activity metadata | 缺失则 null；不因处于同工艺就认为功耗可比 |

### 4.2 Worst slack 与 WNS 必须分开

保留原始报告字段和 `wns_convention`：`clipped_nonpositive`、`signed_worst` 或 `unknown`。OpenSTA 官方参考说明 `report_wns` 在 worst slack 为正时输出 0，而 `report_worst_slack` 报告最差 slack，说明不能从 WNS=0 还原实际正裕量。[S3]

建议 canonical 字段为：`worst_slack_ns`（确知时填写）、`wns_ns`（按明确规范非正）、`vendor_reported_wns` 和原始口径。未知口径不得由模型猜测。如果只有 WNS=0，则可说“该报告范围内没有负裕量”，不能说“最差裕量为 0”或自行补出正数。

### 4.3 TNS、端点数量与 Top-N

TNS 使用工具针对确定检查范围导出的权威汇总，保存是“每端点最差负裕量”等具体口径。**不能把 Top-N 路径列表的负 slack 相加冒充全量 TNS。** 一个 endpoint 可能出现多条 path；不同路径组、场景也可能包含相同 endpoint。

不跨 corner/mode 加总 TNS 来形成所谓“芯片总 TNS”，不把 setup 与 hold 加总，不把多个 IP 的平均 WNS 作为设计质量。确需组合统计时，必须定义去重集合、物理实例和用途，且不能当签核指标。

### 4.4 单位、缺失、精度与字段级证据

统一时间为 ns；面积仅在工具/库定义支持时归一为 µm²，未知面积单位保留原始值并禁止百分比比较；功耗统一为 mW，内存统一为 MiB，并保留原单位与转换因子。不要从“行业通常如此”猜单位。OpenSTA 提供显式的报告单位命令，适配器应利用相应工具能力。[S3]

数值来源包含：报告相对路径、SHA-256、行区间或 JSON pointer、工具与适配器版本、原始值/单位、规范化值/单位、解析状态。`0`、`missing`、`not_applicable`、`parse_error`、`not_reported`、`incomplete` 必须区分。

指标差异小于报告有效精度时标记“精度范围内”，不要输出虚假的小数位。NaN、Infinity、被截断的数、重复且冲突的字段应被拒绝；报告缺失不能自动补零。

## 5. 可比性规则：同工艺只是第一层筛选

### 5.1 将输入变化拆成三类

**设计变量**：预期比较的 RTL 修改及其明确的设计意图。记录但不要求 RTL 散列相同，否则无法比较多轮设计迭代。

**必须保持的分析条件**：IP/config 身份、stage、场景语义、库/宏模型、有效约束、分析选项、报告口径和适用的实现配方。条件不同可能改变结论含义。

**实验变量**：明确批准的工具版本、约束、优化配方等变化。可以做受控实验，但结论只对该实验成立，不允许伪装成纯 RTL 优化。

别把“比较上下文散列”与“设计输入散列”混成一个要求全相等的 hash。也不能把所有变化都排除在上下文之外。

### 5.2 四类比较状态

| 状态 | 条件 | 允许输出 | 禁止输出 |
|---|---|---|---|
| STRICT | 同 IP/config/stage/scene/指标口径，规定分析条件一致；设计改动已记录 | 数值差异、趋势和待验证机制 | 仅凭同条件变化就证明因果、等价或签核 |
| CONTROLLED_EXPERIMENT | 显式批准并完整记录实验变量，其余条件符合实验设计 | 原值、差值、被改变的条件、实验限定结论 | 混入纯 RTL 趋势排行榜或隐瞒实验变量 |
| CONTEXT_CHANGED | 库/频率/约束/配置/阶段等有未受控变化，或无法确认等价 | 条件差异；可并列展示原值但不评价改善/退化 | 常规 PPA 优化百分比、自动告警豁免 |
| INVALID | 关键数据缺失、失败、截断、来源冲突、单位/口径未知 | 数据质量问题与补数行动 | 差值、零填充、通过结论 |

状态允许按指标分别判定。例如 timing 条件变化不必删除一份有效 cell count，但面积是否可比还要审查频率约束是否影响了综合实现；不要自动推断面积独立于时序环境。全报告首页显示最关键阻断项。

### 5.3 场景集合变化和约束“语义一致”

先比较预期集合与实际集合，不能先对交集求最差值再宣布整体变好。少跑一个坏 corner、漏掉一个 clock group，可能制造表面改善。

SDC 文件散列改变先进入条件审查；即使只改注释，也需要可核对的实际加载约束导出或人工审批才能认定等价。递归 source、变量、环境和脚本生成的约束都在范围内。仅 regex 对比顶层 SDC 不足以证明语义等价。

批准等价的记录应带 base/head、变化项、核验证据、审批人和规则版本。审批不等于改写原始 hash，也不允许模型自己批准。

### 5.4 三种基线并存，不能互相替代

| 基线 | 选择方式 | 回答什么 |
|---|---|---|
| 固定里程碑基线 | 人工批准的明确 run；升版留历史 | 与本次目标起点相比改变多少 |
| 上一可比有效轮 | 按谱系和完成时间查找，明确跳过的失败/不兼容轮次 | 最近一次可比改动带来什么 |
| 实验对照基线 | 由实验卡规定，必要时重跑 | 某个变量的效果是什么 |

没有基线时输出 `NO_BASELINE`，只展示单轮指标。基线不能按“slack 最好”“文件名最大”自动选，也不能拿 IP-A 的 R03 给 IP-B 的 R03 做差。重试与重复实验不算独立设计改进。

### 5.5 跨 IP 只做组合视图，不默认做设计优劣排行

跨 IP 可以统一看：本轮完成率、数据质量、各自相对基线的状态、每 IP 的目标达成情况、关键待办、共同环境变更影响。

不同 IP 的面积、频率、路径数量和功能规模不同，不能仅因同工艺而按绝对 WNS/面积给“效率”排名。按目标归一也需要明确目标语义，不宜形成一个掩盖差异的综合分。

若同一环境变更后多个 IP 同向异常，应先检查共享脚本、库、约束模板、模型和解析器，但这只是候选共因，不是证明。汇总面积时也要检查是否是 SoC 内互斥的独立实例，避免父 IP 与子 IP 重复、同网表多个 corner 重复。

## 6. 确定性差异、阈值与趋势

### 6.1 运算规则

```text
普通差值 Δx = x_head - x_base
面积相对变化 = Δarea / area_base × 100%   （base>0、口径一致时）
slack 改变量 = slack_head - slack_base    （正值表示裕量增加）
TNS 负裕量负担 B = abs(TNS)              （仅已确认 TNS≤0 的口径）
TNS 负担减少量 = B_base - B_head
TNS 负担减少率 = (B_base - B_head)/B_base  （B_base>0 时）
```

base=0 时不得除零：0→负值为新出现违例，负值→0 为该完整报告范围内的负裕量消除，0→0 仅表示两轮均无报告到的负裕量。不要对正负跨零的 slack 使用普通百分比。

例如 worst slack -0.12 ns→-0.04 ns：增加 0.08 ns，但仍不满足非负裕量。TNS -20 ns→-5 ns：负裕量负担下降 75%，不是“时序已通过”。示例数据为虚构计算说明。

### 6.2 告警设计

先设硬门禁：关键报告缺失、未预期黑盒、新增未批准的 unconstrained/no_clock、缺必需场景、关键单位未知、条件未经审批改变。不得被“WNS 改善”覆盖。

再设工程变化阈值，由 IP/STA 负责人按精度、基线波动、时钟尺度和目标批准。示例起点：面积增加超过 2% 提醒；setup/hold 裕量减少超过 0.02 ns 提醒；新出现负裕量不论变化是否够大都提醒。**这些只是阈值配置示例，不是行业标准。** 对很快/很慢时钟需调整，并单独配置 setup 与 hold；合理时可辅助使用固定相关时钟周期的比例，但不跨模式或复杂多周期路径机械套用。

区分 `DATA_BLOCKER`、`ENGINEERING_REGRESSION`、`CHANGE_NOTICE`、`REVIEW_PENDING`，避免把数据失败也显示成设计失败。告警规则版本随比较归档。

### 6.3 多轮趋势

固定 base/head 后再计算。每条趋势线只能连同一可比序列中的点；库、工具、目标频率、场景或口径变化处断线并标注。失败/缺失轮次显示空缺，不用上一值填补。重复运行显示重复样本，不选最好值替代整轮。

优先给出按 IP 的表：固定基线差值、上一可比轮差值、当轮状态、约束变化、未决问题。若环境具有运行波动，先做同输入重复测量，再报告范围；两次运行的微小差异不能直接定性为优化。

## 7. 路径级差异与问题生命周期

### 7.1 路径匹配的稳定身份

精确匹配键至少包括 scene、check_type、path_group、launch/capture clock、相关边沿、完整 startpoint/endpoint 和分析口径。保留层级、总线索引、生成实例编号；只做经过验证的名称规范化，不能为了提高匹配率随意删数字。

网表重命名、retiming、复制或层级变化时，用经过确认的 source mapping/映射表辅助。精确路径、端点级、路径族级分别输出匹配置信依据；启发式相似只用于导航，不作为“同一条路径”的证明。

对匹配路径分别看数据到达、要求时间、clock latency/skew、uncertainty/例外，以及可用的 cell/net delay、逻辑深度、fanout/负载。数据侧与时钟侧都可能影响 slack，不能只看组合级数。

### 7.2 Top-N 不是问题全集

建议首轮每个关键路径组保存固定数量的 setup/hold 路径，并明确 N 和筛选条件；具体 N 由报告量和用户需求决定。汇总指标必须来自工具全量统计，不随 N 改变。

基线问题不在 head Top-N 中时，状态是 `NOT_OBSERVED_IN_SAMPLE`，不是 `RESOLVED`。需要对原端点/路径做定向查询或检查完整覆盖后，才能确认是否消除；补报告消耗资源时按审批规则执行。

### 7.3 问题状态与来源

使用 `NEW / PERSISTENT / IMPROVED_BUT_OPEN / WORSENED / NOT_OBSERVED_IN_SAMPLE / RESOLVED_VERIFIED / NEEDS_REVIEW`。单独保留 issue_id，不能让路径排名改变就生成一份全新故障。

每条行动项有负责人、目标、证据、待补输入、下一实验、验收人及关闭依据。AI 可以建议状态和行动，最终关闭由工程师确认。

## 8. 工具适配与实施模块

### 8.1 适配原则

优先使用公司现有工具的结构化导出、Tcl 对象/数据库查询及受支持报告方式。没有结构化导出时，使用固定工具版本、命令选项、单位和语言的文本解析器，配真实样本回归。未知格式须明确失败，不用模型兜底填数。

OpenSTA 当前官方命令参考包含路径报告、setup/hold 选择、路径数量和 JSON 格式等能力；ORFS 有指标 JSON、基线和规则检查实践，可借鉴分层结构。[S3][S4] **这些不构成把公司设计上传公共 QoR dashboard 的授权。** ORFS 文档中的联网检查示例不应直接用于机密项目；本方案默认内部存储与内部比较。

若使用 DC/FC/PrimeTime 或 Genus/Tempus，由工具负责人用所部署版本的官方手册/内置帮助确认命令、参数、报告粒度和导出能力。本文不假定不同厂商相同名字的字段具有相同语义。

### 8.2 实施任务拆分

| ID | 模块 | 输入 → 输出 | 完成定义 |
|---|---|---|---|
| T01 | IP/配置/scene 注册与基线管理 | 人工批准配置 → registry/baseline map | 不依赖文件名猜测，可识别缺失 IP/scene |
| T02 | 作业完成钩子与封存 | 作业状态/报告 → manifest+只读 raw | 成功、失败、部分完成分开；hash、时间、退出码齐备 |
| T03 | 工具适配器 | 已知格式/原生导出 → raw facts | 保存版本/命令/来源；未知格式报错 |
| T04 | 标准化与质量检查 | raw facts → canonical+quality | 单位/缺失/去重正确，关键字段与人工 goldens 一致 |
| T05 | 可比性引擎 | 两个 manifest+规则 → 状态/原因/条件差异 | 不受模型控制，不能漏掉关键环境变化 |
| T06 | 指标差异与趋势 | canonical+比较许可 → diff/alerts/history | 符号、分母零、场景缺失和序列断点测试通过 |
| T07 | 路径匹配与问题跟踪 | paths+映射 → path diff/issues | 明确 exact/heuristic/unmatched；Top-N 消失不自动关闭 |
| T08 | LLM 证据包和输出校验 | 确定性产物+批准上下文 → 分析草稿 | 数字来自输入，引用可定位，事实/假设/待确认分开 |
| T09 | 评审与内部发布 | 草稿+证据 → 接受/退回+行动 | 留审查记录，不修改原始结果，支持模型不可用时发布表格 |
| T10 | 测试、维护、收益统计 | 全部尝试/版本/成本 → 回归与月报 | 记录失败与返工，新增适配器不得破坏旧样本 |

T01→T02/T03→T04→T05→T06 是首版主链。T08 不应先于 T04—T06。路径 T07 可在主链稳定后扩展。模型选型调优不是解析器正确性的替代品。

### 8.3 建议内部接口（设计契约，不是已提供的命令行）

```text
ingest(run_dir)                -> manifest + receipt
extract(receipt, adapter_id)    -> facts + extraction_log
validate(facts, registry)       -> canonical + quality_report
classify(base, head, policy)    -> comparison_permission + reasons
diff(base, head, permission)    -> metric_delta + condition_delta + alerts
prepare_evidence(diff, limits)  -> evidence_bundle
explain(evidence, model_route)  -> structured_draft
review_publish(draft, decision) -> reviewed_report + actions
```

接口返回版本、输入散列、退出状态、错误、日志位置和是否截断。真正的命令和集成入口由 T01—T10 实施后给出，不能将上面伪接口当作现成可执行工具。

## 9. 首次实施计划：从手工小闭环到稳定运行

以下是项目排期参考，不是对本次回答交付时间的承诺。按门禁而不是日历强行推进；未提供人力和工具条件，工作量需在摸底后修订。

| 阶段 | 建议安排 | 要做什么 | 放行条件 |
|---|---|---|---|
| M0 范围与基线 | 第 1—2 个工作日 | 明确消费者、IP/config、场景、报告、工具与现有脚本；选历史样本；计时原流程 | registry、首个人工差异样例、指标/可比性口径被负责人接受 |
| M1 确定性闭环 | 第 3—7 个工作日 | 接通 T02—T06；先两 IP、三轮；错误样本回归；不接 LLM 也有可用表格 | 关键字段准确、错误被阻断、可比性和算术测试通过 |
| M2 AI 辅助影子运行 | 第 2—3 周 | T08/T09；两模型同证据对照；历史盲测和当前轮并行，人工流程仍为准 | 未捏造数字/来源，评审可控，错误有安全退路 |
| M3 多 IP 扩展与常态化 | 第 4 周起，按需 | 分批加入更多 IP/scene，路径跟踪、事件触发、维护与收益月报 | 跨 IP 留出集通过，有负责人、版本回退、收益证据 |

上述排期不是要求先等四周才能使用。M0 就能交付第一份手工核对的差异报告；自动化逐步替换人工步骤。也不是保证四周可完成任意公司集成。

### 9.1 没有新平台时，第一轮就怎样操作

1. **选一个问题和一个 IP。** 例如“本轮面积为什么变大、setup 是否真的改善”；选明确 base/head，不先扫全部目录。
2. **收集原始输入。** 两轮的 QoR/area/timing/constraint-check/日志、执行状态，以及实际库、SDC、RTL、配置和 stage 信息。将缺项写入清单。
3. **填 06 的运行卡和比较卡。** 元数据不能确认时先标记，不让模型帮忙猜。
4. **由人或已有脚本提取首组指标。** 使用长表模板，填原值、单位、来源及状态；逐项回到报告核验。
5. **先做可比性判定。** 不可比就输出“缺什么/变了什么”；不要继续写常规优化结论。
6. **用确定性方式计算差异。** 可以是已有脚本或受检查的表格公式；锁定字段、符号与分母零处理。
7. **把差异表和最小证据交给模型。** 要求只解释已核实事实，最多给少量假设和区分实验，不整包塞入全部报告。
8. **人工评审并记录时间。** 接受、修改或退回；再在第二个 IP 上重复，检验方法是否只适合第一个样本。

这八步可以在获准内部文件与现有工具上执行；其中“手动可完成”不等于当前仓库已提供生产解析器。

## 10. 每一轮的标准操作规程

| 顺序 | 操作者与动作 | 必须检查 | 产物/失败处理 |
|---|---|---|---|
| O01 触发 | 作业钩子/维护者发现完成或失败 | run_id 是否唯一、完成状态是否可信 | 建立 ingestion receipt；失败也入台账 |
| O02 封存 | 维护者保存 manifest 与 raw | 报告属于本轮、输入散列、时区、退出码、预期报告 | 原始产物只读；部分数据隔离 |
| O03 抽取 | 适配器处理报告 | 工具/格式支持、单位、必需字段、重复/截断 | raw facts+解析日志；未知版本停止 |
| O04 质检 | 规则引擎+必要人工核对 | 场景/时钟/端点覆盖，warning/黑盒，缺失和来源 | quality report；不合格不发绿色结果 |
| O05 选基线 | 规则查找+负责人确认 | IP/config/stage/scene、固定/上一可比/实验基线 | comparison manifest；无基线只出单轮表 |
| O06 判可比 | 确定性规则+例外审批 | 有效约束、库、工具、分析条件、报告口径 | STRICT/实验/条件变化/无效+原因 |
| O07 算差异 | 脚本/受测规则 | 符号、零分母、组/场景去重、条件断点 | 差异表、告警、趋势；不能依赖 LLM 算数 |
| O08 补证据 | 设计/STA 负责人 | 关键路径、约束变化、RTL diff 是否足够 | 必要时只导出有限片段；补跑先批预算 |
| O09 AI 草稿 | 模型在只读证据上分析 | 数字与来源有效、假设不冒充事实、无越权命令 | 结构化解释；超时失败则保留确定性报告 |
| O10 审查 | 设计及必要 STA 负责人 | 结论、优先级、待办和关闭依据 | 接受/退回/需补数；记录修正工时 |
| O11 发布 | 维护者 | 标题包含 IP/base/head/stage/scene/状态 | 内部报告；模型原稿不自动发给所有人 |
| O12 闭环 | 行动负责人 | 下轮是否验证假设，历史问题如何变化 | issue/实验卡更新，不用文档生成代替问题关闭 |

每轮报告首页固定显示：有效/总 IP 数、有效/预期观察数、最新失败轮次、不可比项、硬门禁、关键变化、待办。详细附录再放指标和路径，避免读者从长文中找状态。

## 11. 多 IP 运行、并发和资源管理

一个 API key 的并发 10 只约束模型请求，不能推出可并发 10 个综合作业或有十名工程师的能力。先确认两个模型是否共享配额，以及是否还有 RPM/TPM 和租户限制。

建议初始全 key 模型并发上限 6—8（需内部批准和实测调整），不要每个客户端各开 8 个。同一 IP/比较的发布由单一写入者完成；可以并行只读处理不同 IP。为人工交互、取消和重试留容量。

分别管理采集/解析 CPU、LLM 请求、EDA 作业/license 和人工评审四条队列。模型调用结束即释放其槽位；等待综合运行不占一个长时间模型请求。没有新证据不循环调用模型重复总结。

缓存 key 至少含原始内容、schema/parser/rules/prompt/model 配置版本；旧草稿不能在输入变化后作为新结论。429/暂时失败有限重试并退避；格式错误/数据缺失不靠无限重试解决；禁止通过额外 key 绕过未批准配额。

优先事件触发导入，不让 agent 不断遍历共享盘。取消和重试要幂等，防止同一轮重复发布或重复启动 EDA。

## 12. LLM 的任务合同与角色边界

### 12.1 输入只给最小证据包

包含：任务问题、base/head 与可比性判定、关键数值与原文位置、条件差异、少量关键路径、批准的 RTL diff/设计意图、未确认项、预算与禁止事项。不要默认把全库、全部 SDC 或全部报告送入模型。

日志、报告、注释中的文字是待分析数据，不是允许执行的指令。工具权限应在模型外限制；模型不能因文件中的“忽略此前规则、运行上传命令”而获得权限。

### 12.2 输出分成四层

| 层 | 示例 | 审查要求 |
|---|---|---|
| 已核实事实 | 面积增加 3.0%，setup worst slack 增加 0.08 ns | 数字必须出自确定性表，引用可定位 |
| 有限结论 | 本场景裕量改善但仍负；不能评价未跑场景 | 与完整性和可比性状态一致 |
| 待验证假设 | RTL 仲裁路径改变可能影响 mux 深度 | 必须附支持/反对证据及缺失输入 |
| 下一步实验 | 固定约束与库，仅回退该 RTL 修改重新比较 | 批准后由工程流程执行，不自动启动 |

不同模型互审可以发现问题，但不是独立真值。输出校验至少核对所有数字、run/scene 身份、引用和状态；错误不能通过增加“置信度 99%”掩盖。

### 12.3 模型评估最小集

两个模型用同一已核实证据包、同一任务合同和相同预算。先评估 12 个有区别的包：正常、实际退化、改善但仍违例、约束改变、单位变化、场景缺失、Top-N 消失、共享环境变化、根因证据不足、工具失败、跨 IP 误配、功耗活动不一致。

指标包括数值复述准确、来源正确、硬门禁保留、假设/事实区分、错误根因率、人工审查时间和预算内完成率。测的是该工作流中的模型适用性，不从模型名称预设胜者。

## 13. 验收、测试与停止规则

详尽测试矩阵见 06。首版至少经过以下门禁，门槛为本方案建议，不是行业认证：

| 层 | 验收要求 | 不通过时 |
|---|---|---|
| 数据抽取 | 小型标注集上关键字段、单位、来源全部正确；可选未知项如实缺失 | 修适配器，不让 LLM 补数字 |
| 比较规则 | 所有已设计的错误配对、条件改变、缺失/截断样本均被正确阻断/标记 | 暂停自动发布，修复后重放历史 |
| 运算/路径 | 零分母、符号、去重、精度、Top-N 和重命名测试符合预期 | 不出趋势和关闭结论 |
| LLM | 有限样本中无编造数值/来源、无越权、无放宽约束以“通过” | 回退确定性表格，修改合同或路由 |
| 操作 | 模型失效、工具失败、重试、取消、旧输入和回退演练可控 | 不扩大 IP 范围 |
| 业务 | 比现有人工+脚本的净人工投入减少，结果被实际使用，评审未成新瓶颈 | 缩小范围、仅保留脚本、转向或停止 |

不要把“测试样本全部通过”宣传成生产零错误。保留未参与调试的 IP/轮次，定期重测。关键异常和所有自动关闭项应 100% 人工审查；常规字段可在成熟后按风险抽查，但质量要求不下降。

## 14. 故障处理、变更与回退

| 故障/变化 | 操作 |
|---|---|
| 报告缺失、截断、解析失败 | 隔离该观察并列出缺项；其他 IP 可继续；总览仍显示缺失 |
| 实际库/约束/scene 不一致 | 暂停常规比较，出条件差异；受控实验需另建实验卡 |
| Parser 升级 | 用封存 raw 重解析到新版本目录；对 goldens 和历史差异回归，不覆盖旧结果 |
| 工具/PDK/库升级 | 新建条件序列；选择代表 IP 做桥接对照；固定基线升版需人工批准 |
| 模型超时/不可靠 | 保留确定性报告，回退人工解释，不转公网模型 |
| 基线误选 | 作废相应 comparison，不删 raw；选择正确基线重建并保留更正说明 |
| 已发布报告有错误 | 明确撤回/更正和影响范围，通知实际消费者；不静默覆盖 |
| 实验无收益或维护过重 | 停止自动解释或停该候选，保留有用脚本与数据口径 |

安全日志只保留获准内容；不要在调试日志打印 API key、完整内部配置或未授权源码。公开仓库中的真实输入误提交需要按公司事件流程处理，而不是仅删掉工作树文件。

## 15. 收益与人力：单独核算本专题

### 15.1 三组对照

A=人工+现有脚本；B=更完善的确定性采集/比较但运行时不调用 LLM；C=B+LLM 分析。至少分别报告 B−A 与 C−B 的收益，避免把全部脚本收益都说成模型推理收益。AI 辅助开发脚本的建设工时变化另记。

每次计时：找数据、核元信息、抽取、比较、解释、评审、修正、跟踪和返工；机器 wall time 与人工投入分开。以“完成一份通过验收的 IP 轮次比较包”为单位，不能把一个包中的多个 corner 都算作独立的人力收益案例。

### 15.2 纯演示情景，不是效果预测

假设 6 个 IP、每个每月 8 个需要分析的比较包，共 48 包；原流程每包 1.5 人工小时；新流程全部准备/审查/返工平均 0.6 小时；共享维护 6 小时/月：

```text
基线人工 = 48 × 1.5 = 72 小时/月
新流程人工 = 48 × 0.6 + 6 = 34.8 小时/月
净释放 = 37.2 小时/月
本任务净节省率 = 37.2 / 72 ≈ 51.7%
按 160 小时/FTE 月折算 = 0.2325 FTE
```

这只对应报告专题的工作量，不能外推整个岗位节省 51.7%。首次建设另扣：若建设投入为 60 小时、稳定月收益确实为 37.2 小时，简单工时回收约 1.61 个月；未计财务折现、成本差异和需求变化，不能当现金回收承诺。

若原流程已有脚本仅需 0.7 小时/包，同样假设下基线 33.6 小时、新流程 34.8 小时，反而净多花 1.2 小时。因此必须以现有自动化为基线。

每月同时报告：有效比较比例、解析失败率、不可比率及原因、告警有用率、错误根因率、审查/返工小时、按 IP 的覆盖和新工具成本。良好的“不确定/不可比”识别不是失败，不能为了让指标好看删掉。

## 16. 最终交付清单与实施结束定义

首版实施完成应交付：IP/场景与基线注册表；锁定版本的采集/适配脚本；manifest 与指标 schema；带来源的数据与质量报告；确定性比较规则和错误样本测试；多 IP 状态总览及单 IP 差异报告；可选模型输入/输出合同；评审与行动记录；操作/回退手册；按现有基线计算的工时证据。

本次文档交付已经定义这些内容，但没有声称公司实际脚本和验证环境已经搭建完成。缺少真实工具和报告时，不应给出伪装成可直接运行的 EDA agent。

**推荐启动动作：由设计工程师与综合/STA 负责人一起选 2 个代表 IP、各 3 个已有轮次，先手工完成一份有来源的差异表，并确认哪些轮次允许比较；然后只自动化这条已验收的小流程。**
