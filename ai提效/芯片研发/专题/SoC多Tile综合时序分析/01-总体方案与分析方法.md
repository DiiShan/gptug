# SoC 多 IP/Tile、多节点、多轮综合与时序报告分析：总体方案

> v1.0｜2026-10-05｜独立子专题，工程设计而非已运行系统。  
> 已知场景：整个 SoC 包含多个较大的 IP；每个 IP 以一个 tile 独立综合；同一制造工艺，可能使用不同 corner；不同设计验证节点下有多轮综合/时序报告。  
> **节点＝设计/验证里程碑，不是制造工艺节点；tile＝本项目独立综合单元，不默认等于 chiplet 或物理 die。**  
> 未提供实际工具/版本、报告样本、IP 清单、节点定义和资源条件，本文不编造商用 EDA 命令、内部测试成绩或确定收益。  
> [专题入口](README.md)｜[数据契约与比较规则](02-数据契约与比较规则.md)｜[操作、验收与收益评估](03-实施操作与验收评估.md)

## 1. 目标不是批量总结，而是持续的工程决策支持

每次 SoC 汇总必须可靠回答：哪些 tile 已产出本节点要求的结果，哪些失败或缺失；相对哪个基线发生了什么变化；变化是否可比；最应处理的风险在哪里；下一步由谁做什么；尚缺哪些证据；实际是否减少总人工投入。

建议同时建设三类产物，而不是一张混合排行榜：

| 产物 | 回答的问题 | 不允许推导出的结论 |
|---|---|---|
| 节点进度与覆盖视图 | 哪个 tile 在哪个里程碑达到哪些交付门槛 | 材料齐全不等于时序通过，更不等于全 SoC 签核 |
| 同条件 QoR 差异与趋势 | 同配置、同场景/口径下相对基线变化如何 | 未控制约束/库/流程变化时不能归因于 RTL |
| 风险与根因证据包 | 哪些候选问题需处理，证据与区分实验是什么 | LLM 的解释或两个模型一致不是根因证明 |

整体原则为：**确定性工具负责事实、计算和规则；LLM 负责受证据约束的解释、关联和沟通；专业负责人负责门禁、预算和签核。** 模型不可用时，采集、质量检查和差异分析必须仍可运行。

本专题独立展开是因为用户要求，不改变全岗位试点选题方法；报告分析并非默认第一名。

## 2. 先明确七个独立维度

| 维度 | 推荐标识 | 含义及使用规则 |
|---|---|---|
| 工艺平台 | process_id、pdk_release、library_set_id | 工艺相同仍可能库、模型、VT/允许单元集合不同 |
| IP 与独立综合单元 | ip_id、tile_id、config_id、wrapper_revision | 当前默认 IP 与 tile 一一对应；不同参数/外壳要分配置 |
| SoC 实例 | soc_instance_id、tile_design_ref | 同 IP 多实例与同一个独立综合设计不是一回事 |
| 设计验证里程碑 | milestone_id、acceptance_revision | 例如早期可综合、功能集成、收敛交付；名称由项目定义 |
| 工具流程阶段 | flow_stage | elaborated、mapped-synthesis、post-place、post-CTS、post-route 等，按实际流程配置 |
| 分析场景 | scenario_id、scenario_revision | mode、PVT、RC/寄生、时钟/例外与分析方法的有效组合 |
| 迭代与执行 | iteration_id、run_id、attempt_id、analysis_id | 改动意图、实际作业、重试、分析观察分开标识 |

同一里程碑可以有多轮综合；不同里程碑可以同为 mapped-synthesis；同一综合网表可以有多个 STA 场景。反之，综合为多个优化目标生成不同网表时，必须分开 synthesis run，不能伪装成同网表的多场景观察。

禁止靠目录中 `M2/r3/ss` 三个字符串推断全部身份。里程碑标签不是质量事实：同时保存功能范围、验证成熟度、黑盒情况和已经满足的门禁。

## 3. 顶层、tile 与实例的关系

### 3.1 默认按用户实际的一 IP 一 tile 落地

tile 注册表记录 IP、配置、综合 top、wrapper、接口、时钟/电源域、责任人、SoC 中实例列表和计费/面积归属。首次不要求重划分 IP，也不要求全 SoC 平铺综合。

如果同 IP 的两个实例具有不同参数、接口绑值、时钟预算、宏配置或物理上下文，不能自动复用同一份结果。允许复用时，应有等价配置和适用环境的确认记录；运行一次与 SoC 实例数分别统计。

### 3.2 tile 独立综合必须记录边界假设

必须记录 wrapper 中真实逻辑、临时 tie-off、stub/blackbox、虚拟时钟、I/O delay、input transition、output load、接口约束与预算版本。可移除 wrapper 与真实 SoC 逻辑分开标记。

无负载输出、常量输入、未连接功能、临时关闭逻辑等会改变分析对象；数值可以入库，但相应功能覆盖和可比性不能被忽略。优化掉的逻辑不能仅因面积变小就算收益。

### 3.3 跨 tile 路径是独立覆盖对象

只有 tile 内部时序结果时，平台只能声称“所观察 tile 的局部分析状态”。跨 tile 路径、顶层互连、共享时钟与其他顶层逻辑另建覆盖台账。

对于采用预算分解的同步接口，分别记录源 tile 的输出预算、互连预算、目的 tile 的输入预算及其时钟参考边。**不能把两个 tile 的 slack 相加当成跨 tile slack，也不能在未统一参考边和时钟项时直接相加两个 I/O delay 数字。**

建议维护两层审查：预算契约一致性审查；批准的顶层/层次 STA 或其他正式集成验证。若使用抽象/接口时序模型，记录生成网表、场景、端口覆盖和有效条件，不能跨版本盲目复用。PrimeTime 官方材料将层次分析、多场景和多 corner 分别列为能力；这支持采用专用流程承接集成分析，而不是靠 LLM 拼接局部结果。[S4]

## 4. 里程碑、批次与 SoC 快照

### 4.1 节点要求按项目批准，不预设全行业标准

可用以下例子启动讨论，但不得当作公司已有节点定义：

| 示例里程碑 | 可能的工程目标 | 要求矩阵中的典型变化 |
|---|---|---|
| M0 早期可综合 | 输入能展开、主要结构可观察 | 明确占位功能、宏/黑盒、有限场景；不宣传为完整 PPA |
| M1 功能集成 | 主要接口和功能集齐 | 增加必要场景、功能/配置覆盖、边界预算核对 |
| M2 收敛候选 | 设计与约束趋于稳定 | 更严格的差异、违例、验证和交付门槛 |
| M3 交付候选 | 形成下游接收证据 | 冻结输入与规则版本，未决项审批和接收人确认 |

每个里程碑定义必需 tile/config、flow_stage、scenario/check、report_type 及允许的例外。早期允许某项暂不适用，应保留批准理由；不能让模型或脚本自行从分母删除失败场景。

### 4.2 各 tile 不要求相同轮号

IP_A 的 R8 与 IP_B 的 R3 可以共同组成一次 SoC 状态快照；它们是否属于某个里程碑由明确的成员表决定。不能用“所有目录最新文件”拼成 SoC 状态，不能按轮号相等假设输入同步。

一个快照至少包含 snapshot_id、里程碑、截止时间与时区、预期成员、每成员选定 run/analysis、功能配置、状态、数据年龄、沿用原因和审批。冻结后不可原地替换成员；补到数据时生成新快照修订。

区分正式批准快照与动态监控看板。动态看板可以显示最新进展，但每次导出仍要封存当时选择的成员清单。

### 4.3 同时展示三种“最新”

最新一次执行、最后一个有效结果、正式快照选定结果可能不同。最新执行失败时，失败必须显式显示；可以旁列上一个有效值，但标为历史沿用，不能伪装成本轮成功。

对于复用结果，显示 `carried_forward_from`、年龄、适用配置和审批。未达到当前节点要求的历史结果不能充当当前节点通过证明。

## 5. 总体架构及建设层次

```text
获准的综合/STA 产物、输入版本和作业状态
    ↓ 封存，生成不可变 run/analysis manifest
工具/版本适配器：原生结构化导出优先，受测文本解析次之
    ↓ 单位与字段语义归一，保留逐字段证据
原始产物库 + 规范化事实库 + 版本化注册表
    ↓ 预期矩阵、质量检查、可比性、基线选择
确定性比较引擎：差异、趋势、覆盖、规则告警
    ↓ 切片后的证据包，不传全部大报告
LLM：解释、跨证据关联、问题卡与实验建议
    ↓ 数字/引用检查 + 专业复核
SoC 快照报告、tile 深入报告、行动项与关闭记录
```

首版可使用只读目录、JSON/CSV 和本地可查询索引，不要求立即上线数据库、复杂看板或向量库。规模增长后再采用内部数据库和对象存储；权限与不可变原始产物原则不变。不要将商用库、网表、真实报告或敏感配置上传到本公开 GitHub。

## 6. 采集范围与指标字典

### 6.1 必需数据

运行完成信息与严重错误；综合面积和单元统计；时钟与约束覆盖；setup/hold 汇总；有限关键路径明细及其选取策略；输入与工具有效版本；关键配置/边界变化。报告不存在是缺失，不是该指标为零。

分析场景需纳入实际 mode、PVT、RC/寄生来源、ideal/propagated clock、OCV/derate、CRPR、SI、GBA/PBA 等适用项。OpenSTA 官方 README 列出网表、Liberty、SDC、SPEF 及多种时钟与例外；ORFS 文档说明平台、设计、工具变量及覆盖优先级。这是保存实际有效环境而非仅存顶层脚本的公开依据。[S1][S2]

### 6.2 指标必须分层，不做单个总分

| 指标族 | 建议指标 | 关键限制 |
|---|---|---|
| 运行 | 成功/失败/超时、wall time、CPU time、峰值内存、license 等待 | 人工时间、工具运行和排队分别计算 |
| 范围 | 功能/config、映射端点、宏/黑盒、未约束项、必需场景覆盖 | 退出码零不代表结果有效 |
| 面积 | stdcell、macro、总单元面积、层级 exclusive/inclusive | 不混 core/die area；同网表多场景不重复累计 |
| 单元构成 | seq/comb、buffer/inverter、latch、VT、映射类型 | 分类可能重叠；先定义集合关系 |
| Setup/Hold | worst slack、规范 WNS、TNS、违例端点 | min/max、检查类型、场景、范围和端点口径分别存 |
| 路径 | 起终点、时钟/边沿、数据/时钟分量、层级、路径族 | Top-N 是截取样本，不是所有路径 |
| 约束 | clocks/generated clocks、I/O、例外及作用范围变化 | 文件 hash 相同不保证环境中生效结果相同 |
| 质量 | max transition/capacitance/fanout、意外 latch/unmapped 等 | 与 setup/hold 分开显示，不相互抵消 |
| 功耗（可选） | leakage、internal/switching、活动覆盖、工作负载 | 活动与频率/电压不一致时不直接比较动态功耗 |

保留工具原始字段与归一字段。worst slack 可以为正；本方案规范化 WNS 为 `min(0, worst_slack)`，但仅在已覆盖且非空的范围内计算。没有路径或覆盖不明时返回 null/unknown，不能当 0 违例。

在明确端点集合 E、同一场景/检查与最差路径口径后，规范 TNS 为 `sum(min(0, s_e))`。这不是把 Top-N 每条路径 slack 相加。工具口径不同则保存原值并声明不可直接互换；见数据契约。

## 7. 比较之前先决定“这个比较回答什么”

| 类型 | 目的 | 允许的解释 |
|---|---|---|
| C0 条件固定的迭代比较 | 设计变化在同场景/流程下产生什么结果 | 同条件观察差异；是否功能等价仍另验 |
| C1 条件变化比较 | 换库、SDC、工具或 recipe 的影响 | 条件变化的观察；不能自动归因设计优化 |
| C2 跨里程碑成熟度比较 | 从 M0 到 M1 是否接近当前目标 | 范围/目标/质量进展；非直接 PPA 竞赛 |
| C3 跨 corner/mode 比较 | 同一设计在不同场景的敏感性 | 分场景分布和最差包络；不是时间上的改善 |
| C4 跨 flow_stage 比较 | 综合预估与物理阶段的相关性 | 同源设计的校准/偏差；不是同口径回归 |
| C5 同条件重复运行 | 工具波动与可复现性 | 估计噪声，不能挑最好 seed 当典型表现 |
| C6 跨 tile 组合评估 | 哪些单元/接口阻塞当前节点 | 按各自预算和覆盖分类，不按原始 WNS 排能力 |

可比性按指标判定，不能只给整个 run 一个布尔值。例如两个场景引用同网表，同口径面积可以复用；时序必须区分场景。相反两轮综合 corner 改变并生成不同网表时，面积变化也属于 recipe 变化下的结果，不能叫纯 RTL 收益。

将结论标记为 comparable、conditional、not_comparable、insufficient_evidence，并列原因码。未知字段不默认相等；LLM 不可覆盖判定。

## 8. 基线体系：固定、滚动、节点、实验同时保留

固定批准基线用于防止慢性退化；前一个可比有效 run 用于看本次变更；前一里程碑的批准快照用于成熟度追踪；控制实验基线用于归因。每条差异记录实际 base/head 的 ID，不只写“对比上轮”。

基线选择先过滤 tile/config、作用范围、stage、场景与比较类型，再按批准策略选；无可比基线就显示首次建档。不能因为最新一轮失败自动把它隐藏，也不能按最好的 WNS 选择基线。

固定基线更新须审批，保留旧版本和理由。分析规则、parser、阈值升级独立版本化；重解析两侧后才比较，不能一侧新解析器、一侧旧口径而不标注。

跨节点共同场景趋势与当前节点全部必需场景应并列显示。只看交集会隐藏新场景的风险；只看新全集又可能把覆盖扩大误判成设计恶化。

## 9. 多轮分析方法

### 9.1 确定性差异与趋势

计算绝对差、适用时的相对差、目标余量变化、是否越过门槛及持续轮次。对于 slack 用 ps/ns 绝对差和门槛状态；基线为 0/负值时不要输出误导性百分比。

WNS 改善但 TNS/违例端点变差时，必须同时说明；面积下降但黑盒增加、时钟遗漏、功能减少时先显示覆盖/条件风险。缺失不能以插值或零值进入趋势。

跨 tile 风险优先级参考本 tile 目标缺口、必需场景数量/严重性、持续性、集成影响、下一节点阻塞与证据把握；不简单用原始负 slack 排所有 IP，不用面积小证明设计优。

### 9.2 路径与问题追踪

稳定路径标识至少包含 tile/config、stage、mode、check、起终点、launch/capture clock 与边沿、报告范围；保留原始名字和映射版本。相同起终点在不同检查或不同场景不是同一测量。

rename、flatten、retiming、寄存器复制和跨层优化可能破坏精确匹配。先使用工具提供的映射/原始标识，再做带置信标记的路径族归并；模糊匹配仅用于定位候选，不能自动关闭问题。

Top-N 中不再出现标为 `not_observed_in_sample`。只有在当前适用场景下有定向重报/完整端点检查和合格证据时，才能判断该风险消除；存在其他场景/检查违例时仍不能关闭整个问题。

建议分别保存路径观测状态与问题处理状态。观测可为新增、持续、恶化、改善、未观察、无法映射；问题可为待分诊、分析中、待实验、已确认、待复验、已关闭、经批准接受风险。

### 9.3 初级归因到确认根因

将候选原因分为设计范围/RTL、约束/边界、库/宏、工具/recipe、物理/寄生、报告口径、随机波动、缺失数据。AI 每个原因必须引用证据，给出竞争解释、缺失输入与最小区分实验。

证据等级建议：F＝已观察事实；H＝相关性支持的假设；E＝控制实验支持；R＝责任人确认并有复验证据。不能把“某 commit 修改加法器、同时 WNS 恶化”直接升成 R。

必要时采用 2×2 桥接实验：旧/新设计 × 旧/新环境。令 Qij 表示设计 Di 在环境 Ej 的结果，分别计算设计效应、环境效应和交互项 `Q11-Q10-Q01+Q00`。必须先确认两套设计都能在两套环境中合法运行。无法完成桥接时明确混杂，不能强行给出唯一原因。

## 10. SoC 汇总的正确做法

### 10.1 至少四种覆盖率并列

执行完成率；数据有效率；可比率；在当前批准门槛下的通过率。分别写分子/分母与要求版本。不能把“所有有数据项都通过”表述成“整个 SoC 通过”。

预期分母来自批准的需求矩阵，包含缺失和失败成员；合法不适用需审批后显式列出。tile 粒度与 scenario/check 粒度同时提供，避免一个复杂 tile 的大量场景使统计失真。

### 10.2 不同指标使用不同聚合规则

| 指标 | 允许的 SoC 级展示 | 禁止做法 |
|---|---|---|
| Worst slack/WNS | 同一语义下观察集合的最小值，注明局部范围；分时钟/场景展示 | 平均 WNS、相加 slack、宣称等于全芯片关键路径 |
| TNS/违例端点 | 默认按 tile/场景分表；确需合并时明确不重叠端点和去重口径 | 同一端点多个 corner 重复相加后冒称全局 TNS |
| 面积 | 批准实例清单 × 对应独占设计面积＋独占顶层逻辑 | 同网表多个场景重复累计，父子 inclusive 面积重复累计 |
| 跨 corner | 分场景或最差包络并标最差场景 | 将所有 corner 当作同时存在的多份逻辑 |
| 功耗 | 一致工作负载/活动条件及场景组合下的估计 | 把各 tile 独立最坏功耗直接叫实际芯片功耗 |
| 执行资源 | 唯一实际作业的消耗及排队 | 同一个作业因导出多报告重复计费 |

若多个实例确实可复用同一 tile 面积，可按实例数计估算，但仍标记 wrapper 剔除、顶层逻辑、未建模互连/CTS/缓冲与物理阶段差异。部分覆盖时只能给“已覆盖部分面积估计”，缺少单元不能默认为零。

全 SoC 频率也不能从各 tile 的 WNS 简单换算：路径类型、约束、跨时钟关系及边界预算不同。频率能力应通过批准时序方法在明确约束下验证。

## 11. 看板和每轮报告

建议提供五页/五个视图，不强制具体软件：

1. SoC 节点页：snapshot、目标节点、数据截止、预期/有效/失败/缺失/沿用、集成覆盖与阻塞。
2. Tile 深入页：配置/版本、关键指标、双基线趋势、场景完整性、约束/功能变化、路径族与行动项。
3. 场景矩阵页：tile × mode/corner/check 的状态和缺失，不只显示最差一格。
4. 变更证据页：base/head 条件差、确定性指标差、源报告位置、AI 假设和评审结果。
5. 跨 tile 接口页：预算版本、两端状态、模型匹配、顶层验证证据和未覆盖边。

每个数字能追到 artifact hash＋行区间或结构化字段路径；每个图表有数据版本和分母。图表跨不可比边界断开实线，或用明确标识显示环境/功能/节点变更，不以平滑曲线暗示连续可比。

节点评审摘要建议固定为：本次范围和有效性；阻塞与新增风险；可比条件下的重要变化；不可比变化与原因；跨 tile 缺口；责任人/实验/截止条件；尚未被证实的结论。

## 12. AI 的工作边界与模型评估

建议分别测试两个内部服务在字段证据引用、条件识别、差异解释、候选归因与行动建议上的表现。模型、客户端和网关作为组合记录；不按名称预设谁更强。

LLM 不接管生产 run 的数值解析、单位换算、聚合、可比性和 pass/fail。适配器初建时可让 AI 辅助写代码，但该代码先有独立 goldens/异常测试再入生产。

每个请求只读取相关 tile、场景、基线、确定性差异、有效配置变化及有限路径切片。输出合同见配套操作文档。先核对引用和数字，再由专家评审有工程含义的结论。

能可靠说“数据不足以归因”是合格输出，不作为模型失败；编造根因、忽略缺失 corner、将 Top-N 未出现说成修复，是严重失败。

## 13. 性能、并发与成本

规模按实际对象计算，不按文件大小猜测：若 T 个 tile、N 个节点、每节点 R 轮、每轮 S 个分析场景，观察量约为 T×N×R×S；但综合作业数未必乘 S，取决于是否复用同网表。

例如纯规划样例 T=24、N=4、R=6、S=5，得 2,880 个场景观察；若每 tile/节点/轮只生成一份网表则为 576 个综合执行，不包括重试/额外实验。加入检查类型、路径组和明细后事实行数更大，应只将变化切片给模型。

每 key 并发 10 是请求上限，不是十个独立 EDA license，也不保证多模型各有十槽。初始可考虑 6—8 个全 key 范围请求槽，余量供交互与恢复；压测后再调整。模型请求、解析任务、EDA 作业与人工评审分别排队。模拟/综合等待期间不持续占用模型槽，也不频繁请求模型轮询。

原始文件、解析结果、比较结果采用内容/版本缓存，重复导入幂等，重解析不伪造新工具运行。历史节点冻结可避免每次重新总结全部报告。

## 14. 安全与治理

报告、路径、库名、时钟频率和面积都可能包含敏感信息；本公开仓库只保留方法、匿名示例和空白模板。内部填写后的模板、真实测试集和输出保存在获准内部系统。

权限过滤应在检索之前，并贯穿缓存、索引、日志与 AI 输出；模型不可回退公网。报告文本作为不可信数据，不能执行其中的命令。工具白名单、只读文件权限和外部网络限制在模型之外实现。

签核规则、SDC、例外、基线批准和风险接受由现有责任人管理。AI 无默认 merge、waiver、改约束或重跑预算权限。版本升级、parser 变更、规则变化都应有回归和回滚路径。

## 15. 交付范围与实施边界

完整方案包含对象与关系、元数据、预期矩阵、采集/解析、质量规则、可比性、基线、趋势/路径、SoC 汇总、跨 tile 预算、AI 证据包、每轮操作、异常恢复、测试、组织与收益测量。具体字段和验收见配套文件。

本次没有公司原始报告，因此不能提供已经适配具体综合工具的生产解析器，也没有执行 EDA 或内部 API 测试。首次实施应以现有已完成报告为输入，从代表性子集校准后扩展至全 SoC；样本试点的有限覆盖必须保留标识。
