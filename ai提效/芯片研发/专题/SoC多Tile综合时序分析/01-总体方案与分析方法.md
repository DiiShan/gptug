# 01｜总体方案：以报告分析为主线

> v2.0 · 2026-10-10｜[入口](README.md)。你交付代码，综合团队运行，你分析回包。运行环节保留，但不属于你的日常执行任务。

## 1. 目标与分工

每轮交付三类结果：**范围和缺口、可信的比较结果、带证据的行动项**。不以文档页数、模型回答长度或单一 WNS 排名衡量成果。

| 工作 | 负责人 | 交接物 |
|---|---|---|
| RTL/配置及变更说明 | 你 | 代码交付 ID、commit/内容标识、top/config、功能变化、已知问题 |
| 约束/库/宏/流程配置、资源调度 | **综合团队负责** | 实际生效环境摘要、版本/散列、批准要求；设计意图由你确认 |
| 综合、STA、检查与报告导出 | **综合团队负责** | run/analysis、状态、报告、来源和场景覆盖 |
| 解析、校验、比较和报告分析 | 你；脚本＋可选 AI | 事实表、限制、风险、假设和问题单 |
| 环境调查、补报、控制实验、重跑 | **综合团队负责** | 新执行/导出记录；不得改写旧回包 |
| 代码修复、验证、再交付 | 你；验证按原职责 | 新版本与验证证据；触发新的正式分析循环 |
| 跨 tile/顶层分析与签核 | **综合团队负责协调** | STA/集成/后端按原责任体系提供证据；你不拼接局部 slack 代替 |

默认接收已交付文件，不建设作业调度器、不直接登录 EDA 会话、不复制全部 PDK/库。需要的运行信息由综合团队提供摘要或可审计引用；缺失会限制结论，不会因换负责人而取消要求。

## 2. 分清对象

| 对象 | 含义 |
|---|---|
| IP/tile/config | 每 IP 一个独立综合 tile；参数、wrapper 不同分配置 |
| SoC instance | 一个 tile 设计可能被多次实例化；复用结果需明确适用配置 |
| milestone | 设计/验证里程碑，不是制程节点 |
| flow_stage | mapped、post-place、post-CTS、post-route 等工具阶段，与里程碑分开 |
| scenario/check | mode、PVT、RC、有效约束和分析方法；setup/hold 等检查分开 |
| iteration/run/analysis | 修改意图、实际执行、同网表某场景观察分别标识；重试有新 run |
| snapshot | 本次 SoC 评审明确选定的 tile/config/run/analysis 成员集合 |

各 tile 轮号可以不同。快照必须保留最新执行、最后有效值和正式选定值；最新失败不能被旧成功掩盖。补交数据生成新 revision，不覆盖已接受快照。

## 3. 保留的七类比较

| 目的 | 处理方式 | 不能得出的结论 |
|---|---|---|
| 同条件 RTL 迭代 | 固定功能合同与相关环境，允许 RTL 改变 | 单凭 PPA 变化证明功能等价或唯一根因 |
| 条件变化 | 列出库、SDC、周期、边界、工具和流程差 | 全部改善都由 RTL 造成 |
| 跨设计验证节点 | 功能/要求变化、共同场景趋势、新增缺口分表 | 功能补齐导致面积增加就是退步 |
| 跨 corner/mode | 分场景观察和最差场景标识 | 场景差是迭代收益；平均 slack 证明安全 |
| 跨工具阶段 | 分阶段或做校准分析 | 综合估计等于 post-route 签核 |
| 同条件重复运行 | 固定输入与环境，记录线程/seed 等适用变量 | 选择最好一次当典型结果 |
| 跨 tile/SoC 组合 | 按各自要求和明确快照统计覆盖/阻塞 | tile 内部通过等于全芯片通过 |

基线保留固定、滚动、节点、实验四类。每个比较写明 base/head；禁止看见结果后挑最有利基线。具体数值、状态和判定顺序见[02](02-数据契约与比较规则.md)，字段级任务见[06](06-流程分阶段实施明细表.md)。

## 4. 分析步骤

**接收回包 → 身份/完整性检查 → 固定解析 → 条件审查 → 数值与对象差异 → 节点/SoC 快照 → 可选 AI 解释 → 人工反馈。**

路径按起终点、clock/edge、check、scope 和映射版本追踪；rename/flatten/retiming 后无法精确匹配就标未映射。Top-N 消失只代表样本未观察，不自动关闭问题。

根因记录分为已观察事实、候选假设、控制实验支持、负责人确认。需要桥接时，可请求旧/新设计 × 旧/新环境的对照，交互项为 Q11−Q10−Q01＋Q00；先确认四种组合合法。**实验运行和预算由综合团队负责**；没有对照时保留混杂，不强行唯一归因。

## 5. SoC 汇总与独立综合边界

| 内容 | 正确展示 |
|---|---|
| 覆盖 | 从批准的必需集合出发，分别统计执行、数据、可比、达标状态；保留失败/缺失/过期 |
| 面积 | 区分 stdcell/macro/core/die、inclusive/exclusive；同网表多场景不重复加；实例按批准归属计算 |
| Setup/Hold | 按 tile/scenario/check 展示；观察范围内最差值注明“局部”；不相加或平均 slack 冒充全局 STA |
| TNS/端点 | 默认分场景；合并必须有不重复的对象与一致统计口径 |
| 运行资源 | 按真实 run 去重；由综合团队提供，不按报告份数累加 |
| 功耗/物理 | 仅在活动、场景、模型和阶段适用时比较；首版可不启用但保留字段 |
| tile 边界 | 保留 wrapper、tie-off、stub、I/O delay/load/transition、时钟参考与预算版本 |
| 跨 tile | 维护端口位、预算、模型版本及顶层证据缺口；不能相加任意 I/O delay 或两端 slack |

综合团队负责提供生效边界和模型信息；你负责确认 RTL 功能/接口意图。跨 tile 预算需统一参考边和计时约定，真实集成检查仍由对应专业流程执行。

## 6. 起步与范围

先做一个 tile、两轮已完成报告，再覆盖代表性 tile、多个真实节点、必需场景和失败样例。首次只需目录、JSON/CSV、受测解析程序和事实报告；数据库、看板、多代理和运行时 LLM 均按收益决定。

先复用综合团队已有 QoR 导出和脚本。你只建设接收、分析、反馈部分；对方自动采集能力不足时可提出接口需求，不把其平台改造列成你的必做前置条件。具体操作和验收见[03](03-实施操作与验收评估.md)。

公开工程背景参考沿用旧版：OpenSTA 输入与分析说明、ORFS 配置和 Metrics、PrimeTime 层次/多场景资料；不以这些公开实现冒充公司工具命令。本次仅修订方法与职责，未重新测试公司工具。
