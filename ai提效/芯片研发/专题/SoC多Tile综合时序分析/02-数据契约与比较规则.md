# 数据契约、指标语义、可比性和聚合规则

> v1.0｜2026-10-05｜配套[总体方案](01-总体方案与分析方法.md)。  
> 本文件是待内部实现的数据契约，不是已经运行的 schema validator 或 EDA 适配器。示例全部虚构；字段填入真实数据后只存获准内部系统。  
> 新结构建议用 `soc-qor/2.0` 标识，以区别旧 05/06 的简化 IP/run 模型。旧数据先迁移或显式标记未知，不能猜补节点、tile、corner。

## 1. 对象关系与事实粒度

不能把所有东西塞进一张“IP＋轮次＋WNS”表。建议定义以下逻辑对象，首版可用分文件 JSON/CSV 表达，并非要求建立同样数量的数据库服务。

| 对象 | 主键/关系 | 保存什么 |
|---|---|---|
| project | project_id | 工艺、权限分类、SoC 版本、责任人 |
| milestone | milestone_id＋revision | 节点目标、顺序/前驱、批准验收要求、功能基准 |
| tile_design | tile_id＋config_id＋revision | IP、top、wrapper、参数/宏、功能范围、边界预算 |
| soc_instance | soc_revision＋instance_id | 实例路径到 tile 配置的映射、数量与面积归属 |
| scenario | scenario_id＋revision | mode、PVT、RC、时钟/例外、分析方法、适用检查 |
| requirement | requirement_id＋revision | 某节点某 tile/config/stage 必需哪些场景、检查、产物 |
| iteration | iteration_id | 一次有明确目的的改动及关联需求/问题 |
| execution | run_id | 一次实际工具执行；每次 retry 新 run_id，并指回 retry_of |
| artifact | artifact_id 或内容散列 | 原始文件、格式、大小、内容 hash、完成状态和权限 |
| analysis | analysis_id | 某网表/数据库在某阶段与场景下的真实分析观察 |
| metric_fact | metric_id | 单个指标的值、单位、语义、范围、状态和证据 |
| path_observation | path_observation_id | 路径点、时钟/边沿、slack、分量、采样策略和来源 |
| snapshot | snapshot_id＋revision | 一个节点/截止时间下批准选择的精确成员集合 |
| comparison | comparison_id | base/head、目的、规则、条件差、指标差与可比性 |
| finding | finding_id | 风险/问题、观测、假设、实验、责任人和关闭证据 |
| review | review_id | 谁以哪个输入/规则版本审查什么，结论和时间 |

execution、analysis 不是一一对应：一次工具会话可以分析多个场景；一次 STA 作业也可以复用另一综合作业产生的网表。analysis 同时记录 `producer_run_id` 和 `design_source_run_id`，不因报告重新导出就声称重新综合。

每次执行保留尝试序号和失败原因；run_id 全局唯一且不可被后续重试覆盖。iteration_id、用户展示的 round_label 可以相同，但不能替代 run_id。

## 2. 项目与 tile 注册信息

### 2.1 tile_design

必填：ip_id、tile_id、config_id、top_module、wrapper_revision、functional_contract_revision、实际参数/宏/include/filelist、生成文件版本、接口清单、时钟/电源域、owner、边界预算版本、面积归属策略。

宏/存储明确区分真实实现、带合法时序/面积模型的宏、批准 stub、意外 unresolved blackbox。设置 `model_status` 而不是单个黑盒数量。不同里程碑可以批准不同状态，但批准 stub 也不等于完整 PPA 范围。

软件可见配置、功能使能与 SoC 实例绑定必须显式保存。若同 IP 多实例共用综合结果，记录复用理由及作用范围；不要仅因名字相同就复用。

### 2.2 边界契约

每个接口记录 source/destination instance、端口位映射、协议/同步类别、launch/capture clock 及参考边、mode/corner 适用集合、I/O budgets、transition/load、互连假设、例外、owner 与批准记录。

跨 tile budget 只能在统一参考和计时约定下核对。保留符号、min/max、rise/fall、additive/absolute 的原始语义，不能将任意 delay 数相加后称为预算守恒。

## 3. 里程碑要求矩阵：缺失的分母来自这里

一个 requirement 行的粒度可为：

```text
project/milestone_revision + tile/config + flow_stage
+ scenario/check（指标为设计级时可不适用）+ report_category
```

必需字段：required/optional/not_applicable、适用理由、批准人、目标/阈值版本、有效起止节点、期望数据年龄、是否允许沿用、接受的模型成熟度、验证成熟度门槛。

状态由此矩阵与实际结果左连接产生，而不是从磁盘上找到什么就统计什么。缺失、失败、过期结果保留在分母；不适用需要批准和理由。

面积通常是设计/网表级事实，不要为了每个 corner 建重复面积事实；如果各 corner 分别优化生成不同网表，则每份网表有自己的面积。指标语义决定是否具有 scenario 维度。

矩阵可以限定合法组合，不生成 mode×corner×check 的无意义笛卡尔积。功能模式与 scan 模式、setup 与 hold 的场景要求由 STA 负责人定义；不硬编码“SS 只看 setup、FF 只看 hold”的通用规则。

## 4. run manifest 的必填信息

| 字段组 | 字段要求 | 必须防止的错误 |
|---|---|---|
| 身份 | project、tile/config、iteration、run、retry_of、milestone 引用 | 用轮号覆盖失败执行 |
| 生命周期 | job_id、submitted/started/ended_at、时区、exit_code、execution_status | 有文件就当完成；把排队算人工 |
| 设计输入 | RTL commit、dirty patch hash、内容级输入 digest、filelist 顺序、include/宏/参数、生成器 | 同 commit 实际用了不同生成文件或环境 |
| 产物链 | 输入网表/数据库 hash、输出 hash、source_run、analysis IDs | 旧网表配新标签、不同网表场景混在一起 |
| 工艺/库 | process、PDK release、library/macro 实际文件 hash、VT、dont_use、单位定义 | 同工艺即同库、仅保存库目录名字 |
| 工具 | synthesis/STA 名称、版本/build、脚本和执行选项 | 只记录客户端或 shell 命令标签 |
| recipe | 全量/增量、优化目标、允许变换、物理上下文、seed（适用时） | recipe 变化被归因为 RTL |
| 约束 | 顶层及依赖 SDC hash、source 顺序、变量展开、生效时钟/I/O/例外快照 | 文件相同但环境变量或作用对象改变 |
| 资源 | wall time、CPU time、内存、license 等待、退出/取消原因 | 多分析场景重复计同一作业资源 |
| 质量 | functional scope、意外黑盒、约束/端点覆盖、日志严重错误 | 退出码零当作结果可发布 |
| 权限 | 数据分类、访问控制标签、保留策略 | 指标/路径被当作无敏感信息 |

时间戳保存 ISO 8601 与时区；运行顺序主要依赖显式 lineage/sequence，不只依赖 mtime。

## 5. 场景和报告契约

### 5.1 scenario

保存 mode/case analysis、工艺库集合、温度、电压（多电压域需映射而非单值）、RC corner、寄生数据 hash/来源、时钟传播状态、uncertainty/latency、OCV/AOCV/POCV/derate、CRPR、SI、GBA/PBA、适用检查。

同一个 `ss` 名称若库、电压、温度或 RC 不同，应生成新的 scenario revision。上下文 hash 基于实际有效值，不基于人类标签。未启用、确实不适用和不知道是不同状态。

### 5.2 report recipe

每个报告保存工具命令/选项或其可审计引用、check/path group、start/end/through/filter、min/max、rise/fall、每端点路径数、每组路径数、Top-N、slack threshold、精度、单位、是否完整、是否截断。

优先采用工具原生结构化数据或稳定 API。文本解析必须按工具家族、版本和报告类型分适配器；未知格式隔离，不悄悄尝试“最像的”正则。

adapter 输出字段覆盖率、未识别段落、告警、版本和来源。不让 LLM 在运行时把无法解析字段猜成数值。AI 辅助开发 parser 的代码也必须经过人工和自动测试。

## 6. 字段级 provenance 与无值语义

每个事实至少有：原始值/单位、规范值/单位、metric_semantics_version、object_scope、scenario/check（适用时）、quality_status、evidence_refs、parser_version、transform_version。

证据引用：artifact_id、content_sha256、原始行区间或结构化 json_pointer、提取方法。报告截取后仍保留到完整原文件的位置；不能把 AI 摘要作为原始证据。

数值状态至少区分：`observed`、`missing`、`not_applicable`、`parse_error`、`unsupported`、`truncated`、`conflict`。无值用 null 加原因，不用 0、空字符串或 -999 代替。

同一规范键出现不一致事实时记录冲突。明确权威数据源优先级和审查规则，不能按最后导入的一份覆盖。允许相同内容幂等去重，保留所有来源引用。

## 7. 指标公式与方向

### 7.1 时序

在同一范围、check、场景下，取每个合法端点的最差适用 slack 为 s_e。规范化：

```text
worst_slack = min(s_e)，要求端点集合非空、范围已知
wns = min(0, worst_slack)
tns = Σ_e min(0, s_e)
violating_endpoint_count = count(s_e < 0)
```

工具原始 TNS、WNS 和违例计数仍保存。若工具按不同 scope/去重/边沿口径统计，不能强行转换而不验证。端点是 pin、bit、边沿还是其他对象，写入 `endpoint_identity_policy`。

setup 与 hold 分开；recovery/removal、clock gating、pulse width 等按独立检查存储，不混入 setup/hold 总量。只提供 Top-N 明细时，不从明细“重算全设计 TNS”。

`delta_slack = current - baseline`，数值大通常代表该已定义检查的余量改善，但 pass/fail 仍取决于目标、完整性和其他检查。WNS 从 0 到 0 不代表没有余量变化，应同时保留正 worst_slack。

slack 不用常规百分比表达优化；对于正且有意义的面积/计数基线，`delta_pct=100*(current-baseline)/baseline`。基线为 0 时百分比留空，另记新增；负数基线不用这一公式生成夸大或反向结论。

### 7.2 面积、单元与资源

面积单位必须由工具/库定义确认，未确认时不能擅自标 μm²。保持标准单元面积、宏面积、core/die 面积分离；父层级 inclusive 与子层级不得重复相加。若单元类别重叠，记录 membership，不能假设 comb＋buffer＋inverter 互斥。

同一网表在多个场景下重复出现的面积只是引用，不应新增一份可累加实体。资源以真实 run 为单位去重；一个作业输出十份报告仍是一个作业消耗。

### 7.3 精度与容差

保存未舍入的可得值、原始展示精度和转换过程。数值量纲检查优先于计算。浮点 NaN/Inf 不直接进入数据库或图表。计数不许负数；单位变换与千位分隔/科学计数法有独立测试。

展示舍入、解析允许误差、业务告警容差是三件事。不可将舍入误差用来掩盖门槛越界；容差由 STA/项目负责人按指标与场景批准，不提供跨工艺通用的固定 ps 门槛。

## 8. 状态分轴，不用单一红绿灯

| 状态轴 | 示例状态 |
|---|---|
| 执行 | queued/running/succeeded/failed/cancelled/timeout |
| 数据 | complete/partial/invalid/unknown |
| 要求覆盖 | complete/incomplete/not_applicable_approved |
| 可比性 | comparable/conditional/not_comparable/insufficient_evidence |
| QoR | pass/fail/unknown/not_applicable_approved |
| 功能/验证资格 | qualified/pending/failed/unknown |
| 评审 | unreviewed/accepted/rejected/accepted_with_open_items |

这些状态不自动互相推出。`succeeded`＋`complete` 可以仍是 QoR fail；QoR pass 可以仍是验证 pending；获准发布报告也可以发布失败事实而不是宣布设计通过。

SoC 门禁至少区分“事实报告可发布”“当前里程碑可接受”“功能验证合格”“时序签核完成”。每一种都需要具体规则和责任人，不共享一个万能 PASS。

## 9. SoC snapshot 契约

每个快照记录节点、要求矩阵版本、截止时间、选择策略、批准状态和成员数组。每个成员必须明确 tile/config、instance 集合、flow_stage、selected_run、各必需 scenario/check 的 analysis、缺失/失败项、沿用来源与年龄、审批。

不得混合不同设计网表的场景并伪装为同一轮完整分析；若真实工程决策允许混合修订，则整份快照标为 mixed-revision，并对各成员和受影响接口列明限制，不能称一致性冻结版本。

snapshot hash 随成员变化而变化。补报、late arrival、重新审批或修改要求均生成新 revision；旧快照保留可重建。动态看板与批准快照分开。

### 9.1 覆盖统计

定义必需集合 R 与当前满足条件的集合 V：有效覆盖 `|R∩V|/|R|`。R 为空时标“不适用/未配置”，不能显示 100%。执行率、数据有效率、可比率、通过率分别使用明确集合，不混用分母。

同时给 tile 粒度：某 tile 只有全部必需项满足相应门槛才计为该轴的完整。面积加权覆盖、关键性加权风险可作为附加视图，但不能隐藏缺失的关键 tile；权重与政策版本可追溯。

## 10. 比较合同与判定次序

### 10.1 每个 comparison 都先声明目的

字段至少包括 comparison_type、base/head 的 run/analysis/snapshot、metric_scope、hypothesis、controlled_fields、allowed_changes、forbidden_changes、unknowns、rules_version、批准例外。

**不要要求 RTL hash 必须相同才可做设计迭代比较。** RTL 本来可能是待测变量；它应在 allowed_changes 中，同时控制分析条件与功能契约。相反做工具重复性试验时，RTL/输入 hash 必须相同。

功能范围改变的两版 RTL 即使同 corner 同工具，也不能默认按同功能的 PPA 优化解释；可转为成熟度/能力变化比较，或由项目明确批准新的比较目的。

### 10.2 按指标的条件矩阵

| 变化 | 面积差异 | setup/hold 差异 | 默认解释 |
|---|---|---|---|
| 仅 RTL 改变、功能合同固定、环境一致 | 可比观察 | 同场景可比观察 | 是否等价、因果仍需验证 |
| 网表不变，仅 STA corner 改变 | 同面积引用，不重复计 | 场景敏感性 | 非迭代优化 |
| 综合优化 corner/recipe 改变并产生新网表 | 条件变化比较 | 条件变化比较 | 不能归因于 RTL |
| SDC/实际频率/边界预算改变 | 若重新综合则环境混杂 | 环境混杂 | 需要桥接或明确不可归因 |
| 多一组必需 corner | 已定义设计面积可保留 | 共同场景单独比较，新场景单独列风险 | 不隐去扩大覆盖 |
| M0→M1 且功能补齐 | 成熟度对比 | 同条件部分可观察，整体非同功能比较 | 不把面积增加直接判回退 |
| mapped→post-route | 不同阶段口径 | 不同阶段/寄生/时钟 | 校准，不当作普通回归 |
| parser 或报告格式变化 | 两侧同版重解析后判定 | 同左 | 不直接沿用旧差异 |
| 范围/单位/来源缺失 | 受影响指标不算 | 受影响指标不算 | insufficient_evidence |

### 10.3 建议判定顺序

先检查产物身份/完整性；再检查 metric 语义/范围/单位；再解析比较目的与允许变量；再逐字段判断条件；最后才计算可计算的差异和门槛。不能先算出改善百分比，再用脚注补“不一定可比”。

原因码建议：MISSING_METADATA、SCENARIO_MISMATCH、FUNCTIONAL_SCOPE_CHANGED、BOUNDARY_CHANGED、SDC_EFFECT_CHANGED、TOOL_CHANGED、LIBRARY_CHANGED、STAGE_CHANGED、REPORT_SCOPE_CHANGED、TRUNCATED、PARSER_MISMATCH、BASELINE_MISSING、SNAPSHOT_MIXED 等。它们为本方案内部约定，不声称是 EDA 标准错误码。

## 11. 基线选择及去偏

固定基线由人批准；滚动基线从当前任务的合法可比候选中选时间/lineage 最近者；节点基线取明确批准快照；实验基线取实验卡指定对照。失败和取消仍在运行历史中展示。

预先指定策略，不能在看到结果后挑最好/最坏一轮制造收益。基线记录可以被新版本取代，但历史比较不会原地改变。需要更新 parser/rules 时，生成新的 comparison revision 并保留旧结果。

对于不连续场景集合，建立 matched cohort（共同合法集合）用于趋势，同时显示全量当前要求矩阵；不能把交集的良好趋势当成新全集的门禁通过。

## 12. 路径和问题身份

path_observation 保存 analysis、check、path_group、start/end pin、clock/edge、raw names、canonical names、映射版本、slack、arrival/required、已报告的 data/clock 分量、source refs、Top-N policy。

同端点不同 launch clock 或不同例外适用条件不能盲目合并。path family 用于讨论相近逻辑族，可基于层级、时钟对、端点族、mux/arithmetic/跨界结构形成，但不能替代精确路径证据。

无法映射时标 unmapped；模糊映射标候选且保留原名。重命名去数字、去层级等规范化可能误合并不同逻辑，不作为唯一主键。

Top-N 消失＝未在样本观察到。关闭一个 finding 的条件由适用场景全集、定向证据、验证与责任人确认决定；不能由路径排名消失触发自动关闭。

## 13. 汇总不变量

采用以下不变量作为自动化测试和发布检查：

1. 同一个网表面积不因增加分析 corner 而变成两倍。
2. 新增一个缺失的必需场景，不得提高完整性或通过率。
3. 最新 run 失败时，页面必须展示失败；历史有效结果有明确沿用标记。
4. 未知单位不能产生归一后的物理数值。
5. 缺失 hold 报告不能让 setup pass 升格为 timing pass。
6. Top-N 变小不能自动减少“已确认未关闭问题”的数量。
7. 父子 inclusive 面积和同一端点跨场景数据不能被无条件相加。
8. 分别综合的局部 slack 汇总不能被标成全 SoC STA。
9. 同一输入、parser、规则、基线和成员清单应重建同一确定性结果；LLM 叙述变化不改变数值和门禁。
10. 模型拒绝/超时不能删除原始事实、覆盖缺口或规则告警。

## 14. 示例：跨节点趋势为什么必须分开

以下数字均为虚构的说明样例，单位 ns，假设已确认工具语义：

| tile | 节点/轮次 | 场景 | worst_slack | 情况 |
|---|---|---|---:|---|
| Tile_A | M1/R1 | SLOW_SETUP_v1 | -0.080 | 已批准基线 |
| Tile_A | M1/R2 | SLOW_SETUP_v1 | -0.050 | 环境/功能范围不变 |
| Tile_A | M2/R1 | SLOW_SETUP_v2 | +0.010 | 目标周期放宽，功能范围也增加 |
| Tile_A | M2/R1 | FAST_HOLD_v1 | null | 本节点必需，但报告缺失 |

允许的结论：M1/R2 相对 M1/R1 的同条件 worst_slack 增加 0.030 ns，仍为负。M2/R1 的 setup 值可以展示，但由于目标周期/功能范围变化，不能叫同条件再优化 0.060 ns；当前节点又缺少 hold，不能宣布 timing pass。

再如 Tile_B 最新运行失败，但上次有效数据是 M1：快照显示失败＋M1 历史参考；不是把 M1 文件复制进 M2 目录后视为完成。

## 15. 模板及迁移

[配置模板](配置模板.json)提供未批准的空白项目、节点、tile、场景、快照和比较配置结构。它不是公司配置，也不是可运行验证程序；空白必填项必须阻止正式入库/发布。

旧 05/06 表单可以保留做采集辅助，但迁移时新增 milestone_revision、tile/config/wrapper、scenario_revision、analysis/source_run、expected requirements、snapshot members、metric provenance。无法查证的字段标未知并阻断相应比较；不得依据文件名猜补以满足 schema。

原始文件永远不改写。重新解析保留新 parser 版本和派生数据版本；问题 ID 与证据指向应可跟踪变化。必要时双轨跑新旧规则并人工解释差异后再切换。
