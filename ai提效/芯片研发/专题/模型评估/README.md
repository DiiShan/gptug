## 1. 评估目标：交付可用边界，而不是总分冠军

评估必须回答：什么任务交给哪一款部署服务、通过哪个客户端、使用多大上下文和什么推理配置、允许多少并发、超时及失败后如何处理，以及到底节省多少人工。

|---|---|---|---|---|---:|---|---|---|---|---|
| 规格/接口/寄存器整理 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待定 |
| 局部 RTL 修改 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待定 |
| 验证协助与故障定位 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待定 |
| 综合/后端协助 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待定 |
| 硅后只读分析 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待定 |

不将速度、正确性、安全和人工收益简单相加：严重风险先否决；其余在相同验收质量下比较成本、延迟和收益。

### 1.1 四层评估，分开归因

| 层级 | 被测对象 | 主要问题 | 对照方式 |
|---|---|---|---|
| L0 服务与协议 | 直接 API、网关、部署 | 支持什么？多快？容量和限制是什么？ | 两服务用统一轻量测试器，不经过编码代理 |
| L1 部署后的模型能力 | 固定输入、提示和预算下的输出 | 是否理解、推理、遵循约束并如实回答？ | 两服务使用同一任务与统一工具封装 |
| L2 实际工作流 | 模型＋客户端＋上下文管理＋工具 | 能否完成多轮、跨文件、可验收的工程任务？ | 两服务×三个客户端，先检查兼容再比较效果 |
| L3 生产力 | 工程师＋完整工作流 | 是否降低总人工投入和返工，而非只加快生成？ | 原工具、补强脚本、脚本＋模型三组比较 |

这里的 L1 仍是“部署后的服务能力”，不是脱离量化、推理实现和系统提示的纯权重能力。无法访问底层时，不声称已经隔离这些因素。

## 2. 必须考虑的因素，以及如何评估

优先级 P0 表示首轮必须具备记录或检查；P1 表示进入真实工作试点前完成；P2 表示按任务需要扩展。

| 因素 | 优先级 | 评估方法 | 关键输出/指标 |
|---|---|---|---|
| 身份与可复现配置 | P0 | 平台登记、模型 ID、部署版本交叉核对；不采信模型自我介绍 | 版本、量化、框架、tokenizer、参数与配置散列；未知项明确留空 |
| 协议与功能兼容 | P0 | 流式、usage、JSON、工具往返、错误返回、取消等合同测试 | 功能通过/降级/不支持/未测；协议失败率 |
| 并发配额与实际容量 | P0 | 单服务阶梯并发、两服务混跑、突发、长短混合、恢复测试 | 配额作用域、有效并发、最大合格吞吐、推荐调度上限 |
| 首响应和尾延迟 | P0 | 逐请求记录时间戳，区分首内容、首答案、完整结果 | p50/p90/p95、超时率、首答案前静默时长 |
| 生成速度与吞吐 | P0 | 固定长度负载和同任务负载分别测 | 单请求 tokens/s、总吞吐、达标请求/s、验收任务/小时 |
| 上下文容量与有效性 | P0 | 长度×位置×任务复杂度；单轮与多轮/压缩分开 | 接受上限、任务质量上限、工作流可用上限 |
| 幻觉与证据忠实性 | P0 | 充分、缺失、冲突、错误前提、数值、工具失败题组 | 错误事实率、无依据断言率、关键字段错误、虚构执行次数 |
| 不确定性与回答覆盖 | P0 | 可回答与不可回答样本分开评估 | 有依据回答率、合理弃答率、过度弃答率、选择性错误率 |
| 任务理解与约束遵循 | P0 | 给定允许/禁止修改范围；中途更新需求和版本 | 需求覆盖、越界修改、目标漂移、遗漏约束 |
| RTL/脚本专业能力 | P1 | 编译、仿真、形式/等价及独立参考检查；跨配置测试 | 首次验收率、预算内验收率、引入回归、补丁范围 |
| 分析与调试能力 | P1 | 已关闭问题回放；根因与证据分离；检查最小区分实验 | 根因候选准确性、遗漏、误报、确认根因所需实验成本 |
| 工具使用与错误恢复 | P0/P1 | 返回乱序、文件缺失、非零退出、超时、过期结果、补丁失败 | 参数合法率、工具链验收率、重复副作用、恢复成本 |
| 稳定性与复测一致性 | P1 | 相同任务独立新会话重复；不同负载、日期、实例重复 | 语义验收稳定率、质量波动、服务错误、版本漂移 |
| 数据、权限及安全 | P0 | 合成标记、提示注入、只读边界和网络出口检查 | 未授权读写/外传、凭证暴露、跨会话信息串用 |
| 成本与人工生产力 | P1 | 记录准备、交互、评审、修改、失败接管、维护 | 每验收任务人工分钟/成本、总净节省、EDA/license 开销 |
| 图像及复杂输入 | P2 | 按需求测框图、表格、波形截图，并与文本导出对照 | 字段识别与推理准确性、图像 token/延迟；不默认支持 |

## 3. 测试前冻结的条件

### 3.1 两份部署信息卡

向平台团队确认：上游模型及发布日期、部署 revision、量化精度、推理框架与版本、硬件/副本、实际上下文和最大输出、思考预算与计费口径、API 协议、参数透传、流式语义、缓存策略、限流作用域、RPM/TPM、排队、超时和取消、日志与遥测、外部回退、服务变更通知。

只有 API key 时仍可做黑盒测试，但服务端排队、prefill、decode、KV cache 使用和内部路由只能列为不可观测。首 token 时间不能直接当作 GPU 推理时间。[S1][S3]

### 3.2 公平比较原则

固定任务输入、文件/规格/工具版本、系统规则、允许的工具、输出合同、初始工作区和验收规则；提示开发与封存测试分离。每次独立测试使用干净会话与独立工作区，不让另一模型的答案进入上下文。

比较分两条线：

**容量线：**用各自正确 tokenizer 构造相近 token 长度，隔离输入长度、输出长度和缓存等负载因素。该线只描述服务性能，不用合成填充题宣称专业能力。

**工作线：**给两模型完全相同的业务资料与任务，记录各自实际 token 数；这是业务公平，而不要求两套 tokenizer 得到相同 token 数。统一 wall-clock、人工干预、工具调用等预算；token 预算只作辅助，因为分词和推理 token 口径可能不同。

把默认模式和经过开发集调优的模式分别报告。思考开关/强度只测试平台确认支持的取值；不默认为 temperature=0 可用，也不默认为相同参数值代表相同推理强度。

### 3.3 初始标准负载

下表是待平台确认的起始档位，不是对实际最大上下文的断言。K＝1,024；均记录实际 input/output tokens 与完成原因。

| 负载 | 输入目标 | 可见输出目标 | 代表性材料 | 主要测什么 |
|---|---:|---:|---|---|
| P0 短交互 | 2K | 256 | 规格字段、单接口、简短错误 | 首答案、频繁交互、短请求公平性 |
| P1 常规代码 | 8K | 1K | 局部 RTL＋说明＋相关文件 | 解码、补丁生成、多轮调用基线 |
| P2 跨文件分析 | 32K | 1K | package/模块/配置、规格与日志 | 长输入等待、证据整合、混合负载 |
| P3 长上下文扩展 | 64K/128K，按支持范围 | 2K | 多文件多版本资料 | 长度退化、内存压力、尾延迟 |

输出“目标”不等于 `max_tokens` 一定会被用满。服务容量实验可采用受控生成长度；如使用忽略 EOS 等特殊选项，只能用于获准的容量实验并单独标记，不能用于业务质量结果。工作线保留自然终止，并统计超长、提前结束和截断。

每档分别标记进程/连接冷暖与前缀缓存命中状态；“做过预热”不等于“缓存命中”。容量线使用不同前缀和确认的缓存条件；工作线使用实际复用比例。无服务侧证据时写“缓存状态未知”，不能把任意字符串后缀当作可靠清缓存。

## 4. 速度与延迟：统一测量口径

NVIDIA 的性能工具将首 token、逐 token/逐 chunk 间隔、请求时延和吞吐分开统计；AIPerf 还区分首个非推理输出。应沿用分层思路，并为工程任务增加验收时间。[S1][S2]

### 4.1 逐请求、逐任务事件

| 事件 | 解释 |
|---|---|
| `scheduled_at` | 用户提交或负载发生器计划到达时刻，早于客户端限流队列 |
| `sent_at` | 请求实际发出；本地连接池等待单独记录 |
| `first_content_at` | 首个非空内容事件；可能是显式推理输出，不能是 heartbeat/空包 |
| `first_answer_at` | 首个非推理答案内容；没有该渠道则标记不可观测 |
| `first_valid_tool_call_at` | 首个参数完整且经 schema 验证的工具调用，不能拿半截参数算可用动作 |
| `response_done_at` | 完整响应终止，记录 finish reason、usage 和状态 |
| `task_accepted_at` | 全任务经独立检查与人工验收通过；未通过则为空并记录失败/超时 |

同一客户端内时差使用单调时钟。跨客户端/服务端事件使用同步时钟或 trace；未同步时不要直接相减。保留 request ID 与 task ID 关联。

### 4.2 指标定义

| 指标 | 本计划定义 | 使用注意 |
|---|---|---|
| 客户端排队 | `sent − scheduled` | 必须统计，避免把负载积压隐藏在压测器里 |
| TTFT | `first_content − sent` | 不把 HTTP 头、空事件或心跳当首 token |
| 首答案时间 TTFO | `first_answer − sent` | 推理内容早出现不代表答案早出现 |
| 用户首答案等待 | `first_answer − scheduled` | 包含本地排队，作为交互体验指标 |
| 请求时延 E2E | `response_done − sent` | 包含网络、服务排队和生成；与纯推理耗时不同 |
| 用户完整等待 | `response_done − scheduled` | 不遗漏连接/限流等待 |
| 解码阶段 TPOT | 同口径解码时间÷后续 token 数 | 仅在时间与 token 范围一致时计算；首 chunk 可能不止 1 token |
| 单请求生成速度 | 同口径后续 token 数÷解码时间 | 推理与可见答案分开；usage 缺失时不编造 |
| 系统吞吐 | 明确观察窗口内完成请求数或输出 token 数÷窗口时间 | 输入、输出和推理吞吐不混加冒充可见输出速度 |
| 服务 goodput | 同时满足预设服务 SLO 的有效完成请求数÷窗口时间 | 常规压测工具的 goodput 通常不验证工程正确性 |
| **工程合格吞吐** | **在任务时限和预算内通过验收的任务数÷完整观察时间** | 本计划增加的业务指标；含失败耗用的时间与资源 |
| 人工生产力 | 验收任务数÷实际投入人工小时 | 不把 agent 等待时间自动当作节省人工 |

如果只有 SSE chunk 的时刻，没有准确逐 token 事件，就报告逐 chunk 间隔和估计 TPOT，不能宣称测得真实逐 token 抖动。不要把隐藏推理 token 除以可见答案阶段时间。非流式只测完整时延，不从总时间倒推出真实 TTFT。

至少报告 p50、p90、p95、样本数、失败/超时数、最大静默间隔。p50 是中位数；p95 是约 95% 观测不超过的值。p99 需要更多尾部样本，不能用几十次调用形成服务承诺。不同负载和推理模式分别统计，不把长短请求混成一个无法解释的平均值。

两种吞吐口径可并存：固定请求批次用首发至最后终止；稳态压测用明确的稳态窗口，说明边界请求处理方式。超时/取消/未完成请求保留在总分母和 SLO 失败中；它们缺少完整时延时标记为截尾数据，而不是当作快速结束或从成功率中消失。

### 4.3 速度不能脱离输出量和质量

虚构算例：A 以 100 tokens/s 生成 2,000 tokens，纯生成耗时 20 秒；B 以 40 tokens/s 生成 400 tokens，纯生成耗时 10 秒。只看 tokens/s 会判断 A 快，但短而正确的 B 可能更早完成任务。真实比较还须加上首答案等待、工具轮数、验收和人工修正。

## 5. 并发专项：每 key 并发 10 应怎样测试

### 5.1 先查清“10”约束什么

分别确认是每 key、用户、租户、模型还是全服务限制；两模型是否共享；流式输出期间是否一直占槽；在队列等待是否占槽；取消/断连后槽位何时释放；是否另外限制 RPM、TPM 和总活跃 token；网关是否按会话而非单请求计数。

同时分清三种并行：API 请求并发、agent/任务并发、EDA 作业并发。一个 agent 可以串行多次请求，也可以启动子 agent；不能把它们等同。真实 GPU tensor/pipeline parallel 等是部署参数，不是 API key 并发。

### 5.2 测试矩阵

| 测试 | 方法 | 观察与结论 |
|---|---|---|
| 单模型阶梯 | P0/P1/P2 分别测 C＝1、2、4、6、8、10 | 吞吐何时不再增加；TTFO/p95、超时和质量何时恶化 |
| 两模型混跑 | 同 key 总数不超过 10，测 (10,0)、(0,10)、(5,5)、(8,2)、(2,8) | 查共享配额及竞争；不能仅凭不干扰证明资源独立 |
| 长短混合 | 在相同总 C 下变换短/长请求比例，并与短请求独跑比较 | 长请求是否使短请求饥饿；是否需要不同队列/配额 |
| 突发与平稳 | 授权上限内的瞬时到达，对照相同平均速率的均匀到达 | 突发排队、拒绝、重试放大和恢复 |
| 到达率扫描 | 根据初测容量设约 25%/50%/75%/90%/100% 的计划到达率 | 记录 offered rate、实际发送率、积压和丢弃 |
| 取消与故障恢复 | 获准的取消/超时/429/5xx 故障注入或 mock | 不无限重试；不重复提交有副作用工具；槽位恢复 |
| 长时间稳定性 | 在候选生产负载下持续运行，并跨正常繁忙/空闲窗口复测 | 漂移、缓存/内存问题、尾延迟与其他租户干扰 |

**所有测试需平台批准；在没有额外授权时，不发第 11 个同时在途请求，不轮换 key 绕过限制。** 多 key/跨用户共享资源试验只有在管理员许可和明确租户总上限后才做。故障注入尽量在 mock 或隔离测试环境，不伤害生产使用。

### 5.3 两种负载模式缺一不可

**固定并发闭环：**C 个请求进行中，结束一个补一个，用于寻找容量转折点。

**计划到达率测试：**任务按固定间隔或随机到达，在总并发限制下进入队列，用于观察实际交互等待。到达率超过发送能力时，不能把积压后的实际发送率冒充原计划负载，也不能只从 `sent_at` 开始计算用户体验。vLLM 和 AIPerf 都将请求速率与最大并发分开控制；选用工具时要核查它如何处理这段等待。[S4][S5]

计划到达率测试仍受授权并发硬上限约束；有界队列溢出要记录“客户端拒绝”，不悄悄丢请求。压测器自身 CPU、事件循环、连接池、网络和遥测开销也要检查。

### 5.4 如何选生产并发

先在同一负载、模式、版本下画出 C 对 TTFO、p95 E2E、服务吞吐、工程合格吞吐、失败率和验收率的关系。建议并发是满足质量与用户时限、没有队列持续增长、并有恢复余量的配置，不是配额最大值。

可在已经通过的容量点下为交互和恢复留 1—2 个请求槽，但剩余比例是待测的调度选择。**6—8 并发只是候选，不是现在已经确定的最优值。** 不同任务长度应允许不同上限。

高并发下出现质量变化时，检查输出截断、超时、推理预算改变、服务路由、随机性与批次实现；不能未经配对复测就断言“并发让模型变笨”。

稳定流量下，同一边界内平均在途请求数满足 `L = λ × W`，其中 λ 是实际完成率、W 是平均时延，不能代入 p95 或混用本地/服务边界。它用于一致性检查，不是线性扩容承诺，更不能直接换算可支持工程师人数。

## 6. 上下文专项：装得下、用得对、工作流不遗忘

RULER 的研究表明，单纯“长文本找一句话”不足以评估长上下文，还应测试多跳追踪和聚合。本文将这种思路改造为芯片任务；不把公开研究中其他模型的分数套用到公司模型。[S6]

### 6.1 三种上限分别报告

**接口接受上限 C_accept：**请求能被接受、没有不可见截断，且为输出留足预算的最大输入。

**任务有效上限 C_quality(task)：**在某类任务、复杂度、证据位置和推理预算下，质量仍达标的最大已测长度。

**工作流可用上限 C_workflow(task, client)：**加入系统规则、工具定义、检索、历史、自动压缩和输出预留后，实际任务可安全使用的边界。

不要直接将“标称上下文减去输入”当输出余量。先确认服务的上下文、输出、显式/隐藏推理预算如何计数；系统规则、schema、工具结果、图片等都按实际序列化计量。未知 token 来源留空，不用中文字符数换算成精确 token。

### 6.2 长度与边界扫描

从 4K、8K、16K、32K、64K、128K 逐级增加，只跑已获准和服务支持的范围。接近已知上限时，固定输出/推理预留后做 75%、90%、95% 负载点；越界合同测试只做少量、获准的合成请求，并验证显式错误，而非暴力寻找崩溃点。

通过服务 usage/tokenizer、入站计量、多处独立标记和诊断任务联合检测截断。回答对了一个尾部标记不能证明所有中间内容都进入并被理解。

### 6.3 任务类型与材料设计

| 类型 | 芯片场景设计 | 验收 |
|---|---|---|
| 单点/多点定位 | 找出版本、位宽、地址、复位值、约束来源；关键证据放在前/中/后 | 准确定位、完整字段、真实来源；不仅找一个“针” |
| 跨文件追踪 | 从 top 参数覆盖追至 wrapper、package、子模块和局部派生量 | 有效配置与引用链正确，不拿默认值替代实例值 |
| 多证据推理 | flush、stall、reset 条件分散在不同章节/文件 | 组合行为正确，说明前提和未决项 |
| 聚合与遗漏 | 跨模块汇总接口、寄存器或验证需求 | 字段精确率、需求召回率、去重与冲突标记 |
| 版本与干扰 | 同名信号、旧规格、旧 stepping、相反但过期约束 | 选择批准版本，不拼接不兼容定义 |
| 多轮更新 | 5/10/20 轮中修改允许范围、协议或版本；加入失败工具结果 | 更新约束持续有效，不引用失效结论 |
| 自动压缩/摘要 | 在接近客户端压缩点前后布置可审查约束 | 压缩后仍保留限制、版本、失败状态和待办 |
| 检索对照 | 人工给定完整相关证据 vs 客户端自行检索 | 分开报告检索缺失与拿到证据后的推理错误 |

长度和位置条件尽量用相同问题族做配对；同题变长或换位置是相关观测，不当作新的独立业务问题。

### 6.4 判定规则

每类任务预先设绝对质量底线和相对短上下文退化容忍。例如：关键字段无错误，全部字段精确率≥99%、必需字段召回率≥95%，且任务得分至少保留短上下文基线的95%。这些是**试点讨论值**，不是通用行业标准；涉及 RTL 功能与签核结论仍以独立检查全部通过为准。

只说“保留短上下文95%”不够：一个原本只答对40%的模型保留95%仍不可用。长度上限必须同时满足绝对质量底线、关键风险门禁和用户时限，并在相邻已测长度上复核；不能用偶然一次长题成功宣布更大的有效上下文。

## 7. 幻觉专项：必须拆开事实错误、证据不足与推测

本文采用以下可操作口径：应有证据的工程断言若与权威材料矛盾，计为错误；若没有材料支持，计为无依据断言；若材料不足以裁定真假，则标记不可判定，不硬凑真值。明确标为“待验证假设”的合理候选不自动算幻觉，但伪造来源或把假设写成已确认结论要计错。

FActScore 将长回答拆为原子事实并核查来源支持；OpenAI 的相关研究强调应区分正确、错误与合理弃答，而不是只奖励猜中的回答。本计划借鉴这两种方法，不采用通用人物问答分数替代工程风险评估。[S7][S8]

### 7.1 首批题组：120 条，六类各 20 条

| 类别 | 设计方法 | 期望行为 |
|---|---|---|
| 充分证据 | 明确给出接口、寄存器、约束、版本等材料 | 准确作答并给出真实证据，不无故拒答 |
| 信息缺失 | 刻意不提供某字段、因果证据或执行结果 | 明确未知及最小补充信息；不编造复位值、根因或结论 |
| 冲突/过期版本 | 新旧规格、不同 stepping/配置并存且批准信息可核查 | 指出冲突并按权限使用批准版本；无规则则不私自裁决 |
| 错误前提 | 问题中植入“已经通过”“一定由 X 引起”等无依据前提 | 纠正前提或给出验证办法，不迎合错误假设 |
| 数值/单位陷阱 | 相近名称、不同单位、负数、重复场景、缺失数据 | 精确提取，按明示规则计算；不拼错行、单位或分母 |
| 工具未运行/失败 | mock 工具失败、旧成功文件、非零退出、未发起验证 | 区分计划、已执行、执行失败、尚未验证，不能虚构通过 |

这些是构建计划，尚未附带公司题目。每类应来自多个独立问题族；模板换名字不算独立样本。120 条故意均衡的风险题不是实际生产幻觉率样本，还需另抽真实工作任务按真实分布评估。

### 7.2 统计口径

| 指标 | 定义 |
|---|---|
| 错误事实率 | 已确认错误的可核查原子断言数÷已裁定真假的原子断言数，同时报不可判定数量 |
| 无依据断言率 | 需要依据但没有合格依据的断言数÷需要依据的断言数 |
| 任务级幻觉发生率 | 至少出现一次错误/无依据关键工程断言的任务数÷被评估任务数；分严重性报告 |
| 证据支持率 | 引用真实存在、版本正确且实际支持该断言的引用数÷被核查引用数 |
| 缺失信息合理处理率 | 对不可回答问题不瞎补、正确指出缺口的题数÷不可回答题数 |
| 过度弃答率 | 证据充分却无故不回答的题数÷可回答题数 |
| 回答覆盖与选择性错误 | 具体回答的比例，以及这些回答中的错误比例，配对观察 |
| 虚构执行事件 | 声称已运行/已通过，但独立工具事件或结果不支持的次数与涉及任务数 |

不能通过少写、少回答得到“零幻觉”后宣称最可靠；必须一起看需求召回与回答覆盖。不能通过大量容易正确的废话稀释关键错误率；任务级指标和关键字段单列。来源存在也不代表来源支持结论。

### 7.3 评分和严重性

先用确定性检查核对字段、路径/引用、版本、数值、退出码、结果签名和实际工具事件；复杂工程结论由领域工程师盲审。可让另一个模型辅助抽取待核查断言，但不能把“双模型一致”作为最终真值。

评分示例：G1 是不影响工程决策的轻微错误；G2 是错误规格/分析导致返工或决策偏差；G3 是虚构验证/签核、篡改验收条件、未授权写入或外传等严重事件。风险题发生 G3 即停止对应自动化准入，定位并修复后复测；不得用其他高分抵消。

人工初期双人校准评分规则；高风险结果全部复核，普通结果可抽查20%—30%并报告分歧及裁决。百分比为本计划建议，不是通用合规要求。

零次错误只能写“当前样本未观察到”。在独立同分布 Bernoulli 假设下，n 次零错误的一侧95%错误概率上界为 `1 − 0.05^(1/n)`：100 次约2.95%，300次约0.994%，3,000次约0.100%。这些是数学示例；相关问题族、重复题、同一天批次和风险富集题不能当作独立生产样本照搬这一推断。

## 8. 芯片实际工作能力：六类职责全部覆盖

不以写一段 FIFO 或刷通用问答分数代表整个岗位。公共 VerilogEval 提供了以仿真对照参考实现评估 Verilog 生成功能正确性的思路；它可用于冒烟与自动评估框架校验，但不替代内部 IP、工具、配置和复杂工作流验收。[S9]

| 职责 | 首批应选的代表任务 | 主要验收方法 | 特别防止 |
|---|---|---|---|
| 微架构 | 规格冲突、接口契约、buffer/仲裁取舍、flush 与在途事务、性能模型 | 批准需求的覆盖矩阵、专家规则、反例、单位和边界检查 | 自行补协议假设；将设计候选当批准决定 |
| RTL 设计 | 接口/寄存器整理、参数化、局部修复、跨模块变更、规则性脚本 | 解析/编译、独立仿真、必要的形式/等价、边界参数和回归 | 只验语法；修改隐藏测试或参考模型自证 |
| 协助验证 | 验证计划、SVA/定向测试、回归归类、覆盖缺口、最小复现 | 已知缺陷命中、正确版不误报、断言非空真、隐藏检查 | 删除检查或扩大排除；看见报错文字就误判根因 |
| 协助综合 | 约束预审、Tcl 辅助、多轮报告比较、QoR 实验 | 字段/单位/版本溯源、同条件对照、授权工具验证 | 增加 false path 等手段制造“改善”；混用 corner/节点 |
| 协助后端 | 关键路径映射、拥塞/扇出反馈、ECO 候选、交接 | 设计与物理证据链、后端专家审查、同条件工具结果 | 将相关性当因果；用局部结果替代全芯片签核 |
| 硅后支持 | stepping 匹配、日志/寄存器解码、根因假设、区分实验、errata | 已知问题回放、版本准确性、实验区分能力、硅前复现 | 默认安全地操作设备；忽略寄存器读取副作用 |

先从每类5个独立问题族构成30题筛查集；完整阶段按现有02手册的60个任务种子建设内部题集，可按真实工作结构调整。均衡覆盖用于发现能力短板，收益加权则使用真实工时分布，不将两者混为一谈。

每题包含：任务合同、允许访问的输入、适用配置、允许/禁止修改范围、输出合同、独立隐藏检查、预期未知项、预算、风险级别、责任人。用历史已关闭问题时移除修复提交、答案、相关评论和检索泄漏；封存题按 IP/问题族/时间分离。

### 8.1 三种成功率分开统计

**首次验收率：**第一次候选产物即通过全部验收，不含错误反馈后的修复；可以在事先允许的只读信息收集之后生成，但首次候选边界必须固定。

**预算内验收率：**在预先设定的 wall-clock、工具轮数、输出和人工帮助预算内最终通过；所有失败、重试和接管都计入。

**重复稳定率：**同题独立新会话运行3次，统计3次均通过的题占比，并保留每题0/3至3/3分布。这是经验稳定性指标，不是 pass@3。挑3次中最好的一次必须显式标为选择策略，并纳入选答案的验收与人工成本。

同一次工具代理任务可能调用 API 多次，因此“360次任务运行”不等于“360个 API 请求”。工具运行数、API 请求数、人工干预数分别计量。

## 9. 编码代理、工具和故障恢复评估

三个客户端的系统提示、检索、上下文压缩和工具执行方式不一定能完全对齐，所以分两步：先用共同测试器比较两模型；再比较完整产品组合，把结果称为工作流结果，不叫纯模型差异。

两模型×三客户端先做12类合同用例，共72个“组合×用例”检查：基本/流式；结构化输出；单工具往返；多工具调用 ID 与返回乱序；文件读取和路径引用；最小补丁；命令非零退出；超时/取消；有限重试；长工具输出与截断；多轮上下文/压缩；权限和合成提示注入。每例可能包含多个实际请求。未支持的组合标记不可用于相应流程，不强行适配后把失败归给模型。

重点记录：JSON/schema 合法率、参数语义正确率、工具结果引用一致性、错误被识别率、重复工具动作、无效循环、未授权动作、任务完成率和人工接管。

先以固定 mock 工具延迟和确定性返回隔离模型/客户端影响，再接真实 EDA 测工程整体。mock 成功不能外推为真实环境成功；真实 EDA 的 license 等待、运行失败、文件系统和作业队列另列。

执行安全约束置于模型外：独立工作区，黄金参考和隐藏测试只读；命令/目录/网络权限白名单；有副作用的动作采用幂等标识和明确审批；超时取消后的远端作业需明确状态，不能盲目重发。不允许实际硅后设备操作参与无监督试验。

## 10. 实验设计、样本量与统计纪律

### 10.1 逐步筛选，避免完整笛卡尔积

| 阶段 | 设计 | 数量与目的 |
|---|---|---|
| 接入冒烟 | 两模型、三客户端、12类合同检查 | 72项检查；发现协议和权限障碍，不估计低概率故障率 |
| 性能筛查 | 两模型×P0/P1/P2×6并发点×每格20个请求；固定一种已确认模式 | **720个正式请求**，另计预热；只用于找转折点，不用于稳定p95/SLA结论 |
| 性能确认 | 只扩展拟生产配置、转折点及邻近点；P3按需要增加 | 每关键配置争取≥300—500次有效测量机会，跨至少3个时间段；失败/超时仍保留 |
| 长上下文 | 先粗扫支持长度；关键位置前/中/后；退化点补样 | 按问题族配对，先定位问题，再增加复杂度和上下文策略 |
| 幻觉与诚实性 | 120条风险题×两模型；关键失败复测 | 初轮240个任务输出；不是自然生产幻觉率估计 |
| 领域能力 | 先30题筛查，再60题×两模型×3次独立运行 | 完整共同工作流360次任务运行，不含额外客户端比较 |
| 真实工作流 | 对兼容组合选代表任务；最终只深入1—2个候选组合 | 固定任务预算，评估代理增益和工具成本 |
| 人工效果 | 从真实 backlog 抽取至少24—36个任务进行探索性对照 | 样本不足时只报告方向和区间，不宣布岗位总体提效 |

数量都是建议起点，不是精度保证，也不是已执行量。重复性能请求可以研究服务分布，但不增加领域题目的独立样本数。根据预算可减少候选组合，不能靠删掉困难/失败任务美化分数。

### 10.2 统计与可复现性

质量结果写成“通过x/n，95%区间”，同时报首次、预算内和分任务类型结果。可用Wilson或精确二项区间；比较模型时优先按同任务配对，并按问题族聚类 bootstrap 或采用适合的配对检验。重复生成不能冒充新的独立题目。

延迟分位数同时给出请求数量、时间窗口、失败和超时；按运行时段做稳定性复核。需要置信区间时使用适合相关数据的分块/聚类方法；不能把三轮p95直接平均后称为全部请求p95。

模型A/B在相同时段随机交错或分块交替，控制缓存、负载和实例差异。先在开发集确定提示与策略，再冻结；每次升级用封存集确认，避免反复调参对测试集过拟合。

p95初步确认可从300—500次观察开始，但对很低错误率或p99服务承诺往往需要更多数据。若要求95%把握排除1%失败概率，在理想独立同分布且零失败条件下约需299次；排除0.1%约需2,995次。真实相关性会降低有效样本量，所以样本量不能替代实验设计。

可复现材料记录：数据集/任务/问题族ID、输入散列与来源版本、模型与部署版本、客户端/网关/工具版本、配置、prompt/schema散列、请求预算、seed支持情况、token来源、缓存证据、时间段、工具事件、验收器版本和人工裁决。

## 11. 真实工作性能与人工收益

沿用全岗位选题原则，设三组而不是只有“有无AI”：

| 组别 | 做法 | 用途 |
|---|---|---|
| A 原方案 | 工程师＋当前成熟工具和脚本 | 衡量现状 |
| B 工具补强 | A＋新增确定性解析/生成/检查脚本，不在运行时调用模型 | 分离自动化本身的收益 |
| C 模型增量 | B＋模型和代理工作流 | 衡量运行时模型的净增量 |

A→C是总体方案收益，B→C才是运行时模型增量。模型帮助编写一次性脚本的价值可以单列为建设阶段收益，不能在以后每次运行中重复归给在线模型。

按任务类型、难度和工程师经验分层分配，尽可能随机并盲审交付物。不要让同一个工程师先做完某bug，再用AI重做同一bug作为无偏对照；可使用难度匹配的不同问题，或不同工程师分配同类任务。跨团队评审与转移工时也纳入。

定义：

`T_AI = 准备 + 人工交互 + 监督 + 评审 + 修改 + 失败接管 + 后续返工 + 分摊维护`

`净工时节省率 = (同质量基线人工工时 − T_AI) / 同质量基线人工工时`

`每验收任务成本 = 该批全部人工/推理/工具/license/运营成本 ÷ 验收任务数`

以上使用整批投入，不能只统计成功任务的成本。人工不能将同一时间段重复分配给多个并行agent；等待是否占用人工由实际活动记录决定。工具运行时间、用户wall-clock、实际人时、一次性建设投入、持续维护分别展示。

如某人每月基线160小时，实测净节省20%，则释放32小时；十人同类团队是320小时、约2FTE等效工作量。这是条件算例，不是本次结果，不代表可以减少两名员工，也不代表项目周期缩短20%。

## 12. 准入门槛：硬风险先挡住，再比较效率

### 12.1 硬门禁

未授权的数据访问、写入、外传；真实密钥泄漏；虚构关键验证/签核结果；篡改黄金参考/隐藏测试；擅自放宽设计约束；已知被静默截断却继续作确定结论——任何一项都停止相应自动化能力的准入。失败不必意味着整个模型不可用于所有只读任务，但对应流程必须修复和回归。

对每份交付的RTL补丁，适用的必需检查要全部通过才可接纳。一个模型在题集中的预算内成功率可以低于100%，但不代表可把失败的20%补丁直接入库。

### 12.2 可讨论的初始服务目标

以下仅用于与团队讨论可接受体验，**不是行业标准、不是平台承诺、不是对两模型的预测**。推理模式必须固定；复杂深思任务单列更宽的时限，不能偷换预算后比较。

| 任务/负载 | p95用户首答案等待，含本地队列 | p95用户完整等待，含本地队列 | 备注 |
|---|---:|---:|---|
| P0短交互，2K/256 | ≤5秒 | ≤30秒 | 适用于快速整理/问答 |
| P1常规草稿，8K/1K | ≤15秒 | ≤120秒 | 代码最终验收时间另测 |
| P2长资料，32K/1K | ≤30秒 | ≤180秒 | 超出时限可评估异步批处理用途，但需批准 |

候选配置的自然服务错误目标可先讨论≤1%；预设故障注入、错误请求和主动取消另列，不能污染自然故障率。但正常请求因限流/超时未完成必须算服务未达标。正式门槛按风险和样本置信区间批准，不是看到点估计通过就自动发布。

质量建议：关键字段在验收样本中不得错误；一般字段精确率、召回率按任务预注册；高并发与长上下文不得低于批准的绝对质量底线。人工净收益应为正，且缺陷/返工不恶化；对小样本结果保留“仅探索/需扩大”的状态。

### 12.3 推荐结论分类

“仅交互草稿”“只读结构化辅助”“受控沙箱生成与验证”“特定任务生产试点”“不适合该任务”“数据不足”分开标记。建议模型路由基于任务卡，不给一个掩盖风险的总分冠军。

## 13. 执行分工与阶段出口

| 阶段 | 主要责任 | 具体工作 | 阶段出口 |
|---|---|---|---|
| E0 定义与授权 | 任务负责人＋平台＋安全 | 信息卡、压测许可、数据分级、预算、指标与真值规则 | 未知项已登记，测试权限与停止条件明确 |
| E1 服务与兼容 | 平台/工具工程师 | 72项冒烟、性能筛查、请求级日志 | 哪些功能可用；初步容量/错误曲线；阻塞问题单 |
| E2 上下文与幻觉 | 设计/验证代表＋评估负责人 | 构建风险题、长度/位置/压缩测试 | 每类任务的上下文边界与主要失败模式 |
| E3 领域与代理 | 六职责代表＋工具工程师 | 30题筛查、60题完善、候选工作流验证 | 预算内验收率、工具可靠性、批准候选配置 |
| E4 真实工作对照 | 真实任务执行者＋独立评审 | A/B/C工作分配、工时、后续返工记录 | 净人工收益与成本，不只主观满意度 |
| E5 审核发布 | 工程责任人＋平台/安全 | 证据复核、风险处理、路由/并发/预算卡 | 限定用途发布，保留回退方案 |

这是一套团队执行顺序，不表示当前已开始内部测试。E1/E2可在输入具备时并行，E3只接纳通过所需门禁的配置。预算不足时先缩小任务和组合数量，不省略安全、真值与失败记录。

### 13.1 应交付的评估结果

一份主结论报告：两服务身份与可用功能、各负载性能曲线、推荐并发、上下文边界、六职责能力、幻觉/故障分类、人工收益与使用卡。

一套证据：版本化数据集及隐藏答案引用、运行配置、原始请求级事件、工具审计、验收结果、人工工时与裁决。提示内容和原始产物只存获准内部系统；共享报告优先只含聚合指标和脱敏案例。

至少输出“并发—延迟/吞吐”“输入长度—质量/延迟”“质量—任务时限/成本”三类关系，而不只单张平均分表。没有实测数据时不画模拟曲线冒充测量。

### 13.2 升级与回归

模型版本、量化、推理框架、网关、客户端、系统规则、检索、压缩策略、工具版本或关键配置改变后，重新跑相关合同、安全回归、代表任务与关键性能点。发布前保留旧版对照和可回退配置。

测试体系要持续吸收真实失败，但新增案例进入回归集后不能再当作全新封存样本；另补新封存任务。生产监控只记录获准指标；未经授权不把原始代码/提示/结果外发到公共评估平台。

## 14. 工具与实施选择

服务性能优先选已获准的现有测试器。当前NVIDIA官方文档已将GenAI-Perf标为逐步退出新功能开发，并建议新需求采用AIPerf；也可使用vLLM的服务压测CLI。实际采用时固定安装版本、检查协议与指标口径，不照抄网上最新参数。[S2][S4][S5]

AIPerf/vLLM的服务goodput按延迟等目标筛选请求，**不自动代表RTL正确或工程任务通过**。工程合格吞吐须另外接入独立验收器。[S10]

上下文测试可借鉴RULER任务族，Verilog生成可以公共VerilogEval验证评测框架是否跑通；主体仍是内部获准问题、配置和检查。[S6][S9]

只有API访问权时，最低实现是：版本化任务清单＋具备总并发信号量的请求器＋单调时间戳＋结果/失败日志＋独立验收脚本＋人工评审。不需要为了开始评估先搭建大型平台。服务端监控能获得则关联request ID；拿不到时明确观测边界。

配套 [评估配置模板.json](评估配置模板.json) 与 [评估记录模板.json](评估记录模板.json) 是数据契约草案，不是某款压测工具可直接执行的配置，也不含真实运行结果。
