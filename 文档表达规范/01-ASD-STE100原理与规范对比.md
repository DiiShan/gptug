# ASD-STE100：原理、AI 文档适用性与相关规范对比

更新日期：2026-10-09。本文按主题整理首次交流的实质内容；芯片设计应用独立收录于[芯片设计工作文档建议](02-芯片设计工作文档建议.md)，中文落地规则见[中文技术文档写作指南](03-中文技术文档写作指南.md)。

> 核心结论：ASD-STE100 适合约束技术文档的表达，不负责保证技术结论正确。中文工程文档优先采用“清晰表达＋统一术语＋可验证需求＋证据约束”，不默认要求完整 STE 合规。

## 1. 先区分：官方推荐、个人经验与社区工具

首次问题提到“最近 Anthropic 在推荐 ASD-STE100”。截至本次核查，尚未找到足以确认“Anthropic 将它作为通用官方推荐”的公开一手材料。对 Anthropic 官方网站的定向检索没有得到对应正式说明；这一检索结果不证明相关材料绝对不存在。

本次能够检索定位到 [Karpathy 的个人帖子][karpathy]，内容是尝试用 ASD-STE100 风格提高模型解释的可读性；“做到 80%”是非正式风格描述，不是标准规定的合规等级。另有 [asd-ste100-skill 社区项目][skill]，把相关规则用于 Claude Code。个人体验、社区实现和厂商官方推荐不能互相替代。

Anthropic 的[评估指南][evals]确实讨论了代码、模型和人工三类评判方法，但它不能作为 Anthropic 推荐 STE 的证据。后续如获得确切官方出处，应更新本节及交流记录，不把旧的“未核实”改写成“从未发生”。

## 2. ASD-STE100 是什么

ASD-STE100 Simplified Technical English，简称 STE，即简化技术英语，是限制词汇和句法的受控英语。它源于航空维修文档，由 ASD 下属的 STEMG 维护。官方资料所示 Issue 9 发布于 2025-01-15，包含 53 条写作规则和约 900 个批准使用的基础词。[官方介绍][ste]、[Issue 9 标准入口][standard]

它不是 Markdown 格式，不是文档目录模板，也不是专为大模型设计的提示词框架。它主要解决“同一段文字能否被稳定理解”，而不是“这段话是否符合实际工程”。

### 规则摘要

| 方面 | 要点 | 使用时的边界 |
|---|---|---|
| 词汇 | 约束批准词的词义、词性和用法 | 不是所有技术内容只能用约 900 个词 |
| 专业词 | 按规则允许技术名词和技术动词 | 保留准确的领域术语，不为通俗而改名 |
| 程序性文字 | 指令句通常采用最多 20 个英文词的限制 | 词数计算和例外以完整标准为准 |
| 描述性文字 | 描述句通常采用最多 25 个英文词的限制 | 可以说明系统和原理，不限于操作步骤 |
| 动作组织 | 通常一句一项指令 | 不把同时发生的动作拆成先后执行 |
| 语态 | 强调主动语态和明确动作 | 描述性文字有适用例外，不能凭空补充执行主体 |

以上为规则摘要，不是完整合规检查表。[Issue 9 标准入口][standard]、[官方常见问题][faq]

本次能检索到官方页面和标准条目，但官方站点部分页面及 PDF 全文访问受限；本次未完成标准全文逐条复核。需要正式合规时，应取得所指定版本的完整标准，核对规则、词典、专业术语和例外。本仓库不转载标准全文或完整词典，也不宣称中文指南是官方译本。

## 3. 用它约束 AI 文档，合理在哪里

相比“简洁一点”“专业一点”，术语一致、主体明确、条件清楚、减少混杂句，是更具体的检查目标。以下收益是本项目的工程判断，尚不是本项目模型的测量结果。

| 预期收益 | 具体表现 | 仍需额外保证 |
|---|---|---|
| 降低术语漂移 | 同一机制不随意换成多个近义名称 | 术语定义本身正确 |
| 明确动作与责任 | 指明谁在什么条件下做什么 | 责任分工得到相关团队确认 |
| 降低阅读负担 | 更容易定位前提、步骤、结果和限制 | 技术信息没有被删掉 |
| 便于审阅 | 能逐项检查指令、条件和检查结果 | 必须有可追溯输入和验收规则 |

### 三种使用位置

| 使用位置 | 建议 | 不要混淆 |
|---|---|---|
| 人写给 AI 的任务说明 | 明确目标、输入、限制和成功条件 | 清楚的措辞不能弥补错误目标或缺失资料 |
| AI 写给人的文档 | 优先用于说明、交接、操作和复现 | 可读性不等于正确性与完整性 |
| AI 写给其他 AI 或程序的信息 | 说明字段可以借鉴清晰表达；关键数据采用结构化格式 | 自然语言规范不能替代字段、类型、单位和状态约束 |

[JSON Schema][schema]可描述并检查数据结构约束；结构检查通过不证明数值真实，也不证明结论来自对应报告。语义和证据仍需检查。

## 4. 效果证据能支持到哪里

1996 年的一项研究让 175 名实际从业的航空维修技术人员阅读不同工作卡并完成理解测试。研究报告简化英语改善了理解，效果在复杂工作卡和非英语母语读者中更明显。[研究机构条目与摘要][study]

这支持的是当时工作卡场景下的人类理解改善，不能直接推导出：当前 Issue 9 的所有应用都有效、中文效果相同、AI 幻觉降低某个百分比，或任意模型的任务成功率都会提高。

本次没有取得足够公开、可复核的对照证据，证明仅在提示词中写“ASD-STE100”，就稳定优于设计良好的普通技术写作规则。个人帖子和社区工具说明可以作为试用线索，不能作为跨模型效果排名。[个人体验][karpathy]、[社区实现][skill]

本项目当前状态：**尚未开展针对用户内部模型和工程文档的对照试验。**不提供未经实测的收益百分比。

## 5. 六类主要局限

### 5.1 语言明确，事实仍可能错误

虚构示例：原材料只说“时序存在压力”，改写为“流水线深度不足，增加一级流水线”，虽然更直接，却新增了未经证明的根因和设计决定。

更稳妥的表达应区分：报告中能确认的事实、结果适用范围、未排除的原因、下一步检查。这个证据结构是本项目添加的工程要求，不是 STE 自动提供的能力。

### 5.2 不要把不确定性当作废话删除

“开展必要的相关优化”通常缺乏可执行信息；“当前结果支持假设 A，但尚未排除假设 B”则包含重要边界。要求模型明确不确定性的来源、影响和补证办法，而不是禁止使用“可能”“待确认”。

### 5.3 短句改写可能破坏逻辑和时间关系

必须保持条件作用范围、否定、量词、先后顺序、并发关系、周期边界和例外。不能把“条件 X 下 A 与 B 同时发生”改成“先 A，再 B”，也不能把“A 或 B”改成“A 且 B”。这些错误不能用可读性改善来抵消。

### 5.4 不适合把所有文档都变成操作手册

架构论证、探索性分析和设计取舍需要保留备选方案、假设、反例、负面影响及改变决定的条件。可以改善局部表达，不应削掉推理结构。面向专家的文档也不应无差别删除专业术语。

### 5.5 英语约束不能直接映射到中文

“20 个英文词”不能自动变成“20 个汉字”。中文可以借鉴术语一致、主语清楚、条件明确等原则，不必设置机械字数门槛。[ISO 24495-1 的适用范围][plain]覆盖大多数书面语言，可作为通用清晰表达的参考，但本仓库中文规则仍是项目自定指南，不是 ISO 认证文本。

### 5.6 一句提示不等于合规，也不保证节省成本

只指定标准名称，没有明确版本、词典、术语和例外，不能据此认定合规。ASD 与 STEMG 明确表示，不背书、认证或授权软件工具，包括 AI 工具。[官方工具声明][tools]

短句也不等于更少 token。补充主体、重复术语、加载规则、二次改写和重试均可能增加总量。应比较整个任务的耗时、调用成本和人工返工，而不只比较文档长度。

## 6. 类似规范与互补方法

下表中的机制来自所附原始来源；“选用建议”是本项目工程判断，不是统一基准排名。不同层次的方法可以组合使用。

| 方法 | 主要约束 | 选用建议与局限 |
|---|---|---|
| [Plain Language / ISO 24495-1][plain] | 面向读者的清晰表达原则，适用于多数书面语言 | 中文通用文档的基础；需另加术语、证据及技术校验 |
| [Google 技术文档风格指南][google] | 技术措辞、条件位置、标识符排版与组织 | README、开发者指南、接口说明；不自动证明需求正确 |
| [Microsoft 写作风格指南][microsoft] | 重点前置、简洁、自然语气和行动指引 | 用户指南和日常沟通；不是严格需求语义规范 |
| [Attempto Controlled English / ACE][ace] | 受控英语及明确的机器解释方式，可转换到逻辑表示 | 需要机器处理语义时考虑；建模成本高于普通文档润色 |
| [EARS][ears] | 用固定模式组织前置条件、触发事件、系统与响应 | 功能、状态、异常行为需求；周期、优先级、完整性仍要另定 |
| [RFC 2119][rfc2119] 与 [RFC 8174][rfc8174] | 定义 MUST、SHOULD、MAY 等要求强度及其大写语义 | 协议、接口和规范性要求；不解决证据或全文结构 |
| [Gherkin][gherkin] | 用 Given / When / Then 等组织场景 | 测试意图和验收场景；还需步骤实现、检查器和真实运行 |
| [Diátaxis][diataxis] | 区分教程、操作指南、参考资料与解释 | 整套文档组织；不等于事实校验器 |
| [ADR][adr] | 记录决策背景、决定与后果 | 架构选择和设计取舍；需主动记录备选方案与证据 |
| [DITA][dita] | 结构化主题类型与技术内容组织 | 内容规模大且需要复用时考虑；不宜仅为改变 AI 文风引入整套体系 |
| [S1000D][s1000d] | 以数据模块组织和管理技术资料 | 大规模技术出版与交付；不是一条提示词的替代品 |
| [JSON Schema][schema] | 字段、类型及数据结构约束 | 程序间交付和报告数据；结构有效不等于内容真实 |

简要选用逻辑：句子难读先改善清晰表达；操作易误解再增加 STE 风格约束；需求不清优先 EARS 和要求强度；文档混杂优先 Diátaxis；决策理由丢失优先 ADR；需要机器校验则优先结构化数据。

## 7. 怎么验证对自己的模型有效

以下是建议试验设计，不是已完成的测量。重点是把“写得像规范”和“对实际工作有帮助”分开测。

### 对照设置

| 组别 | 设置 | 要回答的问题 |
|---|---|---|
| A | 原有提示 | 当前基线表现怎样 |
| B | 少量明确的普通写作规则 | 是否无需标准名称也能改善 |
| C | 仅加入 ASD-STE100 风格要求 | 标准名称本身有什么作用；此组不是严格合规验证 |
| D | 中文组合式工程规则＋文档类型模板 | 显式领域约束是否更有用 |

材料覆盖需求、操作、分析、决策及不完整输入。每份先由工程师标出必须保留的事实、条件、否定、时间关系和待确认项。固定模型版本、输入、工具权限、采样参数、输出预算和并发设置；随机化调用次序并重复运行。小规模试点可先每类选数份材料、每个设置重复 3 次，这只是起步方案，不是统计充分性的保证。

### 评价与分工

| 维度 | 检查内容 | 主要检查者 |
|---|---|---|
| 技术保真 | 原意、关键事实、条件、例外和周期是否改变 | 工程师；AI 辅助定位 |
| 无依据新增 | 是否编造数值、根因、责任人或“已验证”状态 | 工程师对照输入和记录 |
| 可读可执行 | 读者能否找到前提、动作、结果和限制 | 不知组别的目标读者 |
| 数据与格式 | 标识符、单位、必填字段、引用定位和结构 | 脚本；无法自动判断的项转人工 |
| 效率与成本 | 首字延迟、总耗时、token、重试及人工修改时间 | 测量脚本与审阅记录 |

语义错误、无依据新增和严重遗漏应作为阻断项，不被文风得分抵消。比较成对样本的通过率、返工时间和波动；不能从很小样本推导普遍优势。不同评判器的适用边界可参考 [Anthropic 的评估实践][evals]，但具体指标和验收要求由本项目定义。

## 8. 推荐落地路径

先固定术语表和文档类型，再提供可追溯输入；先形成技术内容，再做语言改写，最后检查语义是否保持。默认采用[中文指南](03-中文技术文档写作指南.md)；芯片工作另叠加[岗位专用规则](02-芯片设计工作文档建议.md)。

完整 STE 更适合确有英文交付要求、术语维护和合规审查资源的场景。日常中文文档不以“像航空维修手册”为目标，而以“看得懂、查得到、能验证、不改原意”为目标。
