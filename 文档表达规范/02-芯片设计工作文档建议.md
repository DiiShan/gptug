# 芯片设计工作文档建议

更新日期：2026-10-09。性质：工程建议与模板，待结合团队规范试用；不是芯片设计标准、签核规则或真实项目测量报告。

> 覆盖范围：微架构、RTL／接口设计、协助验证、协助综合、协助后端、硅后支持。
>
> 已知工作边界：设计工程师交付代码；综合由其他团队执行；设计工程师对交付报告进行分析。综合执行、运行配置和报告导出不删除，统一标注“综合团队负责”。

通用表达规则见[中文技术文档写作指南](03-中文技术文档写作指南.md)。本文件只补充芯片领域的语义保护、文档结构和责任边界，不重复通用规范。

## 1. 各阶段用什么文档

下表是建议组合。STE 用于改善表达，EARS 用于组织行为要求，ADR 用于保留决策依据；均不能替代设计、验证和签核。方法定义与原始来源见[规范对比](01-ASD-STE100原理与规范对比.md)。

| 工作范围 | 主要文档 | 建议表达方式 | 必须保留的内容 |
|---|---|---|---|
| 微架构 | 方案说明、功能需求、架构决策记录 | 清晰中文＋ADR；功能行为借鉴 EARS | 目标、约束、备选方案、取舍、假设、失效条件、未决问题 |
| RTL／接口设计 | 接口规范、寄存器说明、状态机与行为规格 | 条件—事件—系统响应；统一要求强度 | 采样边沿、周期关系、复位、握手、优先级、异常及禁止行为 |
| 协助验证 | 测试意图、复现说明、问题分析与修复记录 | 场景按 Given / When / Then 思路组织；步骤用明确动作 | 需求 ID、刺激、观测点、预期、实际、判定、运行证据 |
| 协助综合 | 代码交付单、运行回执、报告比较与问题单 | 交接采用明确步骤；分析采用事实—推断—待确认 | 代码与运行版本、配置、约束、报告来源、比较前提和责任人 |
| 协助后端 | 约束说明、实现问题单、变更与影响分析 | 精确需求＋证据化分析 | 场景、约束依据、物理实现上下文、影响范围、确认与回归状态 |
| 硅后支持 | 实验／故障记录、复现及处置流程 | 操作写清前提与停止条件；结果分层记录 | 芯片／板卡／软件版本、样本范围、环境、日志、寄存器、恢复方式 |

优先试点：复现步骤、工具操作、报告交接、问题处置。谨慎套用严格短句限制：架构论证、跨周期协议解释、根因尚未确认的分析。

## 2. 芯片文档不可丢失的语义

以下是本项目建议的审阅项，不表示每篇文档都要建立独立章节。不适用项写“不适用＋原因”，不要填入猜测值。

| 类别 | 写清什么 | 禁止的简化 |
|---|---|---|
| 时钟与周期 | 时钟域、采样边沿、起算事件、结果观察时刻 | 把“下一周期”改成“立即”；省略跨域条件 |
| 复位 | 极性、同步／异步关系、有效期间行为、释放后的条件 | 自动套用模型熟悉的复位方式 |
| 握手与背压 | 接受事件、保持条件、取消条件、同时事件关系 | 把“请求出现”当成“请求已被接受” |
| 优先级与并发 | 冲突事件的优先级、并行行为、覆盖关系 | 将同时行为改成先后动作，或遗漏仲裁规则 |
| 数据语义 | 位宽、符号性、编码、单位、字节序、保留值 | 改动标识符、截断范围，或默认单位 |
| 例外与异常 | 非法输入、超时、取消、重试、禁止条件 | 删除例外，让局部要求变成无条件要求 |
| 范围与假设 | 配置、模式、版本、适用实例、已知假设 | 从一个实例推广到全部 IP、Tile 或芯片 |
| 证据状态 | 事实、推断、假设、建议、待确认、已执行检查 | 把仿真计划写成通过，把相关性写成根因 |

一句话不能明确复杂时序时，保留周期表、状态表或时序图。图表中的标识符和条件必须与正文一致；不能用图代替对边界的定义。

## 3. 责任边界：综合环节保留但不转嫁

| 环节 | 责任安排 | 交付或记录 |
|---|---|---|
| RTL 与变更说明交付 | 设计工程师负责 | 代码版本、变更范围、设计假设和待确认问题 |
| 综合环境准备、启动与重跑 | **综合团队负责** | 工具与环境版本、运行标识、成功／失败状态 |
| 综合配置和约束实施、归档 | **综合团队负责**；设计工程师确认设计相关意图 | 实际配置、约束版本、例外说明和变更记录 |
| 综合日志及报告导出 | **综合团队负责** | 原始日志、时序／面积等实际报告及运行清单 |
| 交付包完整性、数据解析和比较 | 设计工程师主导；可由脚本执行确定性检查 | 缺失项、解析状态、比较资格、差异和证据定位 |
| 报告不足、解析不确定或配置不一致 | 设计工程师提出补充需求；**综合团队负责**补交或重跑 | 未解决项、补交版本及比较限制 |
| RTL 修改建议与设计决定 | 设计工程师负责，按团队流程评审 | 建议、备选方案、影响范围和验证要求 |
| 后端运行和物理实现确认 | 后端团队负责；设计工程师协助 | 实现报告、约束确认、问题单与回归结果 |
| 验证回归及硅后实验 | 按团队实际分工确认 | 执行者、审批条件、实际结果与证据 |

最后两项是建议明确的边界，不宣称本次已经取得相关团队确认。AI 可以整理和提示缺项，但不替代责任人批准。

## 4. 各类文档最小模板

### 4.1 微架构／设计决策

借鉴 [ADR 原作者说明](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions)，增加本项目需要的备选方案与验证字段。

```text
决策 ID／标题：
状态：提议／已批准／已替代
版本、负责人、适用范围：
目标与约束：
已知事实及来源：
候选方案：
比较维度：功能、性能、面积、功耗、验证成本等适用维度
决定及理由：
没有选择其他方案的原因：
负面影响和新增风险：
假设、未决问题、需要补充的证据：
会触发重新评估的条件：
验证计划及批准记录：
```

不能把“推荐采用 A”润色为“已决定采用 A”。删除被否决方案之前，应确认不会丢失后续维护需要的理由。

### 4.2 RTL／接口行为要求

借鉴 [EARS](https://alistairmavin.com/ears/) 的条件与响应结构，但不声称以下中文模板是官方中文语法。

```text
需求 ID：
状态：草案／已确认／已验证／已废止
规范性程度：必须／不得／建议／可选
适用模块、模式和版本：
前置状态或条件：
触发事件及采样定义：
系统响应及观察时刻：
同时事件的优先级：
复位、异常和例外行为：
可验证的通过条件：
上游需求和设计来源：
验证项与证据：
待确认项、负责人、确认条件：
```

**虚构改写示例，不代表任何实际接口协议：**

输入只有“模块收到请求后给出响应”。不能自行补写“一个周期内响应”。应写：“模块收到请求后必须给出响应。请求接受条件、响应时限、背压及复位行为待确认。”

只有原始需求明确规定采样边沿和周期数时，才能保留相应数值；还应说明是在边沿采样、边沿后状态更新，还是观察某一周期内的有效信号。不要让“第 N 拍”成为没有起算定义的词。

### 4.3 协助验证：场景与缺陷

[Gherkin 官方参考](https://cucumber.io/docs/gherkin/reference/)定义了场景组织和步骤与实现的关联。下面仅借鉴其思路，不是已经可运行的测试代码。

```text
场景／缺陷 ID：
关联需求 ID、代码版本、配置：
初始条件：
触发事件及激励时序：
预期行为与判定依据：
实际行为、观测点和偏差：
复现命令／脚本版本／随机种子／运行 ID：
日志、波形及定位：
已排除因素与尚未排除因素：
根因状态：未知／假设／已有验证证据
修复建议、影响范围和回归要求：
执行状态与真实结果：
```

“有测试描述”不等于“测试已经实现”；“测试已启动”不等于“测试通过”；“单个用例通过”不等于“全部相关行为已验证”。文档必须使用实际记录支持的状态。

### 4.4 协助综合：交付包与比较

代码交付、运行、解析和分析的字段名应服从已有数据契约。本节是文档层最低信息要求，不覆盖或重命名仓库现有 JSON／CSV 字段。

| 内容 | 至少记录 | 主要检查方式 |
|---|---|---|
| 运行身份 | 代码提交／版本、运行标识、目标模块、配置 | 脚本检查存在性与跨文件一致性 |
| 比较上下文 | 工具版本、库、工艺角、模式、约束、时钟／路径分组等适用信息 | 脚本比较字段；工程师裁定差异是否允许比较 |
| 原始报告 | 日志、时序及实际交付的其他报告，文件版本或校验标识 | 脚本检查文件、解析状态、单位及数值合法性 |
| 分析结论 | 比较对象、差异、适用范围、来源定位 | 工程师复核；AI 辅助组织候选解释 |
| 缺失与风险 | 未交付、解析失败、单位未知、样本不足 | 明确标记；不把缺失值当成 0 |
| 后续动作 | 补交、重跑、设计复核、建议的验证办法 | 综合相关执行注明“综合团队负责” |

```text
分析主题和范围：
基线运行／当前运行：
输入交付方：综合团队
比较资格：可比较／有限可比较／不可比较
资格依据、配置差异及其影响：
事实：指标、单位、运行标识、原始报告定位
计算：公式、输入与结果
推断：可能解释、证据及替代解释
待确认：缺失报告、配置或设计信息
建议：需要进一步检查或评审的措施
综合执行与补交：综合团队负责
设计分析与代码决策：设计工程师负责
结果状态：草案／已复核／待补证
```

**虚构数值示例：**在已确认比较口径一致的前提下，基线 WNS 为 −0.12 ns，当前 WNS 为 −0.08 ns，则 ΔWNS＝当前－基线＝＋0.04 ns。可写“这两次运行中，该比较项的 WNS 增加 0.04 ns”。不能仅据此写“芯片性能提高 33%”或“某次 RTL 修改已被证明是根因”。相关配置未确认时，先报告比较限制。

与既有专题衔接：[SoC 多 Tile 综合时序分析](../ai提效/芯片研发/专题/SoC多Tile综合时序分析/README.md)、[模型评估](../ai提效/芯片研发/专题/模型评估/README.md)。本次只新增写作建议，不修改这些专题的执行流程或数据契约。

### 4.5 协助后端：约束与问题说明

```text
问题 ID、发现阶段、代码／网表／约束版本：
适用实例、模式、工艺角、时钟域：
现象及原始报告定位：
设计意图与依据：
已确认事实、候选原因与未排除因素：
提出的修改及功能／时序／功耗／实现影响：
需要的检查或回归：
后端团队执行和确认事项：
设计工程师提供或确认事项：
结论状态与未决问题：
```

不能为了“结论明确”自动添加时序例外、修改约束或宣称问题已关闭。文档说明与实际签核状态必须分开。

### 4.6 硅后支持：实验和故障记录

```text
记录 ID、时间及执行者：
芯片版本、板卡版本、固件／驱动版本：
样本范围与适用环境：
问题现象及影响：
前置条件和已批准的实验流程：
操作步骤、每步观察及预期：
日志／寄存器／测量记录的位置：
停止条件、恢复方式及批准要求：
复现次数、成功／失败次数和统计口径：
事实、假设、替代解释和下一项实验：
结论适用范围与尚未确认项：
```

默认先描述只读采集。写寄存器、复位、擦写或改变供电等可能改变状态的操作，必须引用已批准流程，说明影响与停止条件；资料缺失时标为待确认，不由 AI 补全操作参数。单个样本的现象不应直接推广为所有芯片的结论。

## 5. AI、脚本与工程师分别做什么

| 工作 | AI | 脚本／已有工具 | 工程师 |
|---|---|---|---|
| 内容起草 | 依据材料整理草稿、标记缺项 | 提供已解析数据及稳定模板 | 定义任务、资料范围和验收标准 |
| 数据整理 | 解释字段含义；提示异常 | 解析报告、保留来源、检查单位、版本和重复值 | 处理解析歧义与比较资格 |
| 语言改写 | 统一术语、清理冗词、整理结构 | 对照不可改字段、标识符及数值 | 判断条件、周期和设计含义是否保持 |
| 分析 | 提出候选解释、反证需求和检查建议 | 计算差异、执行已定义检查 | 判定根因、设计决定和行动优先级 |
| 审核与交付 | 辅助查漏，输出问题清单 | 输出真实检查结果 | 批准内容及对外结论 |

脚本也不是天然正确：解析器、检查器和参考数据需要测试与版本记录。AI 审核不能成为唯一放行依据。上表为建议分工，本次没有部署解析器或运行 EDA 检查。

## 6. 芯片文档专用提示词

使用前附上中文通用规则、当前任务、原始材料、术语表和明确的文档类型。

```text
在中文工程写作规则基础上，应用以下芯片设计约束：

只依据提供的代码、规格、报告、日志和已确认决定写作。
保持信号名、模块名、命令、路径、数值、单位和版本信息。
保持时钟域、采样边沿、周期起点、延迟、复位、握手、优先级、并发和例外。
没有提供的协议行为、周期数、阈值和责任人标记为“待确认”，不得补造。

根据文档类型组织内容：
微架构：目标、候选方案、取舍、决定、风险和重新评估条件。
RTL／接口：前提、事件、响应、时间关系、例外和验证标准。
验证：初始状态、激励、预期、实际、观测证据和运行状态。
综合／后端分析：比较资格、事实、计算、推断、待确认和建议。
硅后：版本、环境、已批准步骤、观测、停止条件和结论范围。

设计工程师交付代码并分析综合报告。
综合运行、配置实施、报告导出、补交与重跑必须保留，并注明“综合团队负责”。
不得把建议写成已批准决定，把计划写成已执行，把单项检查写成完整签核。
改写后先报告技术含义是否变化，再报告表达质量；无法确认时列出待复核项。
```

## 7. 交付前验收

| 检查 | 通过要求 |
|---|---|
| 工作范围 | 对应岗位所需材料完整，不用通用短句代替专用内容 |
| 技术保真 | 不改变条件、并发、否定、周期、例外、数值和标识符 |
| 证据追溯 | 关键事实能定位到正确版本的输入，不用模型自述作证据 |
| 比较有效 | 说明配置差异及比较资格，不把不同口径混为同一指标 |
| 责任清晰 | 综合团队执行事项完整保留，其他分工如实记录确认状态 |
| 状态准确 | 区分草稿、提议、已批准、已执行、已验证及已签核 |
| 安全与保密 | 公开仓库仅放通用方法和虚构／获准脱敏示例，不上传设计资产、内部日志或密钥 |

关键语义变化、无依据新增、证据错配和虚假完成状态，任一出现均应先修正，再讨论文风优化。文档写清楚是交付要求的一部分，不是技术签核本身。
