# 组合式中文工程写作指南

版本：v1.1　｜　更新日期：2026-10-09　｜　状态：可试用的项目指南，效果待实测

适用对象：人工编写、AI 起草和 AI 改写的中文技术说明、需求、操作指南、分析报告、决策记录及交接文档。

> 写作目标：读者能找到需要的信息，理解条件与结论，完成任务，并核对依据。简化表达，不简化事实。
>
> 本指南借鉴 STE、Plain Language 及其他工程文档方法，但不是 ASD-STE100 的中文译本、中文合规标准或官方认证文本。芯片领域另外使用[芯片设计工作文档建议](02-芯片设计工作文档建议.md)。

原文件名：`03-中文技术文档写作指南.md`。本次更名明确“组合式”定位，保留原有规则、模板和审核内容。只需要以 STE 为主线的中文表达适配时，另读[ASD-STE100 的中文适配指南](04-ASD-STE100中文适配指南.md)；两份指南不是 STE 合规等级之分。

## 1. 先用这一页

### 写作优先级

**技术含义与事实正确 → 必要信息完整、可验证 → 表达清楚 → 简洁和风格统一。**

当简短与准确冲突时，保留条件、单位、例外和不确定性。不存在本指南规定的“每句最多 20 个汉字”规则。

### 最小工作步骤

1. 确认读者、任务和文档类型：读者是要理解概念、执行操作、查询定义，还是批准决定。
2. 提供原始材料、术语、版本和不能改动的内容；缺失项单独列出。
3. 先组织内容，再改善语言。改写不能代替补需求、查证事实或作设计决定。
4. 对照输入检查语义、事实、状态及证据；处理阻断问题后发布。

### 可直接复制的短提示词

```text
使用中文工程技术写作。先保证技术含义和信息完整，再简化表达。
明确主体、条件、动作、结果和适用范围；同一概念使用同一术语。
保持标识符、命令、路径、版本、数值、单位、否定、时间关系和例外。
区分事实、推断、假设、建议和待确认项。缺失信息不得补造。
关键事实注明来源；没有执行的检查不得写成“已验证”。
按文档类型组织内容：需求可验证，操作可执行，分析有证据，决策有取舍。
完成后对照原文检查语义变化、重要遗漏和无依据新增，并列出需人工确认的问题。
```

这段提示是写作约束，不是正确性保证。使用时仍需提供资料和验收条件。

## 2. 先选文档类型，不套一个万能模板

[Diátaxis](https://diataxis.fr/)区分教程、操作指南、参考资料和解释。本项目另按工程任务提供需求、分析和决策模板；这些不是 Diátaxis 新增的官方类别。

| 读者要做什么 | 选用类型 | 首要内容 | 避免什么 |
|---|---|---|---|
| 理解概念或机制 | 概念／原理解释 | 定义、组成、工作方式、边界和例子 | 只有步骤，没有原因 |
| 执行一项任务 | 操作指南 | 前提、动作、检查结果和异常处理 | 原理说明淹没执行步骤 |
| 查询准确含义 | 参考资料 | 字段、接口、参数、类型、范围、单位和例外 | 为行文变化改名，漏掉适用版本 |
| 明确系统应做什么 | 需求规格 | 条件、事件、主体、响应、时限和判定 | “尽快”“适当”等没有判定口径的要求 |
| 判断现象和原因 | 分析报告 | 结论状态、证据、计算、替代解释和待确认项 | 把猜测当成事实，把相关性当因果 |
| 批准或追溯选择 | 决策记录 | 背景、候选方案、选择理由、代价与风险 | 只留结论，删掉权衡 |
| 学会一项新技能 | 教程 | 学习目标、受控示例、逐步练习及检查 | 默认读者已经具备未说明的知识 |

一份文档可以有多种内容，但应把“怎么做”“是什么”“为什么”和“待决定”分开，不在同一段反复切换。

## 3. 十二条中文表达规则

以下是本项目自定规则，不是对 STE 53 条规则的逐条翻译。

| 编号 | 规则 | 检查办法 |
|---|---|---|
| CN-01 | 写清读者、任务和范围 | 读者能否知道本文解决什么、不解决什么 |
| CN-02 | 已确认的结论或当前状态前置 | 开头能否看出结论、限制或尚不能下结论的原因 |
| CN-03 | 同一概念使用同一术语 | 是否无定义地交替使用近义词；同名是否多义 |
| CN-04 | 尽量明确动作主体 | 谁执行、谁确认、谁提供资料；未知时明确写未知 |
| CN-05 | 条件与其约束的动作相邻 | 多个条件的“且／或”、作用范围及例外是否清楚 |
| CN-06 | 一句话表达一个主要判断 | 可拆分无关内容，但不拆坏因果、并发或时间关系 |
| CN-07 | 保护不可改内容 | 名称、代码、命令、路径、数值、单位、版本是否保持 |
| CN-08 | 区分要求强度与事实可能性 | “必须”“建议”“可选”和“可能发生”是否混用 |
| CN-09 | 区分事实、推断与行动建议 | 每个关键结论属于哪一类，是否有依据 |
| CN-10 | 缺失与未知显式标记 | 是否将未提供写成 0、将未执行写成失败或通过 |
| CN-11 | 删除空话，不删除限制 | 精简后是否仍保留条件、假设、例外和适用范围 |
| CN-12 | 让结果可以核对 | 来源、判定标准、实际状态和后续责任是否明确 |

### 术语、缩写和排版

第一次出现容易误解的术语时说明含义；面向专业读者的常用术语不必反复解释。关键命名维护一份术语表，不在多篇文档各自定义不同版本。

| 推荐字段 | 作用 |
|---|---|
| 推荐名称／原始标识符 | 指定稳定称呼，保留与代码或报告的对应关系 |
| 定义与适用范围 | 防止一个名称指向不同对象 |
| 别名／不建议写法 | 说明历史名称和容易混淆的词 |
| 定义来源／版本／确认状态 | 表明定义来自哪里、何时适用 |

正文可使用中文标点；代码、命令、路径、原始错误消息和公式中的必要符号保持原样，用反引号或代码块标识。日期写清年份，时间相关记录写清时区；数值说明单位和统计口径。不要仅用颜色区分通过、失败和待确认。

## 4. 要求强度：项目内明确定义

[RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) 和 [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174)提供英文要求等级及其大写形式的语义。下面是本项目采用的中文约定，不是官方中文翻译，也不能覆盖上游合同或正式规范的用词定义。

| 用词 | 本项目含义 | 使用要求 |
|---|---|---|
| 必须 | 强制要求 | 给出适用条件和可检查的结果 |
| 不得 | 禁止行为 | 指明禁止什么、何时适用 |
| 建议 | 默认应考虑采用，存在合理例外 | 偏离时记录理由和影响 |
| 不建议 | 默认避免，但可能有合理例外 | 采用时说明依据和影响 |
| 可选／允许 | 非强制选择或明确许可 | 不表示该行为一定会发生 |
| 可能 | 对事实或预测的不确定判断 | 说明证据、限制或需要补充的信息 |

“可以”容易兼指能力、许可和可能性，关键需求中应写成具体含义。不要把旧文档的“应”机械替换为“建议”或“必须”；先核对上游定义。

## 5. 证据与不确定性怎么写

### 五类内容分开

| 类型 | 应包含 | 不应包含 |
|---|---|---|
| 事实 | 输入中可观察的内容、来源、版本及范围 | 仅凭常识补出的项目参数 |
| 推断 | 依据、推导过程摘要、假设和替代解释 | 没有依据的确定性根因 |
| 假设 | 为分析暂时采用的条件及其影响 | 隐藏在结论里的未经确认前提 |
| 建议 | 建议动作、目的、前提、风险及所需批准 | 伪装成已批准或已执行的决定 |
| 待确认 | 缺失什么、影响什么、怎样确认 | 单独写“待完善”而不说明问题 |

不是每句话都要贴标签；在分析结论、关键数值、根因判断和行动建议处使用即可。

### 最小证据字段

```text
结论／事实 ID：
内容及适用范围：
来源文件或页面、版本／运行标识：
定位：行号、页码、节标题、记录 ID 等至少一种有效位置
原始值与单位，或支持该结论的原文位置：
计算或推导：输入、公式、限制
核查状态与未决问题：
```

公开事实优先引用原始来源，易变化信息保留核查日期。项目报告优先保留运行、版本和文件定位；有链接但打不开、版本不对应或找不到支持内容，不能视为证据已经核查。

不得生成看似精确但没有校准依据的置信度，例如随意写“根因概率 93%”。可以使用“已有直接证据”“仅有间接证据”“尚未验证”等说明，但仍要列出依据。

### 缺失状态不是零值

| 状态 | 含义 |
|---|---|
| 未提供 | 输入材料中没有该信息 |
| 未执行 | 对应检查尚未运行 |
| 无法解析 | 材料存在，但提取或解释失败 |
| 检查失败 | 已执行检查，结果不满足已定义条件 |
| 不适用 | 该项在当前范围内不成立，需要说明原因 |
| 待确认 | 需要补充资料或由责任人判断 |

这些状态不得统一替换为 0、空白或“正常”。报告中“无记录”与“确认没有发生”必须区分。

## 6. 中文改写示例

以下均为虚构教学示例，不是用户的项目资料。改写只在给定信息内进行，不能为追求明确而新增业务要求。

| 原始表达或输入 | 更稳妥的写法 | 改写重点 |
|---|---|---|
| 应对相关报告开展必要检查。 | 需确认检查人、报告范围、检查项目和判定标准；现有信息不足以形成可执行步骤。 | 信息缺失时不编造责任与动作 |
| 初始化结束后，先加载配置，再启动服务。 | 初始化结束后加载配置。配置加载完成后启动服务。 | 保持已给出的顺序 |
| A 与 B 在条件 C 下同时执行。 | 条件 C 满足时，同时执行 A 和 B。 | 不把“同时”改成“然后” |
| 数据表明，问题可能与配置有关。 | 当前数据提示配置可能是影响因素；尚需检查配置差异及其他可能原因。 | 保留不确定性，不升级为已确认根因 |
| 某检查没有返回结果。 | 该检查未返回结果；执行状态和失败原因待确认。 | 不把无结果写成通过或失败 |
| 问题已修复，等待验证。 | 修改已完成，修复效果待验证。 | 区分代码修改和问题关闭 |

**分母示例：**给定虚构输入“计划执行 100 项检查，已执行 80 项，这 80 项均通过”，应写“已执行项通过率 100%，计划执行完成率 80%，剩余 20 项未执行”。不能只写“全部检查通过”。这里的数字仅用于说明统计口径。

## 7. 可复用文档模板

模板是最小字段集合，不要求每篇都照抄完整目录。不适用项可以删除并说明原因；缺失的必需项保留为待确认。

### 7.1 概念与原理说明

```text
标题、读者与适用范围：
一句话定义：
解决什么问题／不解决什么问题：
核心组成和术语：
工作方式及必要条件：
示例与反例：
限制、例外和常见误解：
来源与版本：
```

### 7.2 操作指南

```text
目标与适用版本：
执行角色、所需权限及输入：
前置条件、风险与批准要求：
步骤：每步写动作、对象、预期观察
完成判定：
异常分支和停止条件：
恢复／回退方式；未确认时明确标注
需要保留的输出与日志：
来源、维护人和核查日期：
```

真正有顺序的操作使用编号步骤。说明性质的备注不要夹带关键操作。涉及删除、覆盖、生产变更等操作，应先写明影响、授权和恢复条件；没有资料时不要凭空生成处置步骤。

### 7.3 需求规格

```text
需求 ID、状态、适用对象和版本：
前置条件或状态：
触发事件：
主体必须／不得执行的行为：
响应时限或时序关系：
例外、边界、冲突优先级：
通过条件和验证方法：
上游依据：
待确认项：
```

这借鉴 [EARS](https://alistairmavin.com/ears/) 的约束思路。不能将自然语言模板自动视为形式化证明，也不能凭模板补齐没有依据的阈值。

### 7.4 分析报告

```text
问题、范围及当前结论状态：
输入及版本、比较资格和限制：
事实与证据：
计算：口径、公式、输入、结果
推断与假设：
替代解释、反证与尚未排除因素：
风险和建议：
待确认项：影响、责任人或负责角色、需要的材料
实际完成的检查：
```

### 7.5 决策记录

```text
决策 ID、背景、状态和负责人：
目标、约束、已知事实：
备选方案及比较维度：
选择及依据：
代价、负面影响和风险：
未决问题与验证要求：
重新评估条件：
批准、替代或废止记录：
```

该结构借鉴 [ADR](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions)，补充本项目的备选方案和验证要求。

### 7.6 参考资料与交接单

```text
对象、适用版本、维护角色：
字段／接口／交付物清单：
名称、类型、含义、单位、合法范围：
必需或可选、默认值及其依据：
依赖、前置条件、例外和限制：
来源与变更记录：
交付人、接收人、验收状态和待补事项：
```

## 8. AI 完整写作与审核提示

### 生成／改写提示

```text
任务类型：[概念说明／操作指南／需求／分析报告／决策记录／参考资料]
读者和目标：[填写]
适用范围和明确排除范围：[填写]
原始材料及版本：[提供]
术语表、项目规范与不可改内容：[提供]
篇幅和输出格式：[可选；不得以篇幅为由删除关键含义]

请遵守以下规则：
1. 只用给定材料支持项目事实。需要外部事实时注明来源与核查日期。
2. 先判断资料是否充分。未知值、阈值、周期、根因和责任人不得补造。
3. 明确主体、条件、事件、动作、结果、范围和例外；保持逻辑与时间关系。
4. 同一概念使用同一术语；保留命令、路径、标识符、数值、单位和版本。
5. 区分事实、推断、假设、建议和待确认项。
6. 根据任务类型使用对应模板，不把所有文档写成操作步骤。
7. 原文可能有错时单列问题，不在润色时默默修改技术含义。
8. 没有实际执行的工具检查，只能写“未执行”或“待验证”。

输出：
A. 正文。
B. 必要的来源与定位。
C. 语义变更、缺失资料、待确认问题；没有发现不等于完成独立验证。
D. 已执行与未执行的检查。对关键技术结论保留人工复核入口。
```

### 独立审核提示

```text
你是文档审阅者。对照原始材料和术语表审核候选文档，不要仅评价文风。
检查：技术含义变化、关键遗漏、无依据新增、术语漂移、数值和单位、
条件与否定、并发和时间关系、范围与例外、证据定位、虚假完成状态。

输出问题表：
问题 ID｜位置｜问题类型｜严重性｜原始依据｜候选表述｜修改建议

对无法判断的项写“需要人工确认”，不要为了给出通过结果而猜测。
有阻断问题时，不得用可读性得分抵消。
审核意见不是实际工具执行或技术签核的证明。
```

使用方式：对话中直接提供规则和资料；需要项目级使用时，将精简规则交给当前客户端支持的项目指令机制，并核对其是否实际被读取。不能仅因仓库中存在某个 Markdown 文件，就认为所有模型和客户端已自动遵守。本次没有修改任何本地客户端配置或安装 Skill。

## 9. 谁负责检查

下面是建议流程，尚未附带已部署的检查脚本。

| 阶段 | AI 适合做 | 脚本／工具适合做 | 人工必须把关 |
|---|---|---|---|
| 输入整理 | 分类、查漏、提炼阅读问题 | 文件存在性、版本、字段、格式检查 | 材料权限、权威版本和任务范围 |
| 草稿形成 | 按模板组织内容、列出未知项 | 提供结构化数据和可复现计算 | 目标、需求完整性、设计判断 |
| 语言改写 | 统一术语、减少冗词、改善组织 | 标识符与数值差异检查、必填项检查 | 逻辑、因果、时间关系和专业含义 |
| 证据审查 | 标记可能无依据的结论 | 检查引用是否存在、记录与版本是否匹配 | 来源是否真正支持结论 |
| 发布 | 整理交付说明和变更摘要 | 链接、文件清单、格式与提交检查 | 技术批准、保密和实际完成状态 |

脚本通过只说明通过了相应检查；它不能证明所有语义正确。AI 复核也有波动，需要工程师校准与抽查。[Anthropic 评估指南](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)讨论了三类评判方法的边界，本表是面向本项目文档的具体分工建议。

## 10. 发布前检查清单

| 级别 | 检查项 | 处理规则 |
|---|---|---|
| 阻断 | 改变技术含义、条件、否定、时间关系或关键数值 | 先修正或取得明确批准 |
| 阻断 | 无依据新增事实、错配证据、将未执行写成已验证 | 先补证或改为真实状态 |
| 阻断 | 关键前提或例外缺失，使读者可能执行错误动作 | 不发布为可执行指南 |
| 阻断 | 泄露未经批准公开的信息或密钥 | 不进入公开仓库 |
| 必查 | 术语、责任、版本、单位、范围、判定和未知项 | 有缺失则修正或明确限制 |
| 优化 | 长句、空话、标题不清、重复和排版 | 在不改变含义的前提下改善 |

这不是量化评估中的官方分级。项目可以进一步细化，但不应通过加总文风得分掩盖阻断问题。

## 11. 如何判断指南是否有效

不要只问“读起来是否像技术手册”。应比较关键内容保留率、无依据新增、查找与执行任务的正确率、审阅时间、人工返工、模型调用成本及多次运行波动。对照设置与评估步骤见[原理与规范对比第 7 节](01-ASD-STE100原理与规范对比.md)。

本指南截至 v1.1 尚无本项目实测效果数据；所有收益预期需由实际文档和目标模型验证。
