# RTL 源码学习提示词：STE 中英对照

版本：v1.0｜更新日期：2026-10-09｜状态：可执行任务模板，尚未在用户源码上实测

本文件把[芯片文档建议](02-芯片设计工作文档建议.md)、[组合式中文工程写作指南](03-组合式中文工程写作指南.md)和[STE 中文适配指南](04-ASD-STE100中文适配指南.md)用于一个具体任务：根据真实 RTL 生成顶层及全部范围内子模块的双语学习文档。不是另一份 STE 标准，也不是已生成的设计说明。

这是经泛化的公开模板：替换 `<RTL_SOURCE_ROOT>`、`<OUTPUT_ROOT>`、`<TOP>` 和 `<主宏定义文件>` 后，交给有权限读取本地源码的执行环境。公开版不保存用户实际模块名、本地路径、源码、内部报告或分析结果；占位符是有意保留的模板参数。

## 相比仅指定 ASD-STE100 的改进

先核实配置与实例层级，再解释源码；模块定义共用文档，实际实例及配置差异逐项说明。表达采用 STE 风格，证据分类、覆盖验收和执行边界是本项目规则，不归称为 STE 原规则。中英文按语义对应，不能为简洁丢失条件或时序。未知项显式标记，未执行检查不得写成通过。

## 可复制提示词

````text
# 任务：基于真实 RTL，编写 <TOP> 及其子模块的中英文对照学习文档

你是一名负责 RTL 源码分析和技术文档编写的工程师。读者懂数字电路和 RTL，但不熟悉这份代码。
目标不是把代码逐行翻译成自然语言，而是解释：模块做什么、数据怎样流动、控制怎样决定行为，以及各模块怎样组成 <TOP>。
这是现有实现的解释任务，不是重新制定需求、修改设计或评估 PPA 的任务。

## 1. 输入、输出和执行边界

- 源码目录：<RTL_SOURCE_ROOT>
- 顶层模块：<TOP>
- 输出目录：<OUTPUT_ROOT>
- <主宏定义文件> 等 define 文件是确认编译分支的重要线索，但不得未经核实就认定它们代表完整的实际编译配置。

只读源码、配置和已有报告。所有新建文档、检查脚本及运行产物必须位于输出目录，不修改 RTL、宏、参数、构建配置或仓库状态。
先检查输出目录；更新本任务同名文件时保留人工修改，不删除无关文件，不堆积多个“最终版”。
不将源码、内部路径或分析结果上传到 GitHub、公共网站或未授权外部服务。
可读取构建入口、filelist、include 和实例化关系明确指向的依赖；不要无边界扫描整块磁盘。
可使用已有工具进行安全的解析、预处理或 elaboration（实例展开），但先检查命令副作用，并把工作目录和产物定向到输出目录。不得默认执行不明构建脚本、综合、完整回归或联网安装工具。

先检查路径是否可访问、顶层源码是否存在。若不能访问，明确记录实际失败原因，不虚构目录、模块或代码分析。局部资料缺失时继续完成不受影响的部分，并标记受影响的结论。

## 2. 先确认源码版本和编译配置，再解释行为

记录分析时间、源码根目录、已读取的相关文件及源码基线。优先记录可取得的 SVN revision、工作副本修改状态；补充文件哈希，以便行号对应到本次读取的内容。不能取得的信息写“未取得”，不得假设工作副本干净。

检查以下实际存在的材料：
- <主宏定义文件> 及其他宏定义、头文件和嵌套 include。
- 构建入口、filelist、文件顺序、include 搜索路径、命令行宏及已有编译日志。
- `define / `undef / `ifdef / `ifndef / `elsif / `else 等条件分支。
- parameter、localparam、实例参数覆盖及 generate 条件。

对影响模块组成、接口、位宽、数据路径、控制或时序的配置，记录：名称、定义或覆盖位置、作用范围、候选值或实际值、采用依据、受影响的分支，以及确认状态。
区分宏是否定义与宏取值；不得把“定义为 0”当作“没有定义”。按实际编译上下文判断定义顺序和作用域，不拼出并不存在的全局配置。

区分三种状态：已有材料确认的构建配置、仅据可见源码得到的条件化判断、尚不能确认的配置。
若缺少真实构建入口，不得把自行选择的默认参数或手工预处理组合写成“项目实际配置”。不同候选配置分别描述，不能混成一个实现。
采用的分析工具、版本、命令、实际结果和限制必须可追溯。文本或正则扫描只作为候选发现手段，不能独立证明完整的编译后层级。

## 3. 建立模块层级和覆盖清单

从 <TOP> 出发递归追踪实例化关系，不只分析第一层，不只按文件名搜索。
对递归依赖中有源码定义的模块建立独立说明，包括当前配置有效的模块、其他可见条件分支中的模块，以及配置尚未确定的依赖。明确区分这些状态，不能把条件模块画成当前一定存在的实例。
仅在目录中存在、但没有发现与 <TOP> 的依赖关系的模块，列为范围外并说明理由，不冒充 <TOP> 子模块。

清单至少包含：
模块名｜源码定义位置｜父模块与实例路径｜实例化位置｜参数覆盖及可确认的有效值｜编译／generate 条件｜当前配置状态｜文档路径｜分析状态。

以“模块定义”为单位建文档，以“实际实例或配置变体”为单位解释用途差异。
同一模块多次实例化时，共用一份实现说明，但列出每个实例；参数、连接或分支导致行为不同的，必须分别说明。
遇到同名但不同文件的模块定义，记录选择依据并区分文档，不能任意选一个。
外部 IP、加密模块、黑盒或未找到源码的依赖，单独列清单，仅说明可见接口、连接和用途边界，不猜测内部实现。
影响行为的 package、interface、函数和 task 也要读取并引用，但不要把它们冒充独立 module 凑数。

## 4. 每个有源码的模块都必须说明什么

<TOP> 和所有范围内有源码定义的子模块，都按下面的检查项分析。章节可按模块特点合并，但每项都必须有实质内容，或“不适用＋源码依据和原因”。“尚未确认”不能写成“不适用”。

### A. 模块定位、设计目的与实际用途

说明该模块实际完成的功能，以及在 <TOP> 中解决的具体问题。
把源码可直接确认的功能、注释陈述的设计意图、根据实现推断的设计目的分开。
列出它位于哪些实例路径，上下游是谁，接收什么、向谁交付什么。
不得只根据模块名、信号名或“常见设计方式”生成通用介绍。

### B. 关键输入输出

按功能分组说明关键端口：方向、位宽或位宽表达式、含义、来源／去向、有效条件，以及适用的时钟域。
同时解释模块端口和父模块实际连接，包含常量连接、未连接、切片和拼接的影响。
影响功能理解的接口不得遗漏；不必逐行复述无关声明。

### C. 内部数据路径

追踪主要数据从输入、选择、变换、存储到输出的实际路径。
说明关键寄存器、缓存／存储器、队列、选择器和运算逻辑的作用，以及读写、更新和保持条件。
区分组合变化与寄存后的变化。只讲源码存在的结构，不给模块套用想象中的缓存或流水线。

### D. 控制条件、状态和优先级

给出决定行为的实际条件表达式，并解释条件成立和不成立时分别发生什么。
存在 FSM 时说明状态、转移条件、动作和冲突优先级。
没有显式 FSM 时，说明计数器、有效位、占用位、指针或其他状态；不得虚构状态机。
区分更新前状态、时钟边沿采样和更新后状态，保留同时事件、保持、清除、取消和异常分支。

### E. 时钟与复位

说明时钟来源、适用边沿、源码可确认的时钟域，以及实际存在的时钟使能或门控条件。
根据实现说明复位极性、同步／异步关系、被复位的状态、未复位的状态及释放后的行为。
无时钟或复位的组合模块必须明确说明，不套用默认复位方式。
发现跨域连接时标出边界和可见处理，但不得仅凭模块名或同步器结构宣称 CDC 安全。

### F. 握手、停顿和数据保持

根据真实代码定义“请求出现”“请求被接受”“响应有效”“响应被接收”等实际存在的事件。
若存在背压或停顿，说明由谁产生、传播到哪里、哪些信号／状态必须保持、何时恢复推进。
不得仅看到 valid / ready 就认定是标准协议，也不得无依据假设数据在停顿时保持。
说明同时接受与完成、同时读写或多方请求等适用情况的实际处理。
不存在相关机制时说明原因。

### G. 参数和编译分支

区分默认参数与实际实例值，说明相关宏和参数如何改变接口、容量、位宽、路径或行为。
当前实现、条件实现和未确认配置分开写；关键行为结论注明适用配置。
不盲目枚举全部宏组合，也不为展示变体擅自修改工程配置。

### H. 正常过程和边界情况

每个模块至少给出一个由实际源码支持的正常过程。时序模块用事件／周期表说明；组合模块用输入条件到输出结果说明。
复杂模块按独立主要功能补充场景，不用一个简单场景冒充全部行为。
按真实结构分析相关边界，例如复位、空满、连续请求、停顿与恢复、并发读写、仲裁冲突、清除／取消和计数边界。
明确初始条件、触发、状态变化、输出和证据。不存在或无法确认的机制不得补写。
若某项行为依赖上游保证，区分“源码内有检查”“由外部约束保证”和“尚未确认”。

### I. 依据、限制和待确认项

列出本模块最重要的代码依据及未解决问题；每个问题写清缺什么、影响哪些判断、怎样确认。
小模块可以精炼，但不能只留模板标题。复杂模块必须解释它区别于其他模块的具体机制。

## 5. <TOP> 顶层还必须给出整体解释

先用简短的中英文摘要说明 <TOP> 的实际功能及本次分析范围，不从名称推断它必然是什么类型的设计。
给出模块层级和主要连接表，分别说明数据流、控制流和停顿／背压传播。
选择有源码支持的代表性端到端过程，串联顶层输入、子模块处理、状态／存储更新和顶层输出。
涉及周期时定义起算事件和观察时刻；区分组合结果、边沿后更新和后续周期。
如延迟依赖配置、队列占用、仲裁或下游响应，应写条件化行为，不编造固定延迟、吞吐率或性能数值。
整体说明与子模块说明必须交叉核对，不能只是把各模块摘要拼接起来。

## 6. 代码证据与结论边界

关键功能、时序、复位、握手、分支和边界行为，必须附紧邻结论的具体代码位置。
格式为：相对源码路径:L起始行-L结束行，并标出相关 module、实例、always、assign 或标识符；必要时附最小源码摘录。
涉及实例用途时同时引用父模块实例化／连接位置和子模块实现位置；涉及配置时补充宏、参数或构建来源。
引用原始文件的真实行号，不用预处理后行号冒充原始位置。范围应足以看清条件、上下文和优先级，不以整文件笼统引用代替定位。
外部依赖采用单独的根目录别名，避免相对路径歧义。源码基线变化时重新核对引用。

明确区分：
- 代码事实：可直接由本次读取的源码确认。
- 静态推导：根据源码推导，列明前提和范围；示例轨迹不是仿真结果。
- 意图推断：根据实现推测设计目的，提供依据，不冒充原作者声明。
- 待确认：缺少配置、源码、协议约束或执行证据。

注释可辅助理解；注释与实现不一致时并列记录冲突，不静默选择注释。
不得用写作规范、常识或流畅表述补齐代码未说明的协议、保证或性能。
不要把现有行为改写成新增设计要求；建议或疑似缺陷另列，不能混入事实描述。
未执行仿真、形式验证、综合、STA 或 CDC 检查时明确写“未执行”，不得写“已验证正确”。

## 7. 英文采用 STE 写作原则，中文按语义逐项对应

英文采用 ASD-STE100 的技术写作原则：统一术语，明确主体、条件和动作，优先使用直接动词和简洁句式，减少含糊指代。
本任务采用 STE 风格，不要求机械限制全部词汇，也不宣称已通过完整 ASD-STE100 合规审计。
保留必要的芯片专业术语、代码标识符和逻辑表达式。原理和行为使用描述句，不把系统自动行为写成命令读者操作的步骤。

中文采用对应的中文适配原则：语义准确、术语稳定、条件清楚、时序完整、指代明确。不把英文词数限制换算成汉字数。
中英文按同一语义单元对应，使用稳定编号；推荐每项先 EN，再中文。表格可采用 EN／中文列，避免两份独立文档逐渐不一致。
可以共用代码、公式、证据和表格中的原始数值，不重复翻译标识符或运行日志。
中文可以调整语序，但不得增加、遗漏或改变英文中的事实、条件、否定、并发、范围和不确定性；发现差异时回到源码核对，再同步修正两种语言。
维护一份共享术语表，不把不同含义的“请求出现／接受”“完成／响应”“停顿／保持”混用。

质量优先级：技术事实与语义准确 > 模块覆盖及必要信息完整 > 证据可追溯 > 中英文一致 > 简洁和风格。
不得为了短句删掉必要条件，不得用更多段落掩盖没有读懂代码。

## 8. 输出文件

默认使用 UTF-8 Markdown，目录组织如下：

README.md                         阅读入口、源码基线、配置状态、文档导航与完成范围
00-源码配置与模块清单.md          分析范围、配置依据、层级、实例清单、外部依赖和排除项
01-<TOP>整体说明.md                顶层完整说明、模块关系、端到端过程及关键边界
modules/<模块名>.md               每个有源码定义的子模块一份；包含实例及配置差异
02-中英术语表.md                  推荐术语、中文对应、含义及源码标识符
03-检查结果与待确认项.md          实际检查、覆盖统计、问题、限制与未执行检查
checks/                           仅在实际需要时保留检查脚本和必要运行记录

同名但不同定义的模块，在文件名中加入稳定的路径后缀，避免覆盖。
不要为每个实例复制整篇实现说明，不额外堆积独立英文版、独立中文版或大量中间草稿。
所有面向读者的说明、表格语义和问题项均中英文对应；源码、命令、原始日志和路径保持原样。
README 提供可用的相对链接和建议阅读顺序，不只列文件名。

## 9. 执行顺序与验收

按“检查输入 → 确认配置 → 建立层级清单 → 阅读实现与调用关系 → 写技术说明 → 中英文改写 → 回到源码复核”的顺序执行。
可以按模块分批完成，但共用同一源码基线、配置表和术语表。使用并行任务时明确各自文件归属，避免同时覆盖公共文件。
不要停留在计划或目录骨架；实际生成文档。任务中断时保留已完成内容，并在清单中标明完成、部分完成、未分析及原因，不把任务过大当作已完成。

完成前实际执行以下适用检查，并记录检查方法与结果：
1. 对照层级清单检查模块文档和实例差异说明，分别统计当前有效、条件分支、配置未定、有源码及缺源码的数量。定义清楚统计口径，不把“已发现对象全部有文档”写成“已证明层级完整”。
2. 检查每个模块的 A— I 项是否有实质内容或有依据的不适用说明，不能用“待确认”隐藏未阅读的源码。
3. 检查引用文件、原始行号、标识符、参数和关键值；重新阅读关键引用，确认它支持对应结论。引用存在不等于结论成立。
4. 检查顶层与子模块、端口与父模块连接、参数与配置、场景与控制逻辑是否一致。
5. 检查中英文的条件、数值、极性、否定、时间关系及不确定性是否一致。
6. 检查 Markdown 相对链接、文件命名、空模板、重复内容和未完成项。

脚本负责可确定的存在性、覆盖清单、链接、行号范围及标识符／数值一致性检查；AI 负责机制解释和语义复核，并说明自动检查无法判断的内容。未做人工审阅时明确写“未做人工审阅”。
任何“通过”“失败”“未执行”“无法判断”“不适用”都必须与实际情况一致，不把模型自检称为独立验证。
最后在对话中只汇总：实际生成的文件、模块与实例覆盖、配置是否已确认、最重要的发现或阻断项，以及未执行的验证。不在对话中重复全部文档，也不宣称获得源码以外的验证结论。
````
